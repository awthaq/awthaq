**What to build:** The project has real governance files — a prospective

legally use, contribute to, or responsibly report an issue against this
library.

**Status:** done

## Result

- `LICENSE` (MIT), copyright "effect-auth Engineering" (this spec's own
  established author name throughout `spec/`) — added a `"license": "MIT"`
  field to the root and all 21 workspace package `package.json` files too,
  none of which had one.
- `CONTRIBUTING.md` — project layout, dev setup, the local `pnpm check`
  gate, changeset conventions, PR expectations. Not literally templated
  from the real upstream repo's file (this session has no access to it,
  and the user was explicit that the remote `effect-auth` is an unrelated
  library this session shouldn't touch or reference) — written to the same
  conventional structure any such file follows, filled in entirely with
  this repo's own real process (`pnpm check`, spec-first workflow,
  Changesets).
- `SECURITY.md` — supported-versions table (only the latest `0.x`, since
  there's no `1.0.0` yet), and a real, usable disclosure mechanism: GitHub
  private vulnerability reporting (no invented email address or contact
  that would need faking).
- `CHANGELOG.md` — wired to `@changesets/cli`, not hand-maintained. Two
  real problems found and fixed while proving the pipeline end-to-end:
  1. `.changeset/config.json`'s `fixed` group was empty, contradicting
     `spec/process/definitions-of-done.md`'s own gate 12 ("a fixed version
     group so all `@effect-auth/*` packages move in lockstep") — populated
     it with all 21 workspace packages.
  2. Every package is `"private": true` (correctly — nothing publishes
     yet), and Changesets silently **skips versioning private packages by
     default** (`privatePackages.version` defaults to `false`) — `pnpm
     changeset status`/`version` did nothing at all until this was set
     explicitly. Added `"privatePackages": { "version": true, "tag": false }` —
     versions and changelogs generate locally; the `tag: false` half keeps
     this from trying to create git tags for packages nothing publishes
     yet.

  With both fixed, added one real changeset (documenting the `Admin`
  plugin, ticket 24's own recent, real, user-facing addition) and ran
  `pnpm changeset version` for real — not a dry run. Every workspace
  package bumped `0.0.0` → `0.1.0` in lockstep, and each package now has
  its own real, generated `CHANGELOG.md` (per-package is the correct,
  idiomatic Changesets shape for a monorepo, not a deviation from the
  ticket's own singular phrasing). Added a root `CHANGELOG.md` too, as a
  plain index pointing at each package's own file, so "CHANGELOG.md
  exists" holds literally at the repo root as well.

`pnpm typecheck`/`pnpm lint`/`pnpm format:check` clean workspace-wide
after the version bump; `pnpm test`/`pnpm test:bdd` unaffected (version
numbers don't touch compiled behavior).
