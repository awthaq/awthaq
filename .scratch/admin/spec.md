## Problem Statement

Support and operations teams that need to reproduce a user-reported problem
have no way to act *as* that user from inside effect-auth today — they can
only read logs and guess. `archive/PRD.md` §17's Phase-2 row names this
directly: "`Admin` (impersonation with hard expiry and `actingAs`)." The
underlying contract-stratum shape for it has existed since the very first
design pass (`UserPrincipal.actingAs`, `spec/behaviors/04-contract-stratum.md`)
and the qadi bridge already knows how to project it onto a policy-visible
subject attribute (BEH-EA-142), but nothing has ever minted a session that
actually carries it — `Sessions.issue` has no such parameter, and
`Authentication`'s `resolvePrincipal` never sets it. Every property
`archive/PRD.md` §18 names as this feature's own security model — "off by
default, admin-gated, reason required, hard expiry, dual identity, audit
events" — remains unimplemented and, until this session, unspecified.

## Solution

A new `@effect-auth/admin` plugin, installable the same way `Password`/
`OAuth`/`Passkey`/`Roles` already are, that lets an authorized caller issue a
bounded-lifetime, dual-identity session for another user (`impersonate`), end
it themselves or have another admin end it (`stopImpersonating`/
`forceStop`), and query a durable audit trail of every episode (`list`).
Realizing this requires two small, generic extensions to `@effect-auth/core`
itself — an optional `actingAs` field on `Sessions.issue`/the `Session` row,
and `Authentication`'s `resolvePrincipal` threading it onto
`UserPrincipal.actingAs` — neither of which is `Admin`-specific machinery;
`Admin` is simply the first, and for now only, caller of either.

## User Stories

1. As an application developer, I want to install `Admin` into my
   `Auth.make([...])` tuple the same way I install `Password`/`OAuth`/
   `Roles`, so that adding impersonation is a composition change, not a
   parallel system to integrate.
2. As an application developer, I want `Admin` to reach `Sessions`/`Users`
   with a plain `yield*` inside its own `make`, never via `dependsOn`, so
   that it doesn't repeat the exact mistake `@effect-auth/passkey`'s own
   ticket 06 already found and corrected (`dependsOn` is for depending on
   *another plugin*, never a core service).
3. As an effect-auth maintainer, I want `Sessions.issue` to accept a new,
   optional `actingAs: { type: string; id: string }` parameter and persist it
   immutably on the issued session's row (no `update`/`jsonUpdate` variant,
   matching `secretHash`/`absoluteExpiresAt`'s own shape), so that any future
   plugin — not only `Admin` — could reuse the identical mechanism
   (BEH-EA-209).
4. As an effect-auth maintainer, I want `Sessions.issue` to set
   `idleExpiresAt` equal to `absoluteExpiresAt` whenever `actingAs` is
   present, and `Sessions.verify`'s idle-refresh touch (BEH-EA-052) to skip
   any session whose `actingAs` is non-null, so that INV-EA-014's hard
   expiry holds without inventing a second, redundant flag (BEH-EA-210).
5. As an effect-auth maintainer, I want `Authentication`'s `resolvePrincipal`
   to place a session's `actingAs` onto the `UserPrincipal` it builds,
   unconditionally, so that the chain `Session.actingAs` →
   `UserPrincipal.actingAs` → `AuthSubject.attributes.actingAs`
   (BEH-EA-142, already normative) is finally unbroken end to end
   (BEH-EA-211).
6. As an application developer, I want to gate impersonation with my own
   `canImpersonate: (subject: AuthSubject) => Effect<boolean>` predicate
   supplied via `AdminConfig`, rather than being forced onto
   `@effect-auth/roles` specifically, so that I can delegate the check to
   whatever authorization mechanism I already use (BEH-EA-212).
7. As an effect-auth maintainer, I want `AdminConfig`'s `canImpersonate` to
   default to always-denying when a host application supplies none, so that
   "impersonation off by default" (`archive/PRD.md` §18) holds even for an
   application that installs the plugin but forgets to configure the gate.
8. As a support agent (an admin), I want to call
   `impersonate({ params: { userId }, payload: { reason } })` and receive a
   session that acts as the target user, so that I can reproduce a
   user-reported problem from inside their own account.
9. As a support agent, I want that call to fail before any session is
   issued if I don't pass the configured gate, so that impersonation is
   never a side effect of an otherwise-successful-looking call.
10. As an application developer, I want `reason` required, non-empty after
    trimming, and capped at 1000 characters, so that every impersonation
    episode carries a real, bounded justification (`archive/PRD.md` §18's
    "reason required").
11. As a support agent, I want my own original session left completely
    untouched when I start impersonating, so that I don't lose my own
    access and can simply switch back to my original session's token later
    with no special "handback" step (BEH-EA-213/216).
12. As an effect-auth maintainer, I want `impersonate` to refuse
    self-impersonation (`AdminSelfImpersonationRefused`) and refuse a call
    made from a session that already carries `actingAs`
    (`AdminAlreadyImpersonating`), so that impersonation chains can never
    stack and a caller can never trivially issue a no-op episode
    (BEH-EA-214).
13. As a compliance/security stakeholder, I want every impersonation episode
    recorded in a durable `admin_impersonation` table (`adminUserId`,
    `targetUserId`, `sessionId`, `reason`, `startedAt`, `endedAt`,
    `endedBy`), independent of the session row itself, so that the audit
    trail survives the session's own deletion or expiry (BEH-EA-215).
14. As a support agent, I want `stopImpersonating()` to revoke my current
    impersonation session and record `endedBy: "self"`, with no
    replacement session issued, so that ending impersonation is a single,
    simple call (BEH-EA-216).
15. As a senior admin, I want to be able to call
    `forceStop({ params: { sessionId } })` to end another admin's active
    impersonation episode (recording `endedBy: "forcedByAdmin"`), so that a
    stuck or misused impersonation has a real kill switch rather than
    waiting out the hard expiry (BEH-EA-217).
16. As a security-monitoring stakeholder, I want a distinct
    `auth.admin.impersonationDenied` event published specifically when the
    gate predicate rejects a caller — never for self-impersonation,
    nested-impersonation, or unknown-target refusals, which are ordinary
    validation failures — so that this event is a real "someone attempted
    unauthorized privileged action" signal, not diluted with input-error
    noise (BEH-EA-218).
17. As a support-ops stakeholder, I want to query the audit trail via
    `list()` (full history, newest-first) or `list({ active: true })`
    (currently-live episodes only), gated by the same predicate, so that I
    can both review history and find a `sessionId` to pass to `forceStop`
    (BEH-EA-219).
18. As a target user being impersonated, I want my own sessions completely
    unaffected — never revoked, listed, or otherwise touched by any
    `Admin` operation — so that impersonation is additive, parallel access
    to my account, never a takeover of it (BEH-EA-220).
19. As an effect-auth maintainer, I want the `admin_impersonation` table
    name prefixed per this project's plugin-contract convention, so that
    `runPluginContractTests` passes for this plugin the same way it does
    for every other one.
20. As a client application, I want every distinct failure
    (`AdminImpersonationDenied`, `AdminSelfImpersonationRefused`,
    `AdminAlreadyImpersonating`, `AdminImpersonationNotFound`, a reason
    validation failure) to be its own typed `Schema.TaggedError`, so that I
    can `Effect.catchTags` exhaustively without parsing message strings.
21. As an effect-auth maintainer, I want this spec's decisions — forced-stop
    support, a durable (not merely event-bus) audit trail, three distinct
    audit events rather than one, and a full-history-plus-active-filter
    listing endpoint — all resolved toward the richer option, matching the
    standing "most feature-rich solution" preference confirmed repeatedly
    during this session's own grilling.

## Implementation Decisions

- **Package**: `packages/admin` already exists as an empty scaffold. This
  spec populates it. Dependencies: `@effect-auth/core` (`Sessions`, `Users`,
  `AuthEvents`, `AuthPlugin`), `@effect-auth/sql` (the new
  `admin_impersonation` repository), `@effect-auth/api` (contract stratum
  types), `@effect-auth/qadi`'s `AuthSubject` type only (for
  `canImpersonate`'s signature — not a `dependsOn`, per BEH-EA-212).
- **Core changes, outside `packages/admin` entirely**: `Sessions.issue`
  (`packages/core/src/Sessions.ts`) gains an optional `actingAs` parameter
  and both `layerMemory`/`layerSql` persist it immutably; the `Session`
  model (`packages/sql/src/Models.ts`) gains a nullable `actingAs` column
  (or two plain columns, `actingAsType`/`actingAsId` — an implementation
  detail for whoever writes the ticket, not fixed by this spec);
  `Sessions.verify`'s idle-refresh touch skips any row with `actingAs` set;
  `Authentication.resolvePrincipal` (`packages/server/src/Authentication.ts`)
  reads a session's `actingAs` onto the `UserPrincipal` it builds
  (BEH-EA-209/210/211).
- **`AdminConfig`**: a `Context.Reference` with a fail-closed default
  (`canImpersonate: () => Effect.succeed(false)`), matching
  `SubjectResolver`'s own established "fail-closed slot default" idiom
  (ADR-EA-012) rather than a no-default required config. Fields:
  `maxDuration: Duration.Duration` (impersonation session lifetime),
  `canImpersonate: (subject: AuthSubject) => Effect.Effect<boolean>`
  (BEH-EA-212).
- **`admin_impersonation` table** (plugin-prefixed): `id`, `adminUserId`,
  `targetUserId`, `sessionId`, `reason`, `startedAt`, `endedAt` (nullable),
  `endedBy` (`"self" | "forcedByAdmin" | "expired"`, nullable) — a durable
  audit trail independent of the `Session` row's own lifecycle (BEH-EA-215).
- **Contract** (`HttpApi` group `admin`, `.middleware(Api.Authentication)`):
  `impersonate` (`POST /admin/impersonate`, `{params:{userId}, payload:
  {reason}}` → a session DTO, mirroring the shape every other sign-in
  endpoint already returns), `stopImpersonating` (`POST
  /admin/stop-impersonating`, no body → `204`), `forceStop` (`POST
  /admin/force-stop`, `{params:{sessionId}}` → `204`), `list` (`GET
  /admin`, optional `active` query param → an array of impersonation-record
  DTOs).
- **Error taxonomy**: `AdminImpersonationDenied` (403 — gate predicate
  rejected), `AdminSelfImpersonationRefused` (400), `AdminAlreadyImpersonating`
  (409), `AdminImpersonationNotFound` (404 — `forceStop` on an unknown or
  already-ended session id), plus the reason-validation failure folded into
  the payload schema itself (a `Schema.String` with a length/non-empty
  refinement, answering the framework's own standard `400`).
- **Audit events**: `auth.admin.impersonationStarted` (adminUserId,
  targetUserId, reason, sessionId), `auth.admin.impersonationStopped`
  (sessionId, endedBy), `auth.admin.impersonationDenied` (gate rejections
  only) — three new tags added to `AuthEvents`'s closed `AuthEvent` union
  (BEH-EA-218). **Correction from this spec's first draft**: `auth.session.issued`
  is not an existing published tag — `AuthEvents.ts` names it only as an
  illustrative example of what its registry design anticipates, with no
  `SessionIssuedEvent` in the actual `AuthEvent` union today. This spec does
  not require adding one; `impersonationStarted` is this plugin's own
  complete signal.
- **`dependsOn: []`** — same reasoning as `@effect-auth/passkey`'s own
  corrected ticket 06: `Sessions`/`Users` are core services reached
  directly, and the admin gate is a config predicate, not another plugin.

## Testing Decisions

- A good test here asserts observable outcomes (a session actually issued
  with `actingAs` set, an audit row's persisted fields, a specific typed
  error for a specific refusal, an event actually published) — never that a
  particular internal function was called with particular arguments.
- **Core-level extension tests** (`packages/core/test/Sessions.test.ts`,
  extended): `issue` persisting `actingAs` immutably; `verify` never
  advancing `idleExpiresAt` for a row with `actingAs` set, via `TestClock`
  the same way BEH-EA-052's existing idle-refresh tests already do.
  (`packages/server/test/Authentication.test.ts`, extended):
  `resolvePrincipal` placing a session's `actingAs` onto the resolved
  `UserPrincipal` — mirrors the existing test's own shape for
  `userId`/`sessionId`.
- **`packages/admin/test/ImpersonationRecords.test.ts`**: the
  `admin_impersonation` persistence layer against both `layerMemory` and
  `layerSql`, the same contract-suite-over-multiple-layers pattern
  `packages/passkey/test/PasskeyCredentials.test.ts` already establishes —
  create/find round-tripping every field, `endedAt`/`endedBy` set exactly
  once, `active`-filtered listing excluding ended rows.
- **`packages/admin/test/Admin.test.ts`** (mirroring
  `packages/passkey/test/Passkey.test.ts`'s shape): domain-level, a plain
  in-test `canImpersonate` function (no `Layer.mock` needed — it's a bare
  config function, not a service) exercising: a denied gate producing
  `AdminImpersonationDenied` and the matching event, without issuing a
  session; a successful `impersonate` issuing a real session via
  `Sessions` with `actingAs` set and leaving the caller's own session
  untouched; self-impersonation and nested-impersonation refusals;
  `reason` validation; `stopImpersonating`/`forceStop` each revoking the
  right session and setting the right `endedBy`; the target's own sessions
  provably unaffected throughout.
- **`packages/admin/test/AuthComposition.test.ts`** (mirroring every other
  plugin's own): proves `Auth.make([Admin])` composes with `dependsOn: []`.
- **`packages/admin/test/AuthHttp.test.ts`** (mirroring
  `packages/passkey/test/AuthHttp.test.ts`'s shape): the `admin` group's own
  contract end to end over a real `HttpRouter`/`HttpRouter.toWebHandler` —
  `impersonate` answering `200` with a session cookie for the target
  identity, `stopImpersonating`/`forceStop` answering `204`, `list`
  answering the audit rows, `403`/`400`/`409`/`404` landing on the correct
  typed errors' real HTTP status.

## Out of Scope

- Any new `@effect-auth/client`/`@effect-auth/react` impersonation-aware
  helper (e.g. reading `attributes.actingAs` to render a "staff bar") — no
  plugin in this codebase has bespoke client bindings today (the same
  precedent `@effect-auth/passkey`'s own spec already followed); the
  generic `AtomHttpApi`/`HttpApiClient` machinery already exposes whatever
  this plugin's contract group contributes.
- A dedicated `AdminPrincipal` tagged principal kind — considered during
  this session's grilling and rejected in favor of reusing
  `UserPrincipal.actingAs`, which BEH-EA-142/211 already give a complete,
  normative meaning to.
- The CLI's `seed admin` command (`spec/behaviors/26-cli.md`, M6/Tooling) —
  an unrelated feature that provisions the first privileged account; no
  overlap with this plugin's own impersonation flow.
- Rate limiting specific to `impersonate`/`forceStop` — not named as a
  requirement anywhere in `archive/PRD.md`; an application that wants it can
  already register a rule against this plugin's own contract groups through
  the existing `RateLimits` registry (`spec/behaviors/14-rate-limiting.md`)
  with no new capability needed.
- Any notification/webhook delivery for the three audit events beyond
  publishing them on `AuthEvents` — a consuming application wires its own
  observer (`AuthEvents.on`) the same way every other event-driven
  integration in this codebase already does.

## Further Notes

- Every richness-vs-simplicity decision in this spec (forced-stop support,
  a durable audit table rather than events-only, three distinct audit
  events, a full-history-plus-`active`-filter listing endpoint) traces back
  to the same standing preference already recorded from the passkey
  session: "we always want the most feature-rich solution," restated
  identically three times across this session's own grilling rounds.
- Unlike every other plugin spec produced so far in this project, this one
  required touching two files outside its own package
  (`packages/core/src/Sessions.ts`, `packages/server/src/Authentication.ts`)
  before the plugin itself can do anything real. Whoever tickets this work
  should treat those as their own prerequisite slice — `Admin`'s domain
  logic has nothing to build against until `Sessions.issue` actually
  accepts `actingAs`.
- `spec/models/15-admin-impersonation.md` (MOD-EA-015) is now superseded by
  `spec/behaviors/27-admin-impersonation.md` for every question it left
  open. Following this project's own established practice (`spec/models/
  03-passkey-webauthn.md` was never retroactively marked superseded once
  `17-passkey.md` existed, nor once passkey actually shipped), this spec
  does not edit MOD-EA-015's own text — it is left as the historical
  sketch it always was.
- `spec/invariants.md`'s INV-EA-014, `spec/traceability.md`'s §1 table,
  `spec/behaviors/index.yaml`, and `spec/behaviors/26-cli.md`'s own footer
  link were all updated in this same pass (CCR-EA-004) to keep the
  cross-reference graph consistent now that BEH-EA-209 through 220 are
  real.
