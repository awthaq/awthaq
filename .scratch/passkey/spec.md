# @effect-auth/passkey

Status: ready-for-agent

> Generated by `/mattpocock-skills:to-spec`, following a `/wayfinder`-style
> grilling session that found most of the "design" already normatively
> settled in `spec/behaviors/17-passkey.md` (BEH-EA-129 through 136) — no
> wayfinder map was created; four remaining open questions were resolved
> directly with the user and are recorded in Implementation Decisions below.

## Problem Statement

effect-auth ships `Password` and `OAuth` as credential plugins, but no
phishing-resistant, passwordless sign-in method. An application wanting
WebAuthn-based passkey sign-in today has nothing to install — `@effect-auth/
passkey` is an empty package scaffold, and the `WebAuthn` port it would
depend on doesn't exist in `@effect-auth/ports` either. Every application
that wants this has to build the entire ceremony (registration/
authentication options, response verification, challenge storage, credential
management, origin validation) from scratch, with all the CVE-class pitfalls
`research/06-webauthn-passkeys.md` documents (three 2026 CVEs across
independent WebAuthn server libraries, each one a case of "the cryptography
was verified correctly; the glue — which user, which origin, which session —
was wrong").

## Solution

A new `@effect-auth/passkey` plugin, installable the same way `Password`/
`OAuth` already are, providing registration, authentication, and credential
management ceremonies against a new `WebAuthn` port (`@effect-auth/ports`)
that wraps `@simplewebauthn/server` — never hand-rolling CBOR/COSE/
attestation parsing — plus a plugin-owned `ChallengeStore` capability for
the single-use, short-TTL ceremony state every WebAuthn ceremony needs.

A passkey credential is registered as an ordinary `@effect-auth/core`
`Accounts` link (`providerId: "passkey"`), so the existing
"can't remove your last remaining credential" invariant (BEH-EA-045,
`LastAccountRefusal`) covers it automatically — a passkey is just another
credential kind under a rule that already exists, per `spec/models/
03-passkey-webauthn.md`'s own framing.

## User Stories

1. As an application developer, I want to install `Passkey` into my
   `Auth.make([...])` tuple the same way I install `Password`/`OAuth`, so
   that adding passwordless sign-in is a one-line composition change, not a
   parallel authentication system to integrate.
2. As an application developer, I want `Passkey` to depend on `Sessions`/
   `Users` (via `AuthPlugin.Service`'s `dependsOn`), so that a passkey
   sign-in produces the exact same kind of session every other credential
   plugin already produces.
3. As an application developer, I want the `WebAuthn` port's default
   implementation (`layerSimpleWebAuthn`) to wrap `@simplewebauthn/server`,
   so that I never have to trust my own (or effect-auth's) CBOR/COSE/
   attestation parsing — a maintained, spec-aligned library does that work.
4. As a plugin author or effect-auth maintainer, I want `WebAuthn` to stay a
   port (never a plugin-provided implementation), so that swapping the
   underlying WebAuthn library later is a `Layer.provide` change, not a
   plugin rewrite.
5. As an application developer, I want `ChallengeStore` to ship three ready
   implementations — `layerMemory` (tests), `layerSql` (atomic-claim,
   SQLite-backed), `layerCookie` (stateless) — with **no forced default**,
   so that I can pick the backend that fits my deployment (a traditional
   server, an edge/serverless function with no shared store) without
   effect-auth guessing wrong for me.
6. As an application developer deploying at the edge with no shared
   database connection pool available to the request, I want
   `ChallengeStore.layerCookie`, so that a passkey ceremony's challenge
   round-trips in a signed cookie instead of requiring a database write.
7. As an application developer, I want `ChallengeStore.layerSql` to use the
   same atomic-claim SQL technique `@effect-auth/core`'s `Verification`
   service already proved out (ADR-EA-016: `INSERT ... ON CONFLICT ... DO
   UPDATE ... RETURNING`, no separate delete-then-insert race), so that
   challenge claiming inherits an already-reviewed, concurrency-safe
   pattern rather than a second, independently-written one.
8. As a user registering a passkey, I want the server to persist my
   credential's public key, counter, device type, backup-state flag,
   transports, and AAGUID only after `WebAuthn.verifyRegistration` succeeds
   against the challenge issued for that specific ceremony, so that a
   forged client-side "success" can never create a credential the server
   never actually verified (BEH-EA-130).
9. As a user, I want a successful authentication ceremony to issue a
   session through the same core `Sessions` capability every other sign-in
   method uses, so that idle/absolute expiry and sliding refresh behave
   identically regardless of which credential type I signed in with
   (BEH-EA-131).
10. As a security-conscious operator, I want every challenge to be
    single-use and deleted on every verification attempt — success or
    failure — with a bounded TTL (five minutes) if never used, so that a
    replayed or abandoned ceremony can never be completed later
    (BEH-EA-132).
11. As a security-conscious operator, I want origin verification to compare
    `(scheme, host, port)` as an exact tuple against my configured
    `origins` list, and `rpId` validated as a registrable-domain suffix —
    never a bare host match — so that my deployment isn't exposed to the
    class of bug CVE-2026-30964 documents (BEH-EA-133).
12. As an application developer, I want to configure `origins` as an array,
    so that multiple deployment origins (a `www.` host and its apex, a
    staging environment) are each listed explicitly.
13. As a user, I want `passkey.remove` to refuse deleting my only remaining
    authentication credential, succeeding once at least one other
    credential (another passkey, a password, or a linked OAuth account)
    would remain, so that I can never lock myself out with no recovery path
    (BEH-EA-134).
14. As an effect-auth maintainer, I want that guard to be the existing
    `Accounts`/`LastAccountRefusal` mechanism (BEH-EA-045), reached because
    a passkey credential is registered as an ordinary `Accounts` link, not a
    second, independently-implemented "last credential" check specific to
    passkeys.
15. As an application developer, I want attestation to default to `"none"`,
    with `"direct"`/`"enterprise"` available only as explicit opt-in
    configuration never required for v1 registration to succeed, so that
    my consumer-facing passkey flow isn't forced through FIDO Metadata
    Service validation it doesn't need (BEH-EA-135).
16. As a client application, I want every distinct passkey ceremony failure
    to be its own typed `Schema.TaggedError` (`PasskeyChallengeInvalid`,
    `PasskeyOriginMismatch`, `PasskeyRpIdMismatch`,
    `PasskeyCredentialNotFound`, `PasskeyVerificationFailed`,
    `PasskeyUserVerificationRequired`, `PasskeyCounterAnomaly`,
    `PasskeyLastCredential`), so that I can `Effect.catchTags` exhaustively
    without parsing message strings (BEH-EA-136).
17. As an attacker attempting username enumeration, I want an
    unknown-credential authentication failure to reveal nothing about
    whether any credential was registered for the supplied identifier, so
    that the passkey flow doesn't leak account existence the way
    `InvalidCredentials` already refuses to for password sign-in
    (BEH-EA-136).
18. As an application developer, I want `conditionalCreate` support at v1
    (a dedicated, session-bound registration-options endpoint that accepts
    the relaxed UP=0/UV=0 flags Chrome's conditional-create flow produces),
    defaulting **on**, so that my users get the single biggest passkey
    adoption lever (per Corbado's 2026 benchmark) without extra
    integration work, while still being able to turn it off for a leaner
    v1 surface if I choose.
19. As a user who just signed in with a password, I want the option to be
    silently, opportunistically prompted to upgrade to a passkey in the
    same session (conditional create), so that enrollment doesn't require a
    separate, deliberate trip to account settings.
20. As an application developer, I want both a username-first authenticate
    path (`allowCredentials` scoped to a known user) and a usernameless,
    fully discoverable-credential path (`allowCredentials: []`, the
    assertion's `userHandle` resolving the user after the fact) as
    first-class, always-available options — neither gated behind an extra
    opt-in flag — so that I can choose the UX that fits my app without the
    plugin dictating one default posture for everyone.
21. As a user managing my passkeys, I want to list, rename, and delete my
    registered credentials, with AAGUID-derived friendly labels (falling
    back to a generic label when unavailable), so that I can tell "my
    laptop's passkey" from "my phone's passkey" in account settings.
22. As an application developer, I want per-credential `deviceType`
    (`singleDevice`/`multiDevice`) and `backedUp` state persisted and
    updated on every authentication, so that I can build lockout-risk
    warnings (a device-bound credential with no backup) without
    implementing BE/BS tracking myself.
23. As an effect-auth maintainer, I want a per-user random `webauthnUserID`
    (distinct from the internal user id) used as the WebAuthn `user.id`
    handle, so that the authenticator/credential manager never sees the
    application's own internal identifiers.
24. As an effect-auth maintainer, I want the `passkey_credential` table name
    prefixed per this project's plugin-contract convention (every declared
    table carries its own plugin's id prefix), so that `runPluginContractTests`
    passes for this plugin the same way it does for every other one.
25. As a test author, I want plugin-level ceremony logic (challenge
    single-use enforcement, last-credential guard, typed error mapping,
    session issuance) testable via `Layer.mock(WebAuthn, {...})` (BEH-EA-195's
    already-established partial-double pattern), so that these tests don't
    depend on real CBOR/attestation parsing at all.
26. As a test author, I want a separate, narrower test of
    `WebAuthn.layerSimpleWebAuthn` itself against real (or
    `@simplewebauthn`-provided) test vectors, so that the actual
    cryptographic wrapper is verified independently of the plugin logic
    that sits above it.
27. As an application developer, I want the plugin's own documentation to
    state plainly that a passkey must never be a user's only factor
    without a documented recovery path (email verification / another
    linked credential), so that I don't accidentally ship a lockout trap.
28. As an effect-auth maintainer, I want this spec's scope to explicitly
    exclude any new client-side (`@effect-auth/client`) passkey-specific
    helper (a `passkeyClient()` wrapping `@simplewebauthn/browser`), so that
    this plugin follows the same precedent every other plugin already
    does — no plugin in this codebase has bespoke client bindings today;
    the generic `AtomHttpApi`/`HttpApiClient` machinery already exposes
    whatever HTTP group this plugin contributes, and the application calls
    `navigator.credentials.create()`/`.get()` itself, same as it would for
    any other endpoint.
29. As an effect-auth maintainer, I want enterprise attestation (MDS3
    validation) explicitly out of scope for this plugin's first
    implementation, so that no infrastructure is built for a validation
    path with zero current caller — the config surface accepts
    `"enterprise"` as a value, but nothing behind it is implemented yet.

## Implementation Decisions

- **Package**: `packages/passkey` already exists as an empty scaffold. This
  spec populates it. Dependencies: `@effect-auth/core` (`Sessions`, `Users`,
  `Accounts`, `AuthPlugin`), `@effect-auth/ports` (the new `WebAuthn` port),
  `@effect-auth/api` (contract stratum types), and `@simplewebauthn/server`
  v14 (the only new external runtime dependency this plugin introduces).
- **`WebAuthn` port** (new, in `@effect-auth/ports`, per `spec/overview.md`'s
  Ports-stratum table and BEH-EA-129): a 4-method interface —
  `registrationOptions`, `verifyRegistration`, `authenticationOptions`,
  `verifyAuthentication` — with exactly one shipped implementation,
  `layerSimpleWebAuthn`, wrapping `@simplewebauthn/server`. No `layerMemory`/
  `layerNoop` variant is needed for this port itself, since plugin-level
  tests stub it out entirely via `Layer.mock` (see Testing Decisions) rather
  than needing a stateful fake implementation.
- **`ChallengeStore`** (new, owned by `@effect-auth/passkey`, **not** a
  cross-plugin port in `@effect-auth/ports`): only this plugin needs
  single-use ceremony-challenge state, so it doesn't belong in the shared
  ports stratum alongside `PasswordHasher`/`Mailer`/`WebAuthn`, which
  `spec/overview.md` names explicitly as the complete ports list. Interface
  per BEH-EA-132: `issue(scope): Effect<Redacted<string>>`,
  `consume(scope, challenge): Effect<boolean>`, deleting the challenge on
  every consume attempt regardless of outcome. Ships three implementations,
  **no forced default** (a deliberate choice — see Further Notes for the
  reasoning this diverges from `WebAuthn`'s single-implementation shape):
  - `layerMemory` — `Ref`-backed, for tests.
  - `layerSql` — SQLite-backed, using the same atomic-claim technique
    ADR-EA-016 already established for `Verification`'s `reserve`
    (`INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`, single-use via a
    partial unique index or an explicit "already consumed" column checked
    in the same statement).
  - `layerCookie` — stateless: the challenge round-trips in a signed
    HttpOnly cookie rather than a database row, for edge/serverless
    deployments with no shared store.
  - Kept as an **independent capability**, not folded into
    `@effect-auth/core`'s existing `Verification` service — `Verification`'s
    shape is identifier-keyed with a payload, built for sign-up/reset flows;
    `ChallengeStore`'s scope is a bare WebAuthn ceremony with neither field.
    Forcing one shape onto the other's data model to save a file was
    rejected in favor of reusing `Verification`'s proven *technique*
    (the SQL claiming pattern) without reusing its *code* or *table*.
- **Passkey credential storage**: a dedicated `passkey_credential` table
  (plugin-prefixed per this project's table-naming convention), one row per
  credential, FK'd to the user — `id` (base64url credential id),
  `webauthnUserId` (a random per-user handle, distinct from the internal
  user id, per BEH-EA-129's "who is asking, independent of what they may
  do" framing extended to "never leak the internal id to the authenticator"),
  `publicKey`, `counter`, `deviceType`, `backedUp`, `transports`, `aaguid`,
  `name` (user-chosen label), `lastUsedAt`, `createdAt`.
- **Registration also creates an `Accounts` link**
  (`providerId: "passkey"`, `subject: <credential id>`) in the same
  operation that inserts the `passkey_credential` row — this is what makes
  BEH-EA-134's "refuse to delete the last remaining credential" guard
  automatic: `Accounts`'s existing `LastAccountRefusal` (BEH-EA-045) already
  enforces this generically across every credential-contributing plugin.
  `passkey.remove` calls the same account-unlinking path every other
  plugin's credential removal already goes through, then deletes the
  `passkey_credential` row; a `LastAccountRefusal` from that call is mapped
  to this plugin's own `PasskeyLastCredential` typed error at the handler
  boundary — the same "wrap a core error into a plugin-contract error"
  pattern `Password`'s own handlers already use.
- **Config**: a `PasskeyConfig` `Context.Reference` with a default, and a
  `config(partial)` override function — the identical pattern `Password`'s
  own `PasswordConfig`/`config()` already establishes (ADR-EA-011,
  "configuration is a service with a default"). Fields: `rpId`, `rpName`,
  `origins: ReadonlyArray<string>` (exact `(scheme, host, port)` tuples per
  BEH-EA-133), `attestation: "none" | "direct" | "enterprise"` (default
  `"none"`), `authenticatorSelection` (`residentKey`/`userVerification`,
  default `"preferred"`/`"preferred"`), `conditionalCreate: boolean`
  (default `true`, per the grilling decision below).
- **Ceremony endpoints** (`HttpApi` group `passkey`): `register/options`,
  `register/verify`, `register/options/conditional` (session-bound,
  accepts UP=0/UV=0 — the relaxed conditional-create path), `authenticate/
  options` (accepts an optional identifier for username-first, or none for
  usernameless — both first-class, neither gated), `authenticate/verify`,
  `credentials` (list), `credentials/:id` (rename via `PATCH`, delete via
  `DELETE`).
- **Conditional Create ships at v1, default on** — resolved directly with
  the user during this spec's grilling session, given an explicit "prefer
  the richer, more complete option over the simpler one" standing
  preference. The dedicated conditional-create endpoint exists from day
  one and is enabled by default; an application can set
  `conditionalCreate: false` for a leaner v1 surface.
- **Usernameless and username-first authenticate paths both ship as
  first-class**, neither requiring separate opt-in configuration — also
  resolved per the same richness-over-simplicity preference. Plugin
  documentation still recommends username-first as the safer starting
  point for apps unsure which to use, but the capability itself isn't
  restricted.
- **Enterprise attestation (MDS3 validation) is explicitly not
  implemented** — `attestation: "enterprise"` is an accepted config value
  (per BEH-EA-135's requirement that it be available as opt-in
  configuration) but no MDS3 metadata validation exists behind it yet, no
  matter how the config is set. Building that validation now, with no
  current caller, was rejected even under the richness-over-complexity
  preference — it's the specific kind of speculative infrastructure this
  project has already avoided elsewhere (`ApiKeyPrincipal`/
  `ServicePrincipal` scopes, per `@effect-auth/qadi`'s own
  `SubjectResolver.ts` header comment).
- **No new `@effect-auth/client` passkey-specific helper.** Every existing
  plugin (`Password`, `OAuth`) is consumed through the fully generic
  `AtomHttpApi`/`HttpApiClient` machinery already in `@effect-auth/client` —
  no plugin has bespoke client bindings today. This plugin follows that
  precedent rather than introducing a new kind of thing; an application
  calls the generated `passkey` group's endpoints directly and orchestrates
  `navigator.credentials.create()`/`.get()` itself. A `passkeyClient()`
  convenience wrapper (per `research/06-webauthn-passkeys.md`'s suggestion)
  is explicitly deferred, not designed here.

## Testing Decisions

- A good test here asserts observable ceremony outcomes (a registered
  credential's persisted fields, a session issued, a specific typed error
  for a specific failure mode) — never that a particular internal function
  was called with particular arguments.
- **Plugin-level tests** (`packages/passkey/test/Passkey.test.ts`, mirroring
  `packages/password/test/Password.test.ts`'s shape) stub `WebAuthn` via
  `Layer.mock(WebAuthn, {...})` (BEH-EA-195's established partial-double
  pattern) — these tests exercise the plugin's own logic (challenge
  issue/consume/single-use enforcement via a real or memory-backed
  `ChallengeStore`, the last-credential guard via a real `Accounts`, typed
  error mapping, session issuance through real `Sessions`) without any real
  CBOR/attestation parsing.
- **A separate, narrower test of `WebAuthn.layerSimpleWebAuthn`**
  (`packages/ports/test/WebAuthn.test.ts`) verifies the actual
  `@simplewebauthn/server` wrapper against known-good test vectors (fixed
  key material / SimpleWebAuthn's own documented test fixtures, or Chrome
  DevTools' virtual authenticator where a real browser-driven test is
  warranted) — kept independent of the plugin logic above it.
- **`ChallengeStore` tests** (`packages/passkey/test/ChallengeStore.test.ts`):
  the same contract-suite-over-multiple-layers pattern `Verification.test.ts`
  already uses (per this session's own earlier `Verification.layerSql`
  work) — one shared assertion suite run against `layerMemory`, `layerSql`,
  and `layerCookie`, proving single-use and TTL-expiry (via `TestClock`)
  identically across all three.
- **`AuthComposition.test.ts`** (mirroring `Password`'s/`OAuth`'s own): proves
  `Auth.make([Passkey])` composes, with its `dependsOn: [Sessions, Users]`
  satisfied.
- **`AuthHttp.test.ts`** (mirroring `Password`'s/`OAuth`'s own): the `passkey`
  group's own contract end to end over a real `HttpRouter`/
  `HttpRouter.toWebHandler`, `WebAuthn` still mocked, proving the actual
  wire-level request/response shapes (status codes, `Set-Cookie` on
  successful authentication) rather than just the domain-level ceremony
  logic.
- Cases to cover, at minimum: registration persists all documented fields
  only after verification succeeds (never on a client-asserted success
  alone); a replayed challenge fails; an expired, never-used challenge
  fails; origin/rpId mismatch fails with the correct typed error;
  authentication issues a real session via `Sessions`; deleting a user's
  only credential fails with `PasskeyLastCredential`, succeeding once a
  second credential (another passkey, or a linked password/OAuth account)
  exists; an unknown-credential authentication failure doesn't reveal
  whether the supplied identifier has any registered credential
  (BEH-EA-136's enumeration-safety requirement); both username-first and
  usernameless authenticate paths resolve correctly; the conditional-create
  endpoint accepts UP=0/UV=0 while the ordinary registration endpoint does
  not.

## Out of Scope

- Any new `@effect-auth/client` passkey-specific helper
  (`passkeyClient()`/`@simplewebauthn/browser` wrapping) — deferred, per the
  no-new-client-seam decision above.
- Enterprise attestation / FIDO MDS3 validation — config value accepted,
  nothing implemented behind it.
- Related Origin Requests (multi-domain passkeys via
  `/.well-known/webauthn`) — not mentioned in `spec/behaviors/17-passkey.md`
  and not requested; revisit if a real multi-domain deployment need arises.
- The Signals API (`signalUnknownCredential`, `signalAllAcceptedCredentials`,
  `signalCurrentUserDetails`) — a real, documented WebAuthn L3 feature
  research recommends, but not named in any BEH-EA requirement; a
  reasonable follow-up, not designed here.
- Chrome DevTools virtual-authenticator-driven browser test tooling as a
  first-class `@effect-auth/test` export — useful, but a tooling-stratum
  concern separate from this plugin's own spec.
- Passkey-first registration (enrolling a passkey before any session
  exists, via `resolveUser`/out-of-band verification-token infrastructure)
  — `research/06-webauthn-passkeys.md` names this as a real pattern
  (better-auth 1.6), but no BEH-EA requirement covers it and it wasn't
  raised in this spec's grilling session; revisit as a separate effort if
  wanted.

## Further Notes

- The three decisions made directly with the user during this spec's
  grilling session (`ChallengeStore`'s three-implementation, no-forced-
  default shape; `ChallengeStore` as an independent capability rather than
  a `Verification` extension; Conditional Create shipping at v1 default-on;
  both authenticate paths first-class) all trace back to one explicit
  standing preference the user stated during that session: "we don't care
  about the complexity but we care about the flexibility... the user
  should have the most feature rich solution." This preference does not
  extend to building genuinely speculative infrastructure with no current
  caller (enterprise attestation stays unimplemented for exactly that
  reason) — confirmed narrowly with the user in the same session.
- **A stale claim, found and corrected during this spec's own grilling
  session**: `@effect-auth/ports/src/index.ts`'s header comment currently
  states that `WebAuthn`'s port is "deliberately not yet implemented" and
  that "nothing in `spec/` or `archive/` names WebAuthn's own port
  methods." This is wrong — `spec/behaviors/17-passkey.md`'s BEH-EA-129
  already gives the port's exact 4-method interface, and BEH-EA-130
  through 136 already normatively settle most of what this plugin needs.
  This is the second stale claim this project has found and corrected in
  as many sessions (the first being the `@effect-atom/atom`
  React-reactivity blocker corrected during the `@effect-auth/react` work).
  Whoever implements this spec should update that header comment as part
  of the change.
- `spec/decisions/016-verification-sql-claiming.md` (ADR-EA-016) itself
  cites the (stale) "WebAuthn port is deferred" claim as a supporting
  analogy for why it scoped `Verification`'s SQL-claiming decision to
  SQLite only. That analogy resting on a false premise doesn't undermine
  ADR-EA-016's own decision (which stands on its own reasoning about
  dialect support), but is worth knowing about if ADR-EA-016 is ever
  revisited.
- `research/06-webauthn-passkeys.md`'s "Open questions for the user"
  section (5 items) is fully resolved by this spec except item 5
  (enterprise attestation timing, resolved as "deferred, not flag-gated"
  — the strictest of its three offered options) and item 4 (last-credential
  delete guard, resolved as already-settled by BEH-EA-134/`Accounts`, not
  requiring the richer "inline re-verification" option that research
  proposed as an alternative).
