## Problem Statement

An application built on effect-auth today gets a browser client
(`@effect-auth/client`, `@effect-auth/react`) but nothing for the
server-rendering half of a Next.js app. Concretely, a Next.js developer has
no supported way to:

- Verify a session cookie against the database from a React Server Component
  or a server action (they'd have to hand-roll cookie parsing and reach into
  `@effect-auth/core` themselves, with no guidance on the pitfalls).
- Distinguish, for `proxy.ts` (Next's routing layer, renamed from
  `middleware.ts` in Next 16.3), a cheap "is there a session cookie at all"
  check from the real, database-backed verification — and every published
  Next.js/Effect guide gets the `globalThis`-pinning required to survive
  Next's dev-server module reloading wrong or omits it, so whatever pattern
  ships here needs to get it right the first time.
- Get a `Set-Cookie` a server action produces (a fresh session after sign-in,
  a cleared one after sign-out) to actually land in Next's own cookie jar,
  since a server action never sees the raw HTTP response object an ordinary
  Effect HTTP handler would write that header onto.

Without this package, every Next.js app integrating effect-auth reinvents
this plumbing from scratch, gets the `globalThis` pitfall wrong at least
once, and has no single documented seam for "did proxy.ts's optimistic check
get mistaken for the real boundary."

## Solution

A new package, `@effect-auth/next`, providing three functions that make the
existing rule explicit and impossible to get backwards:

1. **`getSession`** — the real, database-verified boundary. Called from a
   React Server Component or a server action, it takes the incoming request's
   headers, extracts and verifies the session cookie in-process against
   `@effect-auth/core`'s `Sessions` service, and returns the resolved
   principal, user, and session — or `undefined` if there is no valid
   session.
2. **`hasSessionCookie`** — the optimistic, `proxy.ts`-only check. Presence
   only, no database call, no principal resolution. Its own doc comment says
   plainly that it proves nothing and that the real check is `getSession`.
3. **`withNextCookies`** — bridges a `Set-Cookie` produced by effect-auth's
   own composed HTTP router (a sign-in, sign-out, or CSRF rotation) into
   Next's `next/headers` cookie jar, for use inside a server action.

The package deliberately does not attempt to own Effect runtime
construction, does not depend on `@effect-auth/qadi`, and does not implement
authorization decision hydration — `@qadi/react`'s `hydrateDecisions`/
`dehydrateDecisions`/`QadiProvider` (already re-exported verbatim from
`@effect-auth/react`) already solve that, and effect-auth's whole design
stance is to stay out of authorization entirely (ADR-EA-009).

## User Stories

1. As a Next.js app developer, I want to verify a session cookie against the
   database from a Server Component, so that a page can trust `session` is
   real before rendering protected content.
2. As a Next.js app developer, I want `getSession` to return the resolved
   principal and user alongside the session record, so that I don't have to
   separately call `Users.findById` myself on every protected page.
3. As a Next.js app developer, I want `getSession` to return `undefined`
   (never throw) for a missing, expired, or otherwise invalid cookie, so
   that "no session" and "session lookup failed" are the one ordinary case a
   page handles with a plain `if (!session)`, not an exception to catch.
4. As a Next.js app developer, I want a cheap, cookie-presence-only check
   usable from `proxy.ts`, so that I can redirect an obviously-anonymous
   visitor away from an app shell before a page even renders, without paying
   a database round trip on every request `proxy.ts` sees.
5. As a Next.js app developer, I want `hasSessionCookie`'s own documentation
   to say explicitly that it is not a security boundary, so that I don't
   mistake a passed `proxy.ts` check for real authentication the way
   CVE-2025-29927 punished apps for doing.
6. As a Next.js app developer, I want every page and server action to
   independently re-verify the session rather than trust anything upstream
   (a header `proxy.ts` set, a value the client posted back), so that a
   revoked session or changed role takes effect on the very next request
   that reaches real application code.
7. As a Next.js app developer, I want a way to resolve a qadi subject from
   the principal `getSession` gives me, so that I can `decide`/`filter`
   against it — using `@qadi/core`'s `SubjectResolver` directly myself,
   since `@effect-auth/next` does not resolve subjects on my behalf.
8. As a Next.js app developer, I want a server action that issues or revokes
   a session to have its `Set-Cookie` actually reach the browser, so that
   the next request the browser makes carries the new (or absent) cookie
   without me hand-rolling header plumbing.
9. As a Next.js app developer, I want `withNextCookies` to only ever be
   asked to bridge cookies from effect-auth's own composed HTTP router (sign
   in, sign out, session refresh, CSRF rotation), so that its contract is
   exactly "the same `Set-Cookie` the browser would have gotten over the
   wire, now written into Next's jar instead" — not an open-ended promise to
   intercept cookies from arbitrary domain-service calls that don't produce
   any today.
10. As a Next.js app developer, I want the package's own documentation to
    show the `globalThis`-pinned `ManagedRuntime` pattern Next's dev server
    requires, so that I don't spend an afternoon debugging a devtools log
    that goes empty after a hot reload, the way every unguided Effect+Next
    integration attempt does.
11. As a Next.js app developer, I want `getSession`, `hasSessionCookie`, and
    `withNextCookies` to each take an explicit runtime (or already-resolved
    data) as an argument rather than reaching for a hidden module-level
    singleton inside `@effect-auth/next` itself, so that the package makes
    no assumption about my app's own composed `Layer` type, which it cannot
    know generically.
12. As a Next.js app developer building a server action that mutates
    something unrelated to auth (e.g. renaming a display name via a plain
    domain-service call), I want to know that plain domain services never
    set cookies today, so that I don't wrap an arbitrary `Users`/`Sessions`
    domain call in `withNextCookies` expecting it to do something it
    structurally cannot.
13. As a plugin author whose plugin issues a session (e.g. `Password`'s
    sign-in), I want that issuance to already go through effect-auth's
    composed HTTP router and its existing `HttpApiBuilder.securitySetCookie`
    mechanism, so that `withNextCookies` needs no special-casing per plugin
    to pick up its `Set-Cookie`.
14. As an effect-auth maintainer, I want `@effect-auth/next`'s own
    dependency graph to stay `@effect-auth/core` + `@effect-auth/api` +
    `@effect-auth/react` (no `@effect-auth/qadi`), so that the client-stratum
    packages stay below the authorization bridge, consistent with the
    stratum-layering rule that already forced `@effect-auth/api`'s
    `Subject.ts`/`@effect-auth/qadi`'s `SubjectApi.ts` split earlier in this
    project's history.
15. As a test author, I want `@effect-auth/next`'s own tests to run over
    `@effect-auth/test`'s `TestAuth.layer` whole-pipeline harness (memory
    ports, no real database, no real network listener), consistent with
    every other whole-pipeline test in this codebase.

## Implementation Decisions

- **Package**: `packages/next` already exists as an empty scaffold
  (`package.json`, `src/index.ts`, `README.md` — created by an earlier
  scaffolding pass). This spec populates it; no new package needs creating.
- **Dependencies**: `@effect-auth/next` depends on `@effect-auth/core`
  (for `Sessions`, `Users`), `@effect-auth/api` (for `Api.Principal`,
  `Api.SessionCookie`'s cookie name), `@effect-auth/server` (for
  `Authentication.PrincipalResolver` — added during implementation; see
  `.scratch/next-package/issues/01-wire-package-dependencies.md`'s own
  "Result" for the correction history, since this dependency was originally
  justified partly by a claim about `AuthHttp` that didn't hold up), and
  `@effect-auth/react` (re-exported per the existing scaffold's intent,
  since a Next.js app is still a React app and wants the same
  session/subject atoms client-side). It does **not** depend on
  `@effect-auth/qadi` — see the `getSession` shape decision below.
- **`getSession(headers, runtime)` shape**: returns a Promise resolving to
  a 3-field struct — `{ principal, user, session }` — or `undefined`. This
  is narrower than `spec/overview.md`'s aspirational 4-field `SessionView`
  (`{ principal, user, session, subject }`): including `subject` would
  require `@effect-auth/next` to depend on `@effect-auth/qadi`, which
  would invert the stratum-layering rule that already forced the
  `Subject.ts`/`SubjectApi.ts` split (core/client-stratum packages sit
  below the qadi bridge). The application resolves its own subject by
  calling `@qadi/core`'s `SubjectResolver.resolve(session.principal)`
  directly, exactly as every worked example already shows doing at the
  call site rather than inside `getSession` itself. `spec/overview.md`'s
  4-field `SessionView` remains aspirational/deferred, the same status
  BEH-EA-026's combined struct already has per `@effect-auth/api`'s
  `Subject.ts` header comment.
- **`getSession`'s implementation seam**: composes `Sessions.verify` (the
  real, already-implemented seam — hashes and constant-time-compares the
  cookie's secret, checks absolute/idle expiry, does the throttled
  idle-refresh touch, returns a session-only `SessionView` or fails
  `SessionNotFound`/`SessionExpired`) with `Users.findById` (to attach the
  user) and the verified principal. Any failure from `Sessions.verify`
  (not found, expired) or a missing cookie collapses to `undefined` —
  `getSession` never throws or rejects for the ordinary "no valid session"
  case; only a genuine, unexpected outage (a database error) propagates as
  a rejection.
- **Cookie extraction**: `getSession` takes a `Headers`-like object (what
  both `await headers()` in a Server Component and a Route Handler's
  `request.headers` already are), parses the `Cookie` header itself for
  `Api.SessionCookie`'s configured cookie name (`__Host-session`), and
  degrades to "absent" (never throws) for a malformed or missing header —
  mirroring the parse-defensively stance already established in this
  project's cookie-handling code elsewhere.
- **`hasSessionCookie(request)` shape**: pure, synchronous, presence-only.
  Checks for `Api.SessionCookie`'s cookie name in the incoming request; does
  not verify, does not touch the database, does not resolve a principal. Its
  own doc comment states plainly (per BEH-EA-188) that a forged or expired
  cookie passes this check and that it exists only to avoid rendering a page
  the real boundary (`getSession`) would reject anyway — never treat a
  passed check as proof of anything.
- **`withNextCookies` shape and scope** (revised during implementation —
  see `.scratch/next-package/issues/04-with-next-cookies.md`'s own "Result"
  section for the full correction history, including one caught by
  `/code-review`'s Spec axis): a **pure `(response: Response, jar) => void`
  bridge**, owning no router-invocation plumbing of its own. The calling
  application dispatches a request against its own already-composed HTTP
  router/handler itself (the same one `AuthHttp` builds, invoked in-process
  via a synthetic request/response — the same technique this project's own
  `SubjectApi.test.ts` already uses via `HttpRouter.toWebHandler`) and hands
  `withNextCookies` the resulting `Response`; it only parses whatever real
  `Set-Cookie` header(s) that response carries (produced by that handler's
  `HttpApiBuilder.securitySetCookie` calls — session issuance, CSRF
  rotation) and writes them into `next/headers`'s cookie jar. This is
  narrower than this bullet originally described ("wraps a call into the
  application's own already-composed HTTP router/handler," implying
  `withNextCookies` itself would perform the dispatch) — a deliberate
  simplification, not an oversight. It does **not** attempt to intercept
  cookies from an arbitrary plain domain-service call (`Users.rename`,
  etc.) — plain domain services never set cookies today, only the HTTP
  layer does, and since `withNextCookies` takes a `Response`, not an
  `Effect`, the type system already makes that misuse impossible to
  attempt. (The archive design cookbook's illustrative
  `withNextCookies(Users.use(...))` snippet is treated as loose, superseded
  shorthand for "some mutations need cookie bridging," not a literal
  contract — this project has already found and corrected one stale claim
  from those archive docs this session, regarding React reactivity.)
- **No runtime construction owned by this package**: `getSession`,
  `hasSessionCookie` (where it needs the cookie name, a static config
  reference, not a runtime), and `withNextCookies` each take an explicit
  runtime (or the app's composed router, for `withNextCookies`) as an
  argument. `@effect-auth/next` ships no `ManagedRuntime.make` call, no
  module-level singleton, and no `globalThis`-pinning helper of its own —
  matching qadi's own real Next.js example (`../qadi/examples/nextjs-
  newsroom/src/server/runtime.ts`), which writes this pattern out by hand in
  application code specifically because `effect/GlobalValue` does not exist
  in Effect v4 and the application's own composed `Layer` type cannot be
  known generically by a client package. The package's own README documents
  this pattern as a cookbook recipe (the `globalThis`-pinning, the
  SIGINT/SIGTERM disposal, why a plain module-scope `ManagedRuntime.make`
  silently produces a second runtime under Next's dev-server module
  reloading) rather than packaging it as an export.
- **`proxy.ts` terminology**: BEH-EA-188's "`proxy.ts`" is not
  project-specific naming — it is Next.js's own renamed convention (Next
  16.3 deprecated `middleware.ts` in favor of `proxy.ts`, and restated in its
  own documentation that it "should not be used as a full session management
  or authorization solution"). `hasSessionCookie`'s doc comment can cite
  this directly.
- **Decision hydration (BEH-EA-186/192) is out of scope for new code**:
  `@qadi/react`'s `dehydrateDecisions`/`hydrateDecisions`/`QadiProvider`
  (already re-exported from `@effect-auth/react`, built earlier this
  project's history) already fully solve "seed the client with the server's
  decisions before first paint" — confirmed against qadi's own real
  Next.js example app, where this wiring lives entirely in application code
  built from those exports, not in any qadi- or effect-auth-shipped
  "Next.js provider" component. `@effect-auth/next`'s own package
  documentation shows this pattern in a worked example; no new exported
  symbol is needed for it.

## Testing Decisions

- Tests exercise `getSession`, `hasSessionCookie`, and `withNextCookies`
  against `@effect-auth/test`'s `TestAuth.layer` whole-pipeline harness
  (memory ports, no real database, no real network listener) — the same
  seam `packages/test/test/TestAuth.test.ts` and
  `packages/qadi/test/SubjectApi.test.ts` already use, per BEH-EA-193.
- A good test here asserts observable behavior only: given a request with a
  valid/absent/expired/tampered cookie, what does `getSession` return
  (`undefined` vs. the resolved struct, with which principal/user/session
  fields) — never that it internally called `Sessions.verify` a particular
  way.
- Cases to cover: a valid cookie resolves the full struct; a missing cookie
  resolves `undefined`; an expired session (advanced via `TestClock`, per
  BEH-EA-194) resolves `undefined`; a cookie with a well-formed but
  nonexistent session id resolves `undefined`; `hasSessionCookie` returns
  `true`/`false` purely from cookie presence, independent of whether that
  session is actually valid (assert this by giving it an expired session's
  still-present cookie and confirming it still reports `true` — proving the
  function does not accidentally perform validation); `withNextCookies`
  captures a `Set-Cookie` from a real sign-in/sign-out/CSRF-rotation call
  through the composed router and confirms it reaches the (test-double)
  Next cookie jar; a plain domain-service call wrapped in `withNextCookies`
  produces no cookie writes at all (documenting, not just asserting, the
  "only HTTP-layer effects" scope decision above).
- Prior art: `packages/qadi/test/SubjectApi.test.ts`'s use of
  `HttpRouter.toWebHandler` for a real, in-process HTTP round trip is the
  direct precedent for how `withNextCookies`'s tests invoke the composed
  router without a real network listener.

## Out of Scope

- Building the aspirational 4-field `SessionView` (`{principal, user,
  session, subject}`) from `spec/overview.md` — deferred, same as
  BEH-EA-026's combined struct.
- Any `@effect-auth/qadi` dependency or subject resolution inside this
  package.
- A packaged `createNextRuntime`/`ManagedRuntime` helper — documented as a
  cookbook pattern instead, per the runtime-ownership decision above.
- Extending or modifying `@effect-auth/react`'s `Providers` component —
  unaffected by this package; BEH-EA-192's decision-hydration story is
  already fully solved by existing `@qadi/react` exports.
- A generic mechanism for capturing `Set-Cookie` from arbitrary
  domain-service calls that don't go through the HTTP layer — out of scope
  because no such calls produce cookies today; revisit only if a real,
  concrete need for one arises.
- Any change to `proxy.ts`'s own security posture — it remains, by design,
  an optimistic redirect only (BEH-EA-188), never hardened into a real
  boundary.

## Further Notes

- The three seam decisions above (getSession's 3-field shape,
  `withNextCookies`'s HTTP-layer-only scope, and no packaged runtime helper)
  were confirmed directly with the user during spec synthesis, each with an
  explicit recommendation the user accepted; none was silently assumed.
- `../qadi/examples/nextjs-newsroom` (a real, working Next.js example app in
  the sibling `qadi` repository, same author) is unusually strong prior art
  for this whole package — it independently solved (and extensively
  documented, in-line, with dated findings) the exact `globalThis`-pinning
  pitfall, the `proxy.ts`-is-not-a-boundary lesson (citing CVE-2025-29927
  directly), and the per-request re-authorization rule this spec's user
  stories 6 and 11 restate. Worth reading directly during implementation,
  not just this spec.
- `spec/appendices/03-nextjs-ssr-decision-hydration.md` is the existing
  worked-example appendix combining both source cookbooks
  (`archive/design/usage-examples-v4.md` §13, `archive/design/usage-
  qadi.md` §13); it predates this spec's three seam decisions and should be
  read as superseded by them where they conflict (its own `Providers`
  sketch, and its literal `withNextCookies(Users.use(...))` line, in
  particular).
