# Internationalization (i18n)

The i18n integration is a plugin whose entire contract is: **translate the
`code` of an already-produced error response, after the fact, using a
locale resolved from the request** — it does not translate arbitrary
application strings, and it does not intercept anything but responses that
are already error responses. It is a `hooks.after` contribution matched
against every request, discharging exactly one arrow contract (methodology
doc `02` §2):

```
translation-hook :  { returned: ResponseValue }  ->  { continue }  |  { replace(response) }
```

---

## 1. What this plugin does and does not translate

**Requires:** the response the request pipeline is about to return must
already be a typed error response carrying a machine-readable `code`
string in its body. Any other response shape (a success payload, a raw
`Response`, an error without a recognizable `code`) does not meet the
domain contract of this hook and is passed through untouched.

**Ensures:** if, and only if, the resolved locale's translation dictionary
has an entry for that exact `code`, a **new** error response is raised in
place of the original one, with the same HTTP status and the same `code`,
but with `message` replaced by the translated string and the untranslated
original message preserved under a separate field so nothing observable
about the error's *identity* (its `code`) is lost in translation — only its
human-readable text changes.

**Invariant:** the `code` on the outgoing response is always identical to
the `code` on the incoming one. Translation is purely a presentation-layer
substitution of `message`; it can never change *which* error condition was
reported, only how it reads.

**On violation:** none — this hook has no precondition a caller can
violate in the Design-by-Contract sense, because it inspects rather than
requires. A response that fails to match its domain contract (not an
error, or an error without a `code`) is simply a no-op for this hook, not
a fault.

---

## 2. Locale resolution: a strategy chain with a mandatory fallback

**Requires:** a deployer-configured, non-empty set of locales, each mapped
to a translation dictionary, and a non-empty, ordered list of detection
strategies to try (defaulting to reading the request's own language
preference header if none is configured).

**Ensures:** exactly one locale is chosen per request, by trying each
configured detection strategy **in the deployer's declared order** and
taking the first one that (a) actually yields a candidate and (b) whose
candidate is a member of the configured locale set:

```
   for each strategy in configured order:
      "header"   -> parse the request's language-preference header,
                     honor its quality-value ordering, take the first
                     candidate that is a configured locale
      "cookie"   -> read a configured cookie name, accept its value only
                     if it names a configured locale
      "session"  -> read a configured field off the authenticated user
                     (only meaningful when a session exists), accept only
                     if it names a configured locale
      "callback" -> invoke a deployer-supplied resolver function, accept
                     only if it names a configured locale
      | first configured-locale match found -> USE IT, stop
      | none of the strategies yields a configured-locale match
              -> fall back to the configured default locale
```

**Invariant:** locale resolution **always** terminates in a valid,
configured locale — there is no code path that leaves the locale
undetermined. This is what makes the translation lookup in §1 total rather
than partial from the caller's point of view: a resolution failure never
surfaces as an error, it degrades to the default locale.

### 2.1 The default-locale precondition is self-correcting only up to a point

**Requires:** the deployer names a default locale that is itself present
among the configured translation dictionaries.

**Ensures:** if the deployer's declared default is present among the
configured locales, it is honored exactly. If it is absent (or omitted)
but at least one locale dictionary is configured, the default silently
becomes the language-neutral default locale **regardless of whether that
locale is itself among the configured dictionaries**.

**On violation:** if the language-neutral default is chosen this way but
was never actually configured as one of the translation dictionaries,
every lookup against it in §1 simply finds no entry, and the pipeline
falls through to leaving the original, untranslated message intact. This
is not a crash — the postcondition of §1 ("translation happens if an
entry exists") degrades gracefully to "translation does not happen," which
is a **weaker but still contract-conformant** outcome. Blamed party for a
deployer surprised that no locale is ever translated in this
configuration: **CLIENT** (the fallback default was never actually
supplied a dictionary — a configuration precondition the plugin cannot
enforce at startup because a missing dictionary is not itself an error, it
just yields fewer translated codes).

**On violation (hard failure):** the plugin's own construction-time
precondition — **at least one** locale dictionary must be supplied at
all — is enforced eagerly: an empty dictionary set is refused before the
plugin is ever installed into the pipeline. Blamed party: **CLIENT**.

## 3. The message-key contract: what a translation entry actually guarantees

**Ensures:** a translation dictionary entry is keyed by the exact `code`
string an error carries, and its value is a plain, complete replacement
for the human-readable message — never a template requiring further
interpolation by the framework, never partial text. Supplying an entry for
a `code` the deployer's plugin set does not currently produce is not an
error (dictionaries may be forward-compatible with codes from plugins not
yet installed) — the contract's only requirement is that entries used are
looked up by exact string identity against the `code` on the response
actually being returned.

**Invariant:** translation is looked up **once per response**, against
whatever `code` is on it at hook time — a hook earlier in the pipeline
(from another plugin) that has already changed the response's `code`
supersedes what an earlier layer originally produced; this hook always
translates the code as it stands at the point this hook runs, not the
code the error was originally constructed with.

---

## 4. Higher-order contribution: how plugins make their own codes translatable

This is the one genuinely higher-order aspect of the i18n contract
(methodology doc `02`): **the i18n plugin does not know, at its own
construction time, the full universe of error codes that can ever need
translation** — that universe is the union of every currently installed
plugin's own declared error-code set, plus the base system's own codes.

```
   plugin A  ──declares──▶  its own error-code vocabulary (a flat set
                             of CODE -> default English message pairs)
   plugin B  ──declares──▶  its own error-code vocabulary
   base system ──declares─▶ its own error-code vocabulary
                                      │
                    the i18n plugin's translation-dictionary
                    SHAPE is exactly the union of all of these —
                    a deployer's dictionary for a given locale
                    MAY supply an override for any code from any
                    currently or eventually installed plugin,
                    plus arbitrary additional string keys, but is
                    not REQUIRED to cover the full set (§1 handles
                    "no entry" as a graceful no-op)
```

**Requires:** a plugin that wants its own error codes to be translatable
contributes them the same way every plugin contributes its own error-code
vocabulary to the base system — there is no separate "i18n registration"
step a plugin must additionally perform. The i18n plugin free-rides on
whatever error-code vocabulary is already installed.

**Ensures:** a deployer authoring a translation dictionary sees, at the
type level, autocomplete/type-checking against the exact union of every
currently installed plugin's error codes — the dictionary's *shape*
statically reflects the *current* plugin configuration, while still
accepting arbitrary additional string keys for forward/backward
compatibility with codes from plugins that might be added or removed
later.

**Invariant (per methodology doc `01` §5):** this is a pure widening
contribution — installing an additional plugin can only ever **grow** the
set of codes a translation dictionary may usefully cover; it can never
narrow what an existing dictionary already validly translates. Removing a
plugin does not invalidate an existing dictionary either — its now-unused
entries simply stop being looked up (§3's "not an error" clause).

**On violation:** none applicable — this contribution is additive-only by
construction; there is no way for two plugins' error-code contributions to
conflict at the i18n boundary itself (a genuine code collision between two
plugins is a plugin-system-level concern, addressed in
`03-plugin-system/`, not an i18n concern).
