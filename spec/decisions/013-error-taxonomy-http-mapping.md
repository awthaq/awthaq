## Context

PRD §6 (Design principle 6) requires "typed failures with reasons," and §18 requires "uniform enumeration-safe errors" as part of the security model. `behaviors/04-contract-stratum.md`'s BEH-EA-027 and `behaviors/11-http-error-mapping.md`'s BEH-EA-086 and BEH-EA-088 already assume a specific shape for how this works — every contract error is a `Schema.TaggedError` carrying its own `httpApiStatus`, the HTTP layer reads that annotation with no separate mapping table, and enumeration-sensitive endpoints answer identically regardless of internal cause — but no decision record states *why* errors are modeled this way rather than some other way, or what "enumeration-safe" requires structurally rather than just "requires it."

`research/01-effect-ecosystem.md` Q17 ("Error architecture: one hierarchy vs per-domain errors; HttpApi mapping; user-facing vs internal detail") is the direct source: its recommendation is "**Per-domain tagged errors sharing one marker base** (`AuthError` with `readonly code` and an `expose: "user" | "internal"` policy field), NOT one monolithic hierarchy: per-domain unions keep each plugin's `addError` list closed and reviewable, while the base marker lets middleware/loggers catch `AuthError` uniformly. Map to HTTP centrally: each error Schema carries its status via `HttpApiSchema.setStatus` at declaration (one source of truth, no per-endpoint tables), user-facing `message` lives on the error, internal detail lives in `cause` and is stripped by the HttpApi error encoder." The same Q17 assigns enumeration-sensitive uniformity to a companion question, Q90 ("Enumeration resistance: uniform responses, timing normalization on password miss"), whose answer is realized concretely by `research/07-passwords-2fa.md` Q57 for token-based flows ("the request handler must not branch on user existence for output or timing... one code path, uniform latency") and by `research/08-authorization.md`'s error-typing discussion, which states the authorization-side analogue directly: "`Forbidden` and `ResourceNotFound` are **distinct typed errors in the same `AuthzError` union**... the *HTTP mapping is a route-level concern*: default `ResourceNotFound → 404`, `Forbidden → 403`, with a per-route `notFoundOnDeny: true` escape hatch for cross-tenant resources (enumeration safety...)," citing RFC 9110 §15.5.4–15.5.5 as "the canonical 403-hides-as-404 semantics for enumeration safety." This is the same pattern `behaviors/19-qadi-bridge-path-a.md`'s BEH-EA-147 states for the qadi bridge specifically (cross-tenant denial becomes 404, not 403).

On the narrower question of whether effect-auth's own research corpus documents enumeration attacks against authentication error shapes specifically (as opposed to authorization or token flows): `research/03-auth-landscape.md` was checked directly and contains no enumeration-specific material — the enumeration-safety grounding this ADR relies on comes from `research/01-effect-ecosystem.md` Q17/Q90, `research/07-passwords-2fa.md` Q57, `research/08-authorization.md`'s error-typing section and RFC 9110 citation, and `research/17-capability-security.md`'s Q90 entry, which separately cites Sánchez-Rola et al. (2017, USENIX Security) for the general lesson that "installed-but-supposedly-invisible software leaks its existence" through side channels including error messages and timing — the same principle applied here to accounts and resources rather than installed plugins.

## Decision

Every internal error effect-auth or a plugin can produce is modeled as a `Schema.TaggedError` subclass, declared where the operation that can fail is declared, and grouped into **per-domain tagged-error unions** (one union per plugin or core domain — password errors, session errors, OAuth errors, and so on) that share one common marker shape rather than being members of a single monolithic `AuthError` hierarchy. Each error's HTTP status is fixed once, at the error's own declaration, via its `httpApiStatus` annotation (BEH-EA-027); the HTTP-serving stratum reads that annotation directly (BEH-EA-088) and maintains no second, out-of-band tag-to-status table anywhere in the system. An error carries a stable, user-facing `message`/`code` on the schema itself; any internal diagnostic detail (a database error's cause, an internal reason enum such as `no-role | not-owner | not-member | policy | engine-error`) is attached only to the error's `cause` or to structured log/span data, and is stripped by the HTTP error encoder before a response is serialized — the client only ever decodes the declared `Schema.TaggedError` shape (BEH-EA-088's contract-error boundary).

Enumeration-safety is a structural property of specific errors, not a matter of handler discipline: `InvalidCredentials` (BEH-EA-027, BEH-EA-114) is the single error and status returned whether an email is unknown, a password is wrong, or the account has no password credential at all; a token-consuming endpoint (`requestReset`, magic-link consumption) answers identically for a nonexistent and an already-consumed-or-expired target (BEH-EA-064, BEH-EA-117); and a resource a caller cannot access maps to that resource's own not-found error rather than to a distinguishable `Forbidden`, following the same 403-hides-as-404 rule RFC 9110 §15.5.4–15.5.5 states generally and BEH-EA-147 states for the qadi bridge specifically. This rule applies to every endpoint the composed `auth.api` exposes, including ones a third-party plugin contributes (BEH-EA-086) — a plugin author inherits the same discipline the core error taxonomy already enforces for its own errors, rather than being left to invent enumeration-safety for their own account- or token-existence-sensitive endpoints from scratch.

## Alternatives considered

**One monolithic `AuthError` hierarchy with a centrally maintained tag-to-status mapping table**, the alternative `research/01-effect-ecosystem.md` Q17 poses directly opposite its actual recommendation ("per-domain tagged errors sharing one marker base... **NOT** one monolithic hierarchy"). A single hierarchy with a `switch (error._tag) { case "InvalidCredentials": return 401; ... }`-style central mapping is a familiar pattern from frameworks with a global exception filter (the shape Q17 is implicitly contrasting against) — but it was rejected for effect-auth because it reintroduces exactly the second, separately-maintained source of truth BEH-EA-088 and `archive/PRD.md` §5 (Design principle 5, "one source of truth per concept") rule out project-wide: a plugin's error and its status would live in two different files that can drift out of sync, and a plugin author extending the hierarchy would be modifying a shared, closed union owned by core rather than declaring their own error where their own operation is declared.

## Consequences

**Positive**: An error's status is unforgeable and undiscoverable-from-two-places — reading the error's own declaration is reading its complete HTTP behavior, with no second file to check or keep in sync. Per-domain unions keep each plugin's `addError` list closed and independently reviewable (a reviewer of the `Password` plugin's errors never needs to read the `OAuth` plugin's), while the shared marker shape still lets cross-cutting middleware (logging, tracing, a generic error-response formatter) catch every effect-auth error uniformly. Enumeration-sensitive endpoints are safe by construction rather than by convention: an author cannot accidentally give `InvalidCredentials` two different statuses for two different internal causes, because the schema only has one.

**Negative**: The uniform-error discipline actively works against a debugging affordance a less careful design would offer for free — a developer staring at a `401` in a network tab genuinely cannot tell, from the response alone, whether they mistyped an email or a password, and must fall back to server-side logs (which do carry the internal `cause`/reason) to debug their own test failures during development. This is not a hypothetical inconvenience: `research/01-effect-ecosystem.md` Q17's own design puts the diagnosable detail deliberately out of band (`cause`, stripped by the encoder), so the same mechanism that defeats an attacker's enumeration probe also defeats a legitimate developer's `curl` session. Plugin authors must additionally get every enumeration-sensitive error boundary right in the same way core did — an easy rule to state but one that requires positively identifying which of a new plugin's endpoints are account- or resource-existence-sensitive in the first place, a judgment call BEH-EA-086 delegates to the author rather than one the type system can fully check.

**Trade-off accepted**: The project accepts that debugging an authentication or authorization failure during development is deliberately harder than it would be with a hierarchy that exposed distinguishable reasons on the wire, in exchange for an error surface that is enumeration-safe by construction rather than by the discipline of every handler author across every plugin, official or third-party, remembering not to leak the distinction.
