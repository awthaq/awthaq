## Context

`@awthaq/core`'s `Verification` service has a real, tested `layerMemory` but no `layerSql`, unlike `Users`/`Accounts`/`Sessions` (each already has both). `Verification.ts`'s own header comment names the reason: BEH-EA-063's `reserve` — "first caller to claim this identifier wins," independent of `consume` — needs an exclusive-claim primitive the current `verification_tokens` repository doesn't expose, and that decision changes `issue`'s own behavior too, so it deserved its own pass rather than being folded into the persistence stratum's original build-out.

Four concrete facts, confirmed against the codebase as it stood when this decision was taken (core migrations, the Postgres and libSQL drivers and a real `Verification.layerSql` have all shipped since), motivate the decision below:

1. **`issue`'s semantics already differ between backends.** `layerMemory`'s `issue` overwrites (`HashMap.set` keyed by `identifier` — at most one live token per identifier, ever). `@awthaq/sql`'s `VerificationRepository.findByIdentifier` already does `ORDER BY createdAt DESC LIMIT 1` against a table with no `UNIQUE` constraint on `identifier` at all — it was built anticipating multiple historical rows per identifier, latest wins, with nothing yet deciding whether that's the intended `layerSql` behavior or an artifact of not having addressed this yet.
2. **`reserve` is not a token.** `layerMemory` models it as a wholly separate `Ref<HashMap<identifier, expiresAt>>`, disjoint from the token rows — BEH-EA-063 itself frames it as a distinct operation ("used to serialize an operation rather than to gate a token a caller presents"), not a variant of issuing or consuming a token.
3. **BEH-EA-058's transaction requirement ("consume and the caller's state change commit in one SQL transaction") has no expression in `VerificationShape` today** — nothing about `consume`'s signature lets a caller join a transaction it opened.
4. **No core table has a real, non-test-only migration yet.** Every plugin in this repository (`Password`, `OAuth`, `Roles`) declares `migrations: []`; `Users`/`Accounts`/`Sessions`/the current `VerificationToken` table are all exercised in `packages/sql/test/Repositories.test.ts` against an inline `CREATE TABLE` in the test file itself, not a real migration. `spec/traceability.md` already lists `packages/sql/test/MigrationOwnership.test.ts` as a separate, unbuilt, planned effort — no `AuthCore` plugin exists yet to own core-table migrations at all (`Auth.ts`'s own header comment).

Only `@effect/sql-sqlite-node` is an actual dependency in this repository today; no Postgres or MySQL driver is installed or tested, despite ADR-EA-004/ADR-EA-014 committing the project generally to dialect-neutral SQL persistence.

## Decision

**`reserve` is backed by a dedicated `verification_reservations` table**, not the `verification_tokens` table — `(identifier)` a plain (non-partial) `UNIQUE` column, `expiresAt` its only other real column. Reusing `verification_tokens` was rejected: a reservation is not a token a caller ever presents back (fact 2 above), and folding it into the same table would make a future `UNIQUE(identifier)` constraint on that table ambiguous between "one live token" and "one live token or reservation."

**The claim itself is one atomic statement**: `INSERT INTO verification_reservations (identifier, expiresAt) VALUES (...) ON CONFLICT(identifier) DO UPDATE SET expiresAt = excluded.expiresAt WHERE verification_reservations.expiresAt < :now`, with the caller determining success from whether the write actually took effect (e.g. a `RETURNING` clause, or comparing the returned `expiresAt` to the value just inserted) — encoding BEH-EA-063's "true only while unexpired" rule directly in the `WHERE` clause rather than as a separate application-level check racing against the same row. **This targets SQLite only.** Designing the same primitive against PostgreSQL or MySQL now — dialects with no real driver dependency in this repository yet, and no test to hold either honest — was rejected as speculative infrastructure of exactly the kind this project avoids building ahead of a real caller (the same reasoning `@awthaq/ports`' deferred `WebAuthn` port and `RateLimiter.layerStoreRedisConfig` already apply). A second backend is a swap-in `Layer` later, the same shape `RateLimiter`'s own store abstraction already uses (BEH-EA-109). *(Superseded, Revision 1.2: a real caller now exists — `@effect/sql-pg` shipped as a second, real driver dependency, and `VerificationReservationsRepositoryLive` runs against it in `packages/sql/test/Repositories.postgres.test.ts`, the same repository contract-test bodies as SQLite. The rejection above was correctly scoped to "no real driver, no test to hold it honest" at the time, not to Postgres specifically — see the Alternatives-considered entry below and ADR-EA-004's own status for the broader picture.)*

**`issue` matches memory's one-live-token-per-identifier behavior via one atomic upsert, not a separate delete-then-insert.** A partial unique index, `UNIQUE(identifier) WHERE consumedAt IS NULL`, is added to `verification_tokens` — at most one *unconsumed* row per identifier, enforced by the database itself. `issue` is then `INSERT INTO verification_tokens (...) VALUES (...) ON CONFLICT(identifier) WHERE consumedAt IS NULL DO UPDATE SET id = excluded.id, valueHash = excluded.valueHash, expiresAt = excluded.expiresAt, createdAt = excluded.createdAt, payload = excluded.payload, consumedAt = NULL RETURNING *` (`VerificationRepository.upsertLive`) — one statement, so the database engine's own conflict resolution decides "fresh row" vs. "replace the current live row," not two racing statements. (An earlier draft of this decision specified a separate `deleteLiveByIdentifier` then `insert`, matching `Sessions.layerSql`'s unwrapped `issue`-with-`supersedes` precedent; a code review of the implementation found that two concurrent `issue`s for the same `identifier` could each delete-then-insert and leave *two* live rows behind, diverging from `layerMemory`'s truly atomic `Ref`/`HashMap` overwrite — the single-upsert design above closes that race instead of accepting it, since unlike `reserve`'s claim (which genuinely needs "unexpired," not expressible in a partial index's `WHERE`), `issue`'s own invariant only needs "unconsumed," which a partial index CAN express directly.) Only the *unconsumed* row is ever replaced — already-consumed historical rows are untouched either way; nothing requires destroying them, and `consume`'s response is uniform regardless of a token's history (BEH-EA-064-style indistinguishability), so nothing observable changes either way.

**BEH-EA-058's transaction requirement needs no change to `VerificationShape` at all.** `SqlClient.withTransaction(effect)` (confirmed in `effect`'s own `SqlClient` module) threads the transaction connection transparently through an ambient service — any `sql` call made by anything running inside that wrapped effect, including calls made deep inside `Verification.consume`'s own `layerSql` implementation, automatically joins the same transaction. The calling plugin (`@awthaq/password`'s `confirmReset`, for instance) is responsible for wrapping `verification.consume(...)` together with its own state change (rotating the password) in one `sql.withTransaction(...)` block — exactly the pattern already available to, and expected of, any other multi-step SQL operation in this codebase. `Verification`'s own interface carries no new parameter and no new capability for this.

**Out of scope**: dialect-neutrality beyond SQLite for `reserve`'s claim primitive (a documented future backend, not designed now); and where real, non-test-only migrations for any core table (including the new `verification_reservations` table) eventually live — that is `packages/sql/test/MigrationOwnership.test.ts`'s already-planned problem, not this decision's to solve, and folding it in here would smuggle a materially bigger, already-identified gap into a decision scoped to `Verification`'s own claiming primitive.

## Alternatives considered

**Reusing `verification_tokens` for reservations, via a filtered/partial `UNIQUE` index scoped to unconsumed, unexpired rows.** Rejected: a partial index's `WHERE` clause can reference a row's own columns (`consumedAt IS NULL`) but not the current wall-clock time, so it cannot express "unexpired" at all — an expired-but-unconsumed row would still collide with the constraint, incorrectly blocking a fresh claim BEH-EA-061 says should already be treated as invalid. Fixing that requires the same delete-or-conditional-upsert application logic this decision already uses for the dedicated table, at which point reusing the token table buys nothing and costs the constraint-ambiguity problem above.

**Wiping every historical row for `identifier` on a fresh `issue`, to fully match memory's total absence of history.** Rejected: memory having no history doesn't obligate SQL to discard data nothing asked it to discard, especially given BEH-EA-058's own comment already frames "marks consumed" as a durable column write, not a row deletion — consumed rows are meant to persist.

**Wrapping a separate delete-then-insert `issue` in an explicit `sql.withTransaction`, instead of one atomic upsert.** This was this decision's original position (Revision 1.0), matching what `Sessions.layerSql`'s `supersedes` handling did at the time (unwrapped; since made transactional, RRS-004). Superseded in Revision 1.1: a code review of the implementation found the two-statement form let two concurrent `issue`s for the same `identifier` race and both leave a live row behind — a transaction wrapper would have closed that race too, but a single `INSERT ... ON CONFLICT ... DO UPDATE` closes it with no transaction at all, and is the smaller, more precisely-targeted fix (the partial unique index it relies on documents the "unconsumed" invariant directly in the schema, rather than leaving it to a wrapping transaction's caller-side discipline). `Sessions.layerSql`'s own `supersedes` handling was untouched by that revision; RRS-004/ESR-002 later closed it with a `sql.withTransaction` around tombstone-plus-insert and a `supersededAt IS NULL` guard on the tombstone, so two concurrent supersedes of one session cannot fork its family.

**Designing the claim primitive for PostgreSQL and MySQL now, alongside SQLite.** Rejected: no driver dependency for either exists in this repository, so there would be no test holding a Postgres- or MySQL-specific SQL shape honest — the same reasoning that keeps `@awthaq/ports`'s `WebAuthn` port undesigned until `@awthaq/passkey` has a real caller for it. *(Superseded for PostgreSQL, Revision 1.2: `@effect/sql-pg` shipped as a real dependency and the claim primitive was proven against it via the shared repository contract-test suite — shipping-gaps map, tickets 03/15. MySQL remains undesigned; no driver dependency or test exists for it, so the rejection above still holds there.)*

## Consequences

**Positive**: `Verification.layerSql` has a concrete, race-safe `reserve` primitive, and an `issue` behavior that matches `layerMemory`'s one-live-token invariant even under concurrent calls for the same identifier, not just under sequential ones. The transaction-boundary question (BEH-EA-058) is confirmed closed with zero interface change, removing what looked like an open design question but was actually already solved by `effect`'s own `SqlClient.withTransaction`.

**Negative**: A third `reserve` backend (MySQL, Redis) is real, undesigned future work the moment this project needs one — a Postgres backend shipped in Revision 1.2 (see above), but this decision otherwise still buys a working two-backend implementation, not a portable one. Consumed `verification_tokens` rows accumulate with no sweep/cleanup designed here (the same already-accepted gap this codebase carries for expired rows generally — BEH-EA-061 requires them to be treated as invalid before physical removal, not requires removal on any particular schedule).

**Trade-off accepted**: This decision explicitly does not solve where real (non-test-only) migrations for `verification_tokens`, its new partial unique index, or the new `verification_reservations` table live — `packages/core/test/Verification.test.ts` and `packages/sql/test/Repositories.test.ts` follow the exact same inline-`CREATE TABLE`-in-test pattern already used for every other core table, accepting the same limitation every other `layerSql` in this codebase already carries rather than resolving it unilaterally for this one service.

Implemented: `packages/core/src/Verification.ts`'s `layerSql`, `packages/sql/src/Repositories.ts`'s `VerificationRepository.upsertLive`/`tryConsume` and `VerificationReservationsRepository.claim`, `packages/sql/src/Models.ts`'s `VerificationToken.payload` and `VerificationReservation`. Real (non-test-only) migrations remain `packages/sql/test/MigrationOwnership.test.ts`'s already-planned, separate problem — see `spec/roadmap.md` for milestone.
