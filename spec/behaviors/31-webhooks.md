> `@awthaq/webhooks` composes as `Auth.make([..., Webhooks])` for the administrator's API and `Webhooks.background()` for the delivery machinery. It is a consumer of the event relay ([BEH-EA-100](13-events.md)): it never widens the in-process bus, and it puts no network call on any operation's path. Everything below is what a receiver (a billing service, a CRM sync, a migrated Clerk webhook handler) relies on, and the safety rules that keep an administrator-supplied URL from becoming a way into the network.

## BEH-EA-255: Deliveries are signed like Standard Webhooks and re-stamped on every attempt

```text
REQUIREMENT: Every delivery MUST be an HTTP POST of a JSON body carrying
             `webhook-id` (the event id, identical across every retry),
             `webhook-timestamp` (Unix seconds of THIS attempt) and
             `webhook-signature`: `v1,<base64 HMAC-SHA256>` of
             `<id>.<timestamp>.<body>` under the endpoint's secret, whose
             decoded bytes (`whsec_` + base64 of 32 random bytes) are the key.
             While a rotated-out secret is inside its grace window the header
             MUST carry a signature under each secret, space-separated. The
             library MUST ship `WebhookSignature.verify` for receivers: it MUST
             refuse missing headers, a malformed timestamp, a timestamp outside
             the replay window (both directions, default 5 minutes) and a
             signature that matches no accepted secret, and MUST compare every
             candidate in constant time.
```

This is the scheme Clerk's svix libraries and every Standard Webhooks library verify, so a migrating receiver keeps its verification code. Re-stamping each attempt keeps a retry inside the receiver's replay window however late it is; the stable `webhook-id` is the receiver's idempotency key, which is what makes at-least-once delivery ([BEH-EA-259](31-webhooks.md#beh-ea-259-deliveries-are-queued-idempotently-from-the-relay-and-sent-at-least-once-with-retry-backoff-and-dead-letter)) safe.

## BEH-EA-256: Each endpoint has its own secret, shown once, stored sealed, and rotatable with an overlap

```text
REQUIREMENT: The secret MUST be generated by the library when an endpoint is
             created, returned in that response and in a rotation response and
             never again, and stored only as an `Encryption` envelope
             (the `@awthaq/ports` port) whose additional authenticated data names the
             endpoint and the field, so a sealed secret copied into another
             endpoint's row, or swapped with the previous secret, does not
             decrypt. A delivery whose secret does not decrypt MUST fail as
             `secret` and MUST NOT be sent. Rotation MUST make a new secret
             current, keep the previous one signing for `secretGrace` (default
             24 hours), and never retain more than the current and the previous.
```

The plaintext exists in memory for one signing call and once on the wire to the administrator, so a database read (a backup, a replica, a stolen dump) discloses nothing a receiver would accept. A second rotation drops the first secret: an overlap window is for switching receivers over, not a second, longer-lived credential.

## BEH-EA-257: A payload carries identifiers only, and an external consumer inherits that posture

```text
REQUIREMENT: The delivered document MUST be `{ version, type, id, timestamp,
             correlationId?, traceId?, data, client? }`, `data` being the
             event's own fields. It MUST NOT carry free text about a person
             (the fields declared in `PII_FIELDS`, BEH-EA-100), MUST NOT carry
             the client address or user agent unless `includeClientContext` is
             set (default off), and MUST drop any field whose name reads as a
             credential or contact detail (`email`, `phone`, `password`,
             `token`, `secret`, `hash`, `authorization`, `cookie`) whatever an
             event schema declares.
```

An event is already identifiers, never contact details ([ADR-EA-029](../decisions/029-event-pii-posture.md)); this rule keeps that true when the reader is a third party and a future event is added carelessly. The delivery log stores the same body only so a delivery can be retried; it is never returned by the API and is removed with the endpoint and, per [BEH-EA-262](31-webhooks.md#beh-ea-262-the-delivery-log-takes-part-in-erasure-and-export-and-is-pruned), with the user it names.

## BEH-EA-258: An endpoint subscribes to named events and hears only what happens after it exists

```text
REQUIREMENT: An endpoint MUST list the event tags it wants: exact tags
             (`auth.user.signedIn`), families (`auth.organization.*`) or `*`;
             the list MUST be non-empty, and every pattern MUST match at
             least one tag the library can publish (a typo is refused at
             registration, not silently delivered nowhere). An event MUST be
             queued only for endpoints that are enabled, whose filter matches
             it, and which were registered no later than the event occurred:
             an endpoint MUST NOT receive the audit log's history.
```

Events published while an endpoint is switched off are not queued for it; switching it back on resumes from then. A deployment that needs a replay uses `AuditLog.replay` from the event id it cares about.

## BEH-EA-259: Deliveries are queued idempotently from the relay and sent at-least-once with retry, backoff and dead-letter

```text
REQUIREMENT: The plugin MUST receive events as the `EventTransport` of a relay
             named `webhooks` (BEH-EA-100 addendum) and MUST only enqueue: one
             delivery row per (endpoint, event), unique on that pair, so a batch
             the relay hands over again adds nothing; the relay's cursor
             therefore advances when the batch is durably queued and a slow or
             dead receiver never holds back the others. A worker MUST claim
             due rows with a lease (a second worker finds nothing; a worker that
             dies leaves the lease to lapse and the row is sent again), send
             each, and on a non-2xx answer, timeout or transport failure
             reschedule it after `retryBase * retryFactor^(attempts-1)` capped
             at `retryMax`; after `maxAttempts` the row MUST become `dead`, be
             kept as the log, and never be sent again unless an administrator
             retries it. `disableAfterConsecutiveDead` consecutive dead-letters
             MUST switch the endpoint off; a success MUST reset the count.
```

Delivery is at-least-once: a crash between the POST and the row update sends again with the same `webhook-id`. The outcome recorded is a status code or an error class (`status`, `timeout`, `connect`, `blocked`, `secret`, `endpointGone`), never a response body or an exception message, and is counted on `awthaq_webhook_deliveries_total{outcome}`.

## BEH-EA-260: An endpoint URL is an SSRF surface, checked when registered and again on every attempt

```text
REQUIREMENT: An endpoint URL MUST be an absolute `https:` URL without
             credentials whose host is neither `localhost`, a `.local`,
             `.internal`, `.localdomain` or `home.arpa` name, a single-label
             name, nor an IP literal that is not a globally routable unicast
             address (private, loopback, link-local including the cloud metadata
             address, carrier-grade NAT, documentation, multicast and reserved
             ranges; IPv4-mapped and NAT64 IPv6 judged by their embedded IPv4).
             A host name MUST also resolve, and EVERY address it resolves to
             MUST be public. Both checks MUST run at registration and before
             every attempt. A delivery MUST NOT follow a redirect (a 3xx is a
             failed attempt) and MUST NOT read or store the response body.
             `allowPrivateTargets` (development and test only) lifts the
             scheme and host rules, never the credentials rule.
```

The checks are `OutboundUrl.problem` and `HostResolver.refusal` in `@awthaq/ports`. They narrow DNS rebinding (a name that flips between the check and the connect) but cannot close it, because the HTTP client resolves the name again; egress filtering at the network layer stays the deployer's control. Redirects are refused because a redirect is the classic way from a checked URL to an unchecked one.

## BEH-EA-261: Administration is fail-closed, on the admin tier, and rate limited

```text
REQUIREMENT: The `webhooks.admin` group MUST be admin-tier (BEH-EA-071),
             behind `Api.AdminAuthentication` and CSRF, and every operation
             MUST be gated by `WebhooksConfig.canManageWebhooks({ admin,
             action })`, which denies by default. A denial MUST answer 403,
             publish `auth.admin.actionDenied` (`webhooks.<action>`) and reveal
             nothing about which ids exist; an unknown id is 404 only to a
             caller who passed the gate. Past the gate each administrator MUST
             be limited to `adminRate` calls per window (`429`). Registration
             MUST refuse an invalid URL or filter with the typed
             `InvalidWebhookEndpoint` (422) naming the rule, and stop at
             `maxEndpoints`.
```

The API is create, list, get, update (URL, description, filter, enabled), delete, rotate-secret, list an endpoint's deliveries (newest first, by status) and retry a dead delivery. The delivery log carries outcomes only: no payload, no response.

## BEH-EA-262: The delivery log takes part in erasure and export, and is pruned

```text
REQUIREMENT: The plugin MUST contribute to account erasure (BEH-EA-095): the
             delivery rows about an erased user MUST be deleted inside the
             erasure transaction. It MUST contribute to the data-subject export
             (BEH-EA-254) the outcomes of the deliveries about the subject, never a
             body. Finished (`succeeded` and `dead`) rows MUST be pruned after
             `deliveryRetention` (default 30 days); pending rows never are. Each
             endpoint's own outbound budget (`deliveryRate`, default 300 per
             minute) MUST make a delivery wait, not fail: a postponement is not an
             attempt.
```

The `auth.user.deleted` event itself is queued after the erasure commits and names the erased id: that is the consumer's cue to erase its own copy ([ADR-EA-030](../decisions/030-event-delivery-outbox-relay.md) Decision 6).
