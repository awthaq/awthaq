# Plugin platforms under the microscope — Scientific Literature

Domain: empirical software-engineering and security research on **real plugin platforms and their ecosystems** (Eclipse, OSGi, Firefox/Thunderbird, Chrome, VS Code, JetBrains, WordPress, npm-as-plugin-ecosystem). Companion to `research/09-plugin-architecture.md`, which covers practitioner prior art; this file cites the peer-reviewed evidence about what actually happened to those ecosystems. Verified against primary sources as of 2026-09. One correction to the assignment brief: the suggested "O'Connell / Extending the Eclipse platform" citation could not be verified in any index and is omitted; the McAffer-era canon is covered by the verified IBM Systems Journal paper below (McAffer is a co-author).

## TL;DR

- **Compatibility is an empirical property, not a declared one.** In Eclipse, plugins using only official APIs survived forward source-compatibility at 96.7% vs 50.2% for plugins touching internal "non-APIs" (Businge et al., ICSM 2012). awthaq's `apiVersion` check (Q20) must be paired with measured, compile-based compatibility (Q21–Q22, Q31).
- **Documented-but-discouraged internal surfaces leak.** 44.2% of Eclipse third-party plugins used at least one non-API despite explicit discouragement (Businge et al., SQJ 2013). Unstable seams must be structurally invisible to plugin authors, not merely marked unstable (Q23).
- **Old interfaces stabilize; young interfaces are the risk.** Old Eclipse non-APIs showed high survival, and 79.8% of classes containing long-stable internal methods were bug-free (SCAM 2012; Kawuma & Nabaasa 2022). Freeze a small surface early and promote new surface slowly (Q20, Q23).
- **Breaking changes are negotiated community policy.** Eclipse's "API Prime Directive" (never break clients) vs npm's "bump the major" vs CRAN's gatekeeping (Bogart et al., FSE 2016). Declared majors are unreliable even where policy exists: Eclipse plugins frequently shipped documented breaking changes without bumping majors. awthaq cannot trust plugin-declared versions alone.
- **Forced platform majors are existential for ecosystems.** Firefox's XUL→WebExtensions cut killed most legacy add-ons (Nov 2017); Chrome's Manifest V3 saw <5% adoption before its deadline slipped and developer studies document functionality loss and workarounds. Plan dual-generation windows, codemods, and honest communication (Q100).
- **~80% of API-breaking changes are refactoring-shaped** (Dig & Johnson 2006) — codemods are the highest-leverage deprecation tool.
- **Open marketplaces are an operational trust problem, not a declarative one.** 60% of Chrome Web Store extensions were never updated; half of known-vulnerable extensions remained live 2 years after disclosure; 21 VS Code extensions had verified code-injection exploits reaching >6M installs; JetBrains removed 15 API-key-stealing plugins in 2026. Registry trust (Q7) needs curation, scanning, and update review.
- **Dependency depth = fragility.** npm's dense graph made one maintainer compromise ecosystem-scale (Zimmermann et al., NDSS 2019); packaging-ecosystem studies show a small core of packages dominates updates and reverse dependencies (Decan et al., EMSE 2019). Keep the plugin dependency graph shallow and compiler-verified (Q21–Q22).
- **Extensions and services are complementary patterns** — Eclipse's own architects kept both: "extensions address the extensibility of a component, services address interoperability" (Gruber et al., IBM Systems Journal 2005). Direct support for awthaq's dual model of declarative contributions vs `Context.Tag` services.
- **Abandonment is the default fate of a plugin.** >65% of Eclipse third-party plugins released no version in the year after first release (ICSM 2012); 60% of Chrome Web Store extensions were never updated. Design the host for a majority-stale plugin population.

## Annotated bibliography

### Eclipse: platform architecture and the extension-point model

- **O. Gruber, B. J. Hargrave, J. McAffer, P. Rapicault, T. Watson (2005). The Eclipse 3.0 platform: Adopting OSGi technology.** *IBM Systems Journal 44(2), pp. 289–299.* [PDF (bitsavers mirror)](https://mirrors.meulie.net/bitsavers.org/pdf/ibm/IBM_Systems_Journal/442/gruber.pdf) — First-party account of rebuilding Eclipse's runtime on OSGi while preserving compatibility: version model where major = breaking / minor = compatible, a backward-compatibility *bundle* that let unmodified Eclipse 2.1 plugins run, lazy activation, and the key distinction between the extension framework (extensibility) and the service framework (interoperability). The template for awthaq's "compile once, contribute declaratively" registry plus Effect-service capabilities.
- **Kim Moir (2011). Eclipse.** *The Architecture of Open Source Applications, Vol. 1.* [aosabook.org](https://aosabook.org/en/v1/eclipse.html) (non-academic) — Anatomy of the extension-point model: plugin manifests, `requires` dependencies, extension points with XML *schemas* that the platform validates, a cached plugin registry, lazy activation ("everything is a plugin"). Direct precedent for compiler-validated contributions and `auth plugin list`.
- **Erich Gamma, Kent Beck (2003). Contributing to Eclipse: Principles, Patterns, and Plug-Ins.** *Addison-Wesley.* [O'Reilly catalog](https://www.oreilly.com/library/view/contributing-to-eclipse/0321205758/) (non-academic) — The platform-design philosophy from Eclipse's creators: extension points as the platform's primary API contract, and the discipline of designing for extenders. Background canon for contribution-point design (Q20, Q23).
- **Eric Clayberg, Dan Rubel (2004). Eclipse: Building Commercial-Quality Plug-Ins.** *Addison-Wesley.* [ACM review/citation](https://dl.acm.org/doi/10.1145/1142958.1142976) (non-academic) — The practitioner standard for what commercial plugin development against a host actually requires; evidence that plugin quality lives or dies with host API stability and tooling (PDE).

### Eclipse: empirical studies of the third-party plugin ecosystem

- **John Businge, Alexander Serebrenik, Mark van den Brand (2010). An Empirical Study of the Evolution of Eclipse Third-party Plug-ins.** *EVOL/IWPSE 2010 (Joint ERCIM Workshop on Software Evolution and Int'l Workshop on Principles of Software Evolution).* [ACM DL (via citing article)](https://dl.acm.org/doi/abs/10.1007/s11219-013-9221-3) — Foundational dataset of Eclipse third-party plugins (ETPs) and their dependency evolution; confirms Lehman-style continuing change in a plugin ecosystem.
- **John Businge, Alexander Serebrenik, Mark van den Brand (2012). Survival of Eclipse Third-party Plug-ins.** *IEEE ICSM 2012.* [PDF](https://aserebre.win.tue.nl/ICSM12.pdf) — 467 ETPs / 1,447 versions: plugins on official APIs had a **96.7%** forward source-compatibility success rate vs **50.2%** for plugins using non-APIs; **>65%** of plugins released no version in the year after first release (abandonment is the default); recent plugins survive on *old* non-APIs, not new ones. The core quantitative case for a frozen, small plugin contract (Q20, Q23).
- **John Businge, Alexander Serebrenik, Mark van den Brand (2012). Compatibility Prediction of Eclipse Third-Party Plug-ins in New Eclipse Releases.** *IEEE SCAM 2012.* [PDF](https://aserebre.win.tue.nl/SCAM12.pdf) — Compiled 288 ETPs against 11 Eclipse SDK releases (1.0–3.7): use of *old* non-APIs predicted compatibility success; newly introduced unstable interfaces were the breakage vector. Method = actually compiling plugins across host generations — exactly what `@awthaq/test` and an ecosystem compat matrix should do (Q21, Q31).
- **John Businge, Alexander Serebrenik, Mark van den Brand (2013). Eclipse API usage: the good and the bad.** *Software Quality Journal 21.* [ACM DL](https://dl.acm.org/doi/abs/10.1007/s11219-013-9221-3) — **44.2%** of 512 ETPs had at least one version depending on at least one Eclipse non-API, despite documentation and tooling discouraging it. Documentation-only enforcement of public/private boundaries fails; make unstable seams unreachable (Q23).
- **Simon Kawuma, Evarist Nabaasa (2022). An Empirical Study of Bugs in Eclipse Stable Internal Interfaces.** *arXiv:2203.09134.* [arXiv](https://arxiv.org/abs/2203.09134) — Found **327K** non-API methods that stayed stable across Eclipse evolution; **79.8%** of classes containing long-stable internal methods were bug-free. Supports a promotion pipeline: surfaces graduate from unstable to stable only after demonstrated stability (Q23).

### API evolution and ecosystem governance (cross-platform, Eclipse-centric)

- **Danny Dig, Ralph Johnson (2006). How do APIs evolve? A story of refactoring.** *Journal of Software Maintenance and Evolution 18(2), pp. 83–107.* [Wiley](https://onlinelibrary.wiley.com/doi/abs/10.1002/smr.328) — Over **80%** of API-breaking changes in four frameworks (incl. Eclipse JDT) are structural, behavior-preserving refactorings. Implication: most host-generated breakage is mechanically migratable — ship codemods per plugin-API generation (Q100).
- **Christopher Bogart, Christian Kästner, James Herbsleb, Ferdian Thung (2016). How to break an API: cost negotiation and community values in three software ecosystems.** *FSE 2016.* [ACM DL](https://dl.acm.org/doi/10.1145/2950290.2950325) — Interview study across Eclipse, CRAN, npm: breaking-change handling is community *policy + values* ("API Prime Directive" in Eclipse; snapshot consistency in CRAN; major-bump in npm). Crucially, Eclipse's own semantic-versioning policy broke down in practice: documented breaking changes shipped without major bumps to avoid rippling downstream work. `apiVersion` policy is a governance decision with ecosystem-wide labor consequences (Q20, Q100).
- **Christopher Bogart, Christian Kästner, James Herbsleb, Ferdian Thung (2021). Policies and Practices in 18 Open Source Software Ecosystems.** *ACM TOSEM 30(3).* [ACM DL](https://dl.acm.org/doi/fullHtml/10.1145/3447245) — Large-scale comparison of versioning/deprecation policies across 18 ecosystems (Eclipse included): semver mandates, deprecation-with-default-implementations, and the gap between written policy and practice. evidence base for choosing awthaq's written-vs-enforced compat policy (Q20).

### OSGi: specification canon and academic analyses

- **OSGi Alliance. OSGi Core Release 8 Specification.** [docs.osgi.org](https://docs.osgi.org/specification/) (non-academic) — The normative module/lifecycle/service model: bundles, import/export matching by version ranges, dynamic service registry. The service-registry + manifest-metadata pattern that Eclipse's registry and Nuxt's compat checks echo.
- **Richard S. Hall, Karl Pauls, Stuart McCulloch, David Savage (2011). OSGi in Action.** *Manning.* [manning.com](https://www.manning.com/books/osgi-in-action) (non-academic) — Canonical practitioner treatment ("the backbone of the Eclipse plugin system"): bundle lifecycles, version-range semantics, migrating legacy systems onto OSGi.
- **Clement Escoffier, Richard S. Hall, Philippe Lalanda (2007). iPOJO: an Extensible Service-Oriented Component Framework.** *IEEE International Conference on Services Computing (SCC 2007).* [IEEE Xplore](https://ieeexplore.ieee.org/iel5/4278609/4278610/04278693.pdf) — Service component model on OSGi with extensible "handlers" injecting non-functional behavior (lifecycle, config, events) — an academic precedent for host-managed, declaratively-extended component behavior (compare awthaq hooks/middleware compiled in).
- **Lina Ochoa, Thomas Degueule, Jurgen Vinju (2018). An Empirical Evaluation of OSGi Dependencies Best Practices in the Eclipse IDE.** *MSR 2018, pp. 170–180.* [ACM DL](https://dl.acm.org/doi/10.1145/3196398.3196416), [CWI PDF](https://homepages.cwi.nl/~jurgenv/papers/MSR-2018.pdf) — First empirical validation of industry OSGi dependency best practices against real Eclipse bundles; shows the Eclipse ecosystem itself only partially follows its own modularity rules. Justification for compiler-*enforced* (not documented) structure: `requiresPlugins`/`requiresCapabilities` validated at compile, best practices as errors not style advice (Q21–Q22).

### Firefox / Thunderbird: extension ecosystem and the forced XUL→WebExtensions migration

- **Adrienne Porter Felt (2009). A Survey of Firefox Extension API Use.** *UC Berkeley EECS Technical Report UCB/EECS-2009-139.* [Berkeley](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2009/EECS-2009-139.html) — Reviews 25 "recommended" Firefox extensions to scope which host interfaces legacy extensions actually need — an early, concrete method for sizing API parity before a platform migration (Q100: measure what the ecosystem uses before you deprecate it).
- **J. Wang, X. Li, X. Liu, et al. (2012). An Empirical Study of Dangerous Behaviors in Firefox Extensions.** *Information Security Conference (ISC 2012), LNCS, pp. 188–203.* [Springer](https://doi.org/10.1007/978-3-642-33383-5_12) — Dynamic analysis of extension behaviors affecting web sessions; quantifies how much ambient authority the classic XUL extension model granted. Part of the evidence chain that motivated WebExtensions' least-privilege redesign.
- **Ahmet Salih Buyukkayhan, Kaan Onarlioglu, William K. Robertson, Engin Kirda (2016). CrossFire: An Analysis of Firefox Extension-Reuse Vulnerabilities.** *NDSS 2016.* [PDF](https://seclab.nu/static/publications/ndss2016crossfire.pdf) — Shows absence of isolation between traditional Firefox extensions enables extension-reuse attacks. Architectural isolation between plugins is a security requirement, not a nicety (ties to Effect Layer isolation and fail-isolated hooks, PRD §18).
- **Le An, Marco Castelluccio, Foutse Khomh (2019). An Empirical Study of DLL Injection Bugs in the Firefox Ecosystem.** *Empirical Software Engineering 24.* [Springer](https://dl.acm.org/doi/10.1007/s10664-018-9677-7), [PDF](https://marco-c.github.io/publications/dll_injection-emse2019.pdf) — Ecosystem-health study of third-party-software-induced crashes; notes the post-migration consensus that the WebExtensions API "is more restrictive than the old APIs, but also more secure and stable" — the migration's security payoff, bought at ecosystem cost.
- **Mozilla Add-ons Blog (2017). WebExtensions in Firefox 57.** [blog.mozilla.org](https://blog.mozilla.org/addons/2017/09/28/webextensions-in-firefox-57/) (non-academic) — The deadline canon: Firefox 57 (Nov 2017) would run *only* WebExtensions; every legacy add-on dies unless ported. The canonical forced-major event, announced Aug 2015, API "stable" April 2016 ([critical retrospective](https://rwec.co.uk/blog/2017/11/how-mozilla-completely-dropped-the-ball-with-quantum-and-webextensions/), non-academic).
- **Mozilla Add-ons Blog (2017). Migrating to WebExtensions: port your stored data.** [blog.mozilla.org](https://blog.mozilla.org/addons/2017/01/20/migrating-to-webextensions-port-your-stored-data/) (non-academic) — Migration tooling focused even on *data* migration, not just code — a deprecation UX detail awthaq should copy for plugin migrations (Q100).
- **Thunderbird Project (2017). New Thunderbird Releases and New Thunderbird Staff.** [blog.thunderbird.net](https://blog.thunderbird.net/2017/12/new-thunderbird-releases-and-new-thunderbird-staff/) (non-academic) — Documents the same forced migration hitting a *downstream* embedder's plugin ecosystem; hosts that inherit a platform's extension API inherit its migration burden too.

### Chrome: extension security, permissions, supply chain, and Manifest V2→V3

- **Adam Barth, Adrienne Porter Felt, Prateek Saxena, Aaron Boodman (2010). Protecting Browsers from Extension Vulnerabilities.** *NDSS 2010.* [PDF](https://www.ndss-symposium.org/wp-content/uploads/2017/09/barth.pdf), [Google Research page](https://research.google/pubs/protecting-browsers-from-extension-vulnerabilities/) — The foundational least-privilege extension architecture: declare authority in a manifest, privilege-separate, isolate processes. Found ~three-quarters of 25 audited Firefox extensions used unnecessarily powerful APIs. Direct ancestor of awthaq's capability strings: authority declared statically, granted at install (Q23, Q30).
- **Nicholas Carlini, Adrienne Porter Felt, David Wagner (2012). An Evaluation of the Google Chrome Extension Security Architecture.** *USENIX Security 2012.* [USENIX](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/carlini) — Manual review of 100 Chrome extensions found **70 vulnerabilities across 40 extensions**; banning HTTP-loaded and inline scripts would prevent 47 of the 50 most severe. Declared architecture ≠ secure ecosystem; someone must audit the actual plugins (Q7).
- **Alexandros Kapravelos, Chris Grier, Neha Chachra, Christopher Kruegel, Giovanni Vigna, Vern Paxson (2014). Hulk: Eliciting Malicious Behavior in Browser Extensions.** *USENIX Security 2014.* [USENIX](https://www.usenix.org/conference/usenixsecurity14/technical-sessions/presentation/kapravelos) — Dynamic analysis at scale found malicious extensions, including one with **5.5M users**. Malware prevalence in open marketplaces is a standing condition, not an edge case (Q7).
- **Oleksii Starov, Nick Nikiforakis (2017). XHOUND: Quantifying the Fingerprintability of Browser Extensions.** *IEEE S&P 2017.* [DOI](https://doi.org/10.1109/SP.2017.18) — Quantifies how much browser fingerprinting surface extensions add; the measurement template for "what does installing a plugin expose?" — a question awthaq should answer with `auth doctor` rather than leave to attackers (Q7, Q23).
- **Ignacio Sanchez-Rola, Igor Santos, Davide Balzarotti (2017). Extension Breakdown: Security Analysis of Browsers Extension Resources Control Policies.** *USENIX Security 2017.* [USENIX](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/sanchez-rola) — Shows control over extension-accessible resources is inconsistently enforced across the ecosystem: resource-exposure policy is a real attack surface, not boilerplate (Q23 capability exposure rules).
- **Andreas Sjösten, Steven Van Acker, Andrei Sabelfeld (2017). Discovering Browser Extensions via Web Accessible Resources.** *CODASPY 2017, pp. 329–336.* [ACM DL](https://doi.org/10.1145/3029806.3029820) — Over **28%** of 43,429 Chrome extensions discoverable from outside; surfaces you expose to strangers are fingerprintable authority. Mirrors awthaq's rule that every exposed capability is part of the attack surface.
- **Andreas Sjösten, Steven Van Acker, Pablo Picazo-Sanchez, Andrei Sabelfeld (2019). Latex Gloves: Protecting Browser Extensions from Probing and Revelation Attacks.** *NDSS 2019.* [DOI](https://doi.org/10.14722/ndss.2019.23309) — Follow-up defenses against extension discovery: protection required a second platform generation after the problem was measured — expect the same iteration cycle for awthaq's capability-exposure rules (Q23, Q100).
- **Nikolaos Pantelaios, Nikitas Nikiforakis, Alexandros Kapravelos (2020). You've Changed: Detecting Malicious Browser Extensions through their Update Deltas.** *ACM CCS 2020.* [ACM DL](https://doi.org/10.1145/3372297.3423343) — Detects malicious turns by diffing updates rather than vetting initial uploads: **trust is a property of the whole lifecycle, not the first submission.** Registry design (Q7) must review *updates*, not just onboarding.
- **Aurore Fass, Dolière Francis Somé, Michael Backes, Ben Stock (2021). DoubleX: Statically Detecting Vulnerable Data Flows in Browser Extensions at Scale.** *ACM CCS 2021.* [ACM DL](https://doi.org/10.1145/3460120.3484745) — Static taint analysis across tens of thousands of extensions proves ecosystem-scale automated review of plugin code is feasible — the technical basis for registry-level contract/scanning gates (Q7, Q31).
- **Pablo Picazo-Sanchez, Beatriz Ortiz-Martin, Pablo Schneider, Andrei Sabelfeld (2022). Are Chrome extensions compliant with the spirit of least privilege?** *International Journal of Information Security 21(6).* [Springer](https://doi.org/10.1007/s10207-022-00610-w) — Even under a manifest-permission model, real ecosystems over-request; declared permission strings under-constrain actual behavior. awthaq's compiler should validate *usage* against declared capabilities, not just the declaration (Q21, Q23).
- **Valerio Bucci, Wanpeng Li (2023). From Manifest V2 to V3: A Study on the Discoverability of Chrome Extensions.** *Information Security (Springer), pp. 183–202.* [DOI](https://doi.org/10.1007/978-3-031-49187-0_10), [Aberdeen PDF](https://aura.abdn.ac.uk/bitstreams/5bce64e9-38fc-4ae3-a426-40c4c36bf80e/download) — Crawl of **108,416** extensions: 30.78% had adopted MV3 (Mar 2023); MV3's added constraints cut WAR-based detectability only 4–10%. Hardened platform majors deliver *measured, bounded* improvements — set expectations accordingly (Q100).
- **Matt Frisbie (2023). Understanding the Implications of Manifest V3.** *In: Building Browser Extensions (Apress), pp. 167–185.* [DOI](https://doi.org/10.1007/978-1-4842-8725-5) (non-academic) — The practitioner-side accounting of what MV3 removed and why it was controversial (service workers, blocking webRequest) — the developer-facing mirror of the academic MV3 studies below.
- **Sheryl Hsu, Manda Tran, Aurore Fass (2024). What is in the Chrome Web Store? Investigating Security-Noteworthy Browser Extensions.** *arXiv:2406.12710.* [arXiv](https://arxiv.org/abs/2406.12710) — Longitudinal CWS study: ~60% of extensions live <1 year; **60% never updated**; half of known-vulnerable extensions remained live and vulnerable **2 years after disclosure**; a third ship vulnerable library versions; security-noteworthy extensions reached ~350M users. The definitive dataset for "registries must be actively operated" (Q7).
- **Qinge Xie, Manoj Vignesh Kasi Murali, Paul Pearce, Frank Li (2024). Arcanum: Detecting and Evaluating the Privacy Risks of Browser Extensions on Web Pages and Web Content.** *USENIX Security 2024, pp. 4607–4624.* [USENIX](https://www.usenix.org/conference/usenixsecurity24/presentation/xie-qinge) — Dynamic taint tracking over *all* functional CWS extensions across seven sensitive sites: thousands of extensions with significant privacy risks, hundreds automatically extracting user content, impacting millions of users. Plugins leak by default unless the platform makes exfiltration visible (Q7, PRD §93 redaction).
- **Bihui Jin, Heng Li, Ying Zou (2024). Impact of Extensions on Browser Performance: An Empirical Study on Google Chrome.** *arXiv:2404.06827.* [arXiv](https://arxiv.org/abs/2404.06827) — 72 extensions across 11 categories measurably degrade load time and energy — including in scenarios where the extension is unused. Plugin installation is never free: awthaq's per-request Layer/context costs (Q19) need a published benchmark harness so plugin authors see their cost.
- **Nikolaos Pantelaios, Alexandros Kapravelos (2024). Manifest V3 Unveiled: Navigating the New Era of Browser Extensions.** *arXiv:2404.08310.* [arXiv](https://arxiv.org/abs/2404.08310) — The MV2→MV3 forced major, measured: **<5%** adoption before the deadline paused; now 9/10 *new* extensions are MV3; executing 517 confirmed-malicious extensions shows an 87.8% removal of abuse-associated APIs — yet 29.8% remained functional after conversion and 56% retained harmful capability after modest adaptation. Platform majors help but don't stop motivated adversaries (Q20, Q100).
- **Libor Polčák, Giorgio Maone, Michael McMahon, Martin Bednář (2025). Developers Insight On Manifest v3 Privacy and Security Webextensions.** *arXiv:2507.13926.* [arXiv](https://arxiv.org/abs/2507.13926) — Structured qualitative study of MV3 migration from extension developers (incl. the NoScript lead): majority report limited user benefit, removal of crucial APIs, workaround pressure; transition impacts different plugin *classes* differently; some projects decline to update. The developer-side cost ledger for any breaking plugin-API change (Q100).
- **Ben Rosenzweig, Valentino Dalla Valle, Giovanni Apruzzese, Aurore Fass (2025). It's Not Easy: Applying Supervised Machine Learning to Detect Malicious Extensions in the Chrome Web Store.** *ACM Transactions on the Web.* [ACM DL](https://doi.org/10.1145/3770852), [arXiv](https://arxiv.org/abs/2509.21590) — State of the art in automated marketplace malware detection and its limits: even strong ML detectors are "not easy" at marketplace scale. Automation assists curation; it cannot replace it (Q7).

### VS Code and JetBrains: marketplace trust in developer tools

- **Elizabeth Lin, Igibek Koishybayev, Trevor Dunlap, William Enck, Alexandros Kapravelos (2024). UntrustIDE: Exploiting Weaknesses in VS Code Extensions.** *NDSS 2024.* [NDSS](https://www.ndss-symposium.org/ndss-paper/untrustide-exploiting-weaknesses-in-vs-code-extensions/), [PDF](https://www.ndss-symposium.org/wp-content/uploads/2024-73-paper.pdf) — Systematic taint analysis of **25,402** code-bearing VS Code extensions: 21 extensions with verified code-injection exploits impacting **>6M installations**. Extensions run with developer-machine trust — the same trust awthaq plugins will run with; contract tests and sandboxing claims must be honest (Q7, Q31).
- **Shehan Edirimannage, Charitha Elvitigala, Asitha Kottahachchi Kankanamge Don, Wathsara Daluwatta, Primal Wijesekara, Ibrahim Khalil (2024). Developers Are Victims Too: A Comprehensive Analysis of the VS Code Extension Ecosystem.** *arXiv:2411.07479.* [arXiv](https://arxiv.org/abs/2411.07479) — Analysis of **52,880** extensions: ~**5.6%** exhibit suspicious behavior; hosting lacks practical security controls. Quantifies the background rate of shady plugins an open registry accepts (Q7).
- **Microsoft (current). Using Proposed API.** [code.visualstudio.com](https://code.visualstudio.com/api/advanced-topics/using-proposed-api) (non-academic) — VS Code's two-tier API stability model: stable API vs proposed API restricted to Insiders and gated per-extension. A working middle ground between "everything public is forever" (Eclipse's pain) and "everything is internal" (Firefox's non-API leakage); a candidate pattern for awthaq experimental seams (Q23).
- **JetBrains (2026). Addressing Malicious Third-Party AI Plugins.** [blog.jetbrains.com](https://blog.jetbrains.com/platform/2026/06/marketplace-ecosystem-security-update-malicious-ai-plugins/) (non-academic) — JetBrains removed 15 marketplace plugins built to steal AI-provider API keys (June 2026): the newest large-scale incident, in the ecosystem closest to awthaq's audience. Also relevant: [Marketplace approval guidelines](https://www.jetbrains.com/legal/docs/plugins_site/approval-guidelines/1.0/) (non-academic) — automated feature extraction + human review as the curation pipeline. Note: *no dedicated academic empirical study of the IntelliJ/JetBrains or Atlassian plugin ecosystems was found* — a genuine literature gap.

### WordPress: platform/plugin co-evolution and vulnerabilities

- **Otávio Mesa, Reginaldo Vieira, Marx L. Viana, Vitor H. S. Durelli, Elder Cirilo, Marcos Kalinowski, et al. (2018). Understanding Vulnerabilities in Plugin-based Web Systems: An Exploratory Study of WordPress.** *SPLC 2018 (22nd Int'l Systems and Software Product Line Conference), pp. 149–159.* [ACM DL](https://doi.org/10.1145/3233027.3233042) — Characterizes vulnerability types caused by plugins, their impact, and patch sizes: in a product-line lens, third-party plugins are the dominant defect surface of the composed system. Mirrors awthaq's threat model (PRD §88): the framework is judged by its weakest plugin.
- **Jiahuei Lin, Mohammed Sayagh, Ahmed E. Hassan (2023). The Co-evolution of the WordPress Platform and Its Plugins.** *ACM TOSEM 32(1), Article 19.* [ACM DL](https://doi.org/10.1145/3533700) — Large-scale longitudinal study of how WordPress core releases force adaptation across the plugin ecosystem and where incompatibilities accumulate — the best available empirical model of host-major → plugin-update waves for a schema-bearing plugin platform (Q26, Q100).
- **Jukka Ruohonen (2019). A Demand-Side Viewpoint to Software Vulnerabilities in WordPress Plugins.** *arXiv:1812.05293 (later in Information & Security: An International Journal).* [arXiv](https://arxiv.org/abs/1812.05293) — Known plugin vulnerabilities concentrate in plugins with the largest installation bases: popular surface attracts attackers. Prioritize auditing and hardening of awthaq's most-installed official plugins (Q7, Q92).
- **Patchstack (2025). State of WordPress Security.** [patchstack.com](https://patchstack.com/whitepaper/state-of-wordpress-security-in-2025/) (non-academic) — Industry telemetry: core/plugin/theme vulnerabilities implicated in nearly half of WordPress malware infections, with the overwhelming share of new vulnerabilities reported in plugins (not core). Anecdotal-grade but widely cited; treat numbers as industry estimates.

### npm and package registries treated as plugin ecosystems

- **Alexandre Decan, Tom Mens, Philippe Grosjean (2019). An Empirical Comparison of Dependency Network Evolution in Seven Software Packaging Ecosystems.** *Empirical Software Engineering 24(1), pp. 381–416.* [arXiv:1710.04936](https://arxiv.org/abs/1710.04936) — Cross-ecosystem (npm, Cargo, CRAN, Packagist, RubyGems, NuGet, CPAN) analysis: networks grow while a minority of packages drive most updates and hold most reverse dependencies; fragility rises with transitive dependency counts. For awthaq: keep plugin dependency graphs shallow; a small trusted core will dominate the ecosystem (Q21).
- **Alexandre Decan, Tom Mens (2022). On the impact of security vulnerabilities in the npm and RubyGems dependency networks.** *Empirical Software Engineering 27.* [UMons repository](https://orbi.umons.ac.be/handle/20.500.12907/39344) — Vulnerabilities and their fixes propagate differently across two registries; fixes lag disclosures, and dependency networks amplify exposure. Model for awthaq's official-plugin security-update policy (Q7, Q92).
- **Markus Zimmermann, Cristian-Alexandru Staicu, Cam Tenny, Michael Pradel (2019). Small World with High Risks: A Study of Security Threats in the npm Ecosystem.** *USENIX Security 2019, pp. 995–1010.* [USENIX](https://www.usenix.org/conference/usenixsecurity19/presentation/zimmerman), [PDF](https://www.usenix.org/system/files/sec19-zimmermann.pdf) — Shows npm's densely-connected graph converts one compromised maintainer account (the event-stream incident) into ecosystem-scale impact; quantifies vulnerable-version propagation and unmaintained-package risk. The formal argument for awthaq's shallow, compiler-verified `requiresPlugins` graph and official-plugin hygiene (Q21–Q22).
- **Marc Ohm, Henrik Plate, Arnold Sykosch, Michael Meier (2020). Backstabber's Knife Collection: A Review of Open Source Software Supply Chain Attacks.** *DIMVA 2020, Springer LNCS.* [Springer book](https://link.springer.com/book/10.1007/978-3-030-52683-2) — Taxonomy of real OSS supply-chain attacks across ecosystems; the vocabulary (typosquatting, account takeover, build compromise) for threat-modeling awthaq's plugin distribution (PRD §92, Q7).
- **Shradha Neupane, Grant Holmes, Elizabeth Wyss, Drew Davidson, Lorenzo De Carli (2023). Beyond Typosquatting: An In-depth Look at Package Confusion.** *USENIX Security 2023, pp. 3439–3456.* [USENIX](https://www.usenix.org/conference/usenixsecurity23/presentation/neupane) — 13 confusion mechanisms mined from 1,200+ documented attacks; survey-validated detectors (77% of flags judged genuinely confusing, ~1 warning per 100M+ package pairs). Directly reusable for awthaq's plugin registry: reserved prefixes (Q23) + confusion-aware name checks at publish time (Q7).

## Cross-cutting themes for awthaq

- **Q20 `apiVersion` policy — declared versions are not enough.** Bogart (FSE 2016) shows even Eclipse shipped documented breaking changes without bumping majors; Businge (ICSM 2012) shows compatibility outcomes vary 96.7% vs 50.2% by *what the plugin actually imports*. Keep integer `apiVersion` (exact match at v1) as the cheap structural gate, but pair it with a registry that *measures* compatibility by compiling plugins against supported generations (SCAM 2012 methodology → `@awthaq/test`, Q31).
- **Q21–Q22 compiler-enforced dependencies and diagnostics.** Ochoa et al. (MSR 2018) show ecosystems violate even well-documented modularity best practices; Zimmermann et al. (NDSS 2019) show dependency depth converts small failures into ecosystem events; Decan et al. (EMSE 2019) show fragility grows with transitive dependencies. Enforce `requiresPlugins`/`requiresCapabilities` in the compiler with cycle detection — best practices as compile errors, not docs.
- **Q23 extension-point stability — make unstable seams structurally invisible.** Eclipse's non-APIs were documented, discouraged, and still used by 44.2% of third-party plugins (SQJ 2013), halving survival (ICSM 2012). Old surfaces stabilize (SCAM 2012; Kawuma 2022) — so freeze a small v1 surface, and gate promotion into the stable surface on demonstrated stability + bug-freedom. VS Code's stable-vs-proposed-API tiering is the operating precedent for experimental seams. Also from Gruber et al. (ISJ 2005): extension points carry *schemas* the platform validates — declarative contributions validated by the compiler, services (Effect `Context.Tag`s) for interop.
- **Q7 registry trust model — trust is operational.** The measured base rates are grim: 60% of CWS extensions never updated (Hsu et al. 2024), half of known-vulnerable extensions persist ≥2 years post-disclosure, 5.6% of VS Code extensions suspicious (Edirimannage 2024), 21 vulnerable extensions >6M installs (UntrustIDE), 15 malicious JetBrains plugins (2026). Curation + automated scanning (DoubleX-style static analysis, Rosenzweig 2025 ML limits) + *update-delta review* (Pantelaios 2020) + confusion-aware name checks (Neupane 2023) is the evidence-based stack for `@awthaq/registry`.
- **Q100 compatibility, deprecation UX, and forced majors.** The two natural experiments: Firefox's XUL→WebExtensions (hard cut; ecosystem loss documented across Mozilla/Thunderbird canon and rwec retrospective) and Chrome's MV2→MV3 (deadline slipped after <5% adoption; developer study documents lost functionality and workarounds; Bucci & Li measure bounded security gains). Combine: (1) two-generation dual support, (2) codemods per major — justified because >80% of breaking changes are refactorings (Dig & Johnson 2006), (3) machine-readable deprecation metadata surfaced by `auth doctor` (Eclipse's published per-release deprecation logs are the operating precedent, with a policy of ~2 years' notice before API removal — [Eclipse removals policy](https://eclipse.dev/eclipse/development/porting/4.4/removals.html), non-academic), (4) budget for *data* migration of plugin state, not just code (Mozilla's migration guides).
- **Q26 migrations & co-evolution.** Lin, Sayagh & Hassan (TOSEM 2023) show host majors drive recurring, ecosystem-wide plugin adaptation for a schema-bearing platform like WordPress; Mesa et al. (SPLC 2018) show plugins dominate the composed system's defect surface. awthaq's deterministic, hash-stamped migration aggregation with destructive-op guardrails is the compiler-side answer; expect official-plugin migrations to be the ecosystem's clock.
- **Q30 static install vs runtime configuration.** Barth et al. (NDSS 2010) and the Chrome model (install-time authority, runtime grants bounded by the static manifest) remain the best-evidenced seam; the extension-security literature confirms over-requesting persists even under static declaration (Picazo-Sanchez 2022) — hence compiler validation of config against the frozen graph.
- **Isolation as a security invariant.** CrossFire (NDSS 2016) shows plugin-to-plugin interference is exploitable when absent; awthaq's Layer isolation, fail-isolated after-hooks, and namespaced capabilities are the architectural counterpart.

## Open questions

1. **Measured vs declared compatibility (Q20/Q21):** should the awthaq registry run compile-based compatibility tests per Plugin-API generation (SCAM 2012 methodology) and publish a *measured* compat matrix, treating plugin-declared `apiVersion` as advisory? Who funds the CI?
2. **Structural invisibility of unstable seams (Q23):** can awthaq make internal seams *unreachable* from plugin code (non-exported tags, compiler-private types) rather than documented-but-discouraged? Eclipse data says documentation fails at a rate of 44.2%.
3. **Deprecation cadence (Q100):** two-generation dual support with machine-readable deprecation metadata is the evidence-backed default — but should awthaq ever do a *hard cut* like Firefox 57 (simpler host, mass ecosystem loss), or a deadline-with-slips model like Chrome MV3 (slower cleanup, angrier developers)? Does `auth doctor` carry per-plugin migration ETA?
4. **Registry economics (Q7):** the security data favors curated registries with update review, but who performs scanning/review at v1 — maintainers, CI gates, or third-party auditors? Is "official" a security claim (implying review SLAs) or only a trademark claim?
5. **Codemod investment (Q100/Q22):** given Dig & Johnson's 80%-refactoring finding, should each Plugin API major ship a `@awthaq/codemod` from day one, and should the compiler emit machine-applicable fixes (analogous to ESLint `--fix`) instead of static messages?
