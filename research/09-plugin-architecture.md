# Plugin architecture — Research

Domain: prior-art analysis of plugin/module systems (Q20–Q31 of `research/00-questions.md`). Facts verified against primary sources as of 2026-09. One correction to the assignment brief: *Type-Level TypeScript* is by **Gabriel Vergnaud** (author of TS-Pattern), not Gabriele Petronella — verified at [type-level-typescript.com](https://type-level-typescript.com/) (the site credits `@GabrielVergnaud` and TS-Pattern throughout).

## TL;DR

- **The best plugin contracts are small, declarative, and frozen objects**: better-auth requires only `id` ([plugins docs](https://better-auth.com/docs/concepts/plugins)); VS Code extensions contribute via static JSON `contributes` blocks that are inspectable *without executing code* ([contribution points](https://code.visualstudio.com/api/references/contribution-points)). effect-auth should mirror this: `definePlugin()` → frozen readonly contribution record; the compiler executes, plugins declare.
- **Compatibility metadata works when it is checked, not when it is documented**: Nuxt modules declare `compatibility.nuxt` semver ranges and the host runs `checkNuxtCompatibility`/`assertNuxtCompatibility` with clear console errors ([Nuxt Kit docs](https://nuxt.com/docs/4.x/api/kit/modules), [compatibility](https://nuxt.com/docs/3.x/api/kit/compatibility)); Fastify's `fastify-plugin` carries a supported-Fastify semver range checked at load ([Fastify plugins](https://fastify.dev/docs/latest/Reference/Plugins/)). Gatsby is the cautionary tale: majors (v3→v5) forced plugin lockstep and the ecosystem fragmented and decayed after the 2023 Netlify acquisition ([Netlify press](https://www.netlify.com/press/netlify-acquires-gatsby-inc-to-accelerate-adoption-of-composable-web-architectures/), [Wieruch 2026](https://www.robinwieruch.de/react-gatsby-js/)).
- **Declare dependencies twice, at two layers**: plugin ids for structure/ordering (VS Code `extensionDependencies`), capability strings for implementation-agnostic authority (Chrome `permissions` model, [declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)). `Context.Tag` requirements need no new mechanism — Effect Layer composition already validates them; what it lacks is plugin-level metadata for the CLI, which the string layer supplies.
- **Cycles must be caught by the compiler, never by the type system**: tRPC hit `TS2589` ("type instantiation is excessively deep") "past a certain number of endpoints, which makes it unusable" ([trpc#2448](https://github.com/trpc/trpc/discussions/2448)). Kahn's algorithm on `requiresPlugins` + a shallow, non-generic-over-plugins input type keeps TS out of the cycle-detection business.
- **Ordering must be declarative and stable, never registration order**: Rollup's per-hook `order: 'pre'|'post'` + user order ([Rollup plugin dev](https://rollupjs.org/plugin-development/)), Vite's `enforce` tiers ([Vite plugin API](https://vite.dev/guide/api-plugin)), Babel's rules (plugins first-to-last, presets last-to-first — a *confusing* rule people must memorize, [Babel docs](https://babeljs.io/docs/plugins)). NestJS `APP_GUARD` order silently follows module registration — the anti-pattern to avoid ([Nest guards](https://docs.nestjs.com/guards)).
- **Route conflicts: throw, and canonicalize param names** — find-my-way throws when the same path segment is registered with two different param names (`/foo/:bar` then `/foo/:baz`) ([params-collisions test](https://github.com/delvedor/find-my-way/blob/main/test/params-collisions.test.js)). better-auth leaves uniqueness to a convention ("add the plugin name as a prefix"); effect-auth should enforce structurally via per-plugin prefixes.
- **Schema: own tables namespaced; shared-table columns are the dangerous convenience** — better-auth lets plugins add fields to `user` and infers types globally, and warns "Don't store sensitive information in the `user` or `session` table" ([plugins docs](https://better-auth.com/docs/concepts/plugins)); Medusa 2.0 goes the opposite way: strict module isolation, cross-module data only via explicit `defineLink` join tables ([module links](https://docs.medusajs.com/learn/fundamentals/module-links)). effect-auth: both, with compiler validation.
- **Hook failure semantics belong in the type**: Tapable encodes them in hook classes (bail/waterfall/async-series) ([tapable](https://github.com/webpack/tapable)); effect-auth should split `before*` hooks (may abort, typed `HookAbortError`) from `after*` hooks (compile-wrapped so a failing observer can never fail auth, per PRD §18).
- **Static install vs runtime config**: Chrome MV3's `permissions` (install-time) vs `optional_permissions` (runtime-granted, *bounded by the static manifest*) is the exact seam effect-auth needs ([Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)): configuration is data validated against the frozen capability graph; only installation changes the graph.
- **Type-level composition has a size cliff**: tRPC ([#2448](https://github.com/trpc/trpc/discussions/2448)) and Hono (chained-middleware inference breaks, [hono#3587](https://github.com/honojs/hono/issues/3587)) prove it. Mitigations with track records: builder/type-builder pattern ([Type-Level TypeScript](https://type-level-typescript.com/)), interface merging per plugin, `const` type parameters ([TS 5.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html)), variance annotations ([TS 4.7](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html)), tail-recursion elimination ([TS 4.5](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-5.html)), `satisfies` ([TS 4.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html)).

## Questions answered

### Q20 — Minimal plugin contract & `apiVersion` policy

**Evidence.** better-auth deliberately makes `id` the only required property of `BetterAuthPlugin`; everything else (endpoints, schema, hooks, middleware, rate-limit rules) is optional, and plugins are recommended to be factory functions accepting options ([better-auth plugins](https://better-auth.com/docs/concepts/plugins)). VS Code's manifest separates *static declarations* (`contributes`: commands, views, auth providers — validated as JSON, visible before activation) from *code* (`activate`), plus `activationEvents` for laziness ([contribution points](https://code.visualstudio.com/api/references/contribution-points), [activation events](https://code.visualstudio.com/api/references/activation-events)). Obsidian's manifest carries `id`, `name`, `version`, `minAppVersion` — app-version gating at the store level ([manifest reference](https://docs.obsidian.md/Reference/Manifest)). Fastify plugins are plain functions; metadata (name, supported Fastify semver, encapsulation opt-out) travels on the `fastify-plugin` wrapper, and the host checks the range at load ([Fastify plugins](https://fastify.dev/docs/latest/Reference/Plugins/)). Nuxt modules use `defineNuxtModule` with `meta` + `compatibility.nuxt` semver, checked via `checkNuxtCompatibility`/`assertNuxtCompatibility`, and the official registry validates each module's `nuxt` field ([Kit modules](https://nuxt.com/docs/4.x/api/kit/modules), [nuxt/modules](https://github.com/nuxt/modules)); Nuxt also demonstrates the "behavior version flag" pattern via `future.compatibilityVersion` ([upgrade guide](https://nuxt.com/docs/4.x/getting-started/upgrade)). Chrome's `manifest_version: 3` is a coarse but effective contract breaker ([declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)). Gatsby shows the failure mode: no enforced API-version gate + majors every year → plugins pinned across versions, ecosystem fragmentation, then steward abandonment ([Netlify acquisition, Feb 2023](https://www.gatsbyjs.com/blog/gatsby-is-joining-netlify/); [2026 retrospective](https://www.robinwieruch.de/react-gatsby-js/)).

**Recommendation.** Minimal contract: required = `id` (namespaced, see Q23) + `apiVersion`; optional = `layer`, `api`, `handlers`, `middleware`, `schema`, `hooks`, `events`, `requiresPlugins`, `requiresCapabilities`, `provides`, `conflicts`, `order`. `definePlugin()` validates shape and namespaces at definition time and returns a **frozen** readonly object (no runtime mutation of the plugin record, no `registerPlugin`). Contribution style: declarative (VS Code-style contribution points), not imperative callbacks — this is what makes `auth plugin list`/`doctor`/docs generation possible without executing plugin code (PRD §9.5, §37 already assume this). `apiVersion`: integer major, exact match at v1 (`apiVersion: 1` compiled against Plugin API 1); evolve to Nuxt-style semver *ranges* only when a second API generation actually exists. Publish a machine-readable compatibility matrix (nuxt/modules model) and gate the plugin registry on it. Host support policy: N generations (current + previous) supported, older rejected with an error linking the migration guide; provide codemods at each Plugin API major. Never silently shim v1 plugins on a v2 host — that is how Gatsby-style rot hides.

**Confidence:** high.

### Q21 — Dependency declaration: plugin ids vs capability strings vs `Context.Tag` requirements

**Evidence.** Plugin-id dependencies are proven and simple: VS Code `extensionDependencies` (hard, must be enabled) vs `extensionPack` (bundles) ([activation/anatomy docs](https://code.visualstudio.com/api/get-started/extension-anatomy)); Nuxt `moduleDependencies` lets a module require another module and merge its defaults ([Nuxt i18n module integration](https://i18n.nuxtjs.org/docs/guide/install-module)). Capability-style declaration is Chrome's model: static, namespaced permission strings grant *authority*, granted at install, checkable at runtime via `chrome.permissions` ([Chrome permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions/)). DI-tag dependencies are NestJS's model: dynamic modules `import` other modules and `export` providers; circular imports require `forwardRef` — an escape hatch that exists precisely because cycles were not structurally prevented ([Nest dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules)). Angular solves "many implementations of one contract" with `multi: true` providers collected under an `InjectionToken` ([Angular DI providers](https://angular.dev/guide/di/defining-dependency-providers)). Effect's own Layer graph already validates `Context.Tag` requirements at composition time (PRD §11); PRD §9.3 sketches `requiresPlugins` + `requiresCapabilities`.

**Recommendation.** Keep **two** declaration mechanisms, because they answer different questions. (1) `requiresPlugins: ["oauth"]` — structural/ordinal dependency: this plugin needs *that* plugin's routes, migrations, or ordering position; drives topo sort (Q22, Q26), cycle detection, and `auth doctor`. (2) `requiresCapabilities: ["auth.hasher"]` — implementation-agnostic authority per POLA: the plugin needs *some* provider of a capability; enables substitution (argonalternative hasher, in-memory rate limiter in tests) and exclusive-conflict detection (Q23). This vocabulary comes from object capabilities: a capability is an unforgeable, conveyable authority and components should hold least authority ([Miller, Paradigm Regained](https://pdos.csail.mit.edu/6.828/2004/readings/miller03paradigm.pdf); [Capability Myths Demolished](https://papers.agoric.com/assets/pdf/papers/capability-myths-demolished.pdf); [ocap survey](https://arxiv.org/html/1907.07154v1)). Do **not** make `Context.Tag` a plugin-level dependency mechanism: tags are the *service-level* mechanism and Effect already validates them; inventing a parallel tag-requirement API would duplicate validation the Layer graph performs for free and would give the CLI nothing (tags don't carry versions). What we *should* add: each contribution layer declares the tags it requires as data (`layerRequires`), so the compiler can cross-check declared capabilities against actual layer needs and fail early with a plugin-attributed message instead of Effect's build-time "Service not found" [INFERENCE on exact error ergonomics; the cross-check itself is straightforward].

**Confidence:** high.

### Q22 — Cycle detection & compile-error UX

**Evidence.** TypeScript's own failure mode for cyclic inference is catastrophic UX: `TS2589: Type instantiation is excessively deep and possibly infinite`, reported by tRPC users as "makes it unusable" past a threshold number of endpoints ([trpc#2448](https://github.com/trpc/trpc/discussions/2448)); the tRPC team also notes autocomplete materializes all procedures on every access ([tRPC discord perf thread](https://discord-questions.trpc.io/m/1273877872872001637)). NestJS needed `forwardRef` because its DI graph *permits* cycles — supporting them is a design smell, not a feature ([Nest dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules)). For good error UX: avvio (Fastify's boot library) maintains a reentrant, graph-based boot tree and Fastify can print it; find-my-way ships `prettyPrint` of the route tree ([find-my-way README](https://github.com/delvedor/find-my-way)). ESLint sets the docs-link standard: every rule id maps to a documentation page. PRD §9.4 already sketches the `PluginDependencyCycle` error shape.

**Recommendation.** Detect cycles with Kahn's algorithm over `requiresPlugins` edges during compilation (phase 3–4 of PRD §12.3); reject self-dependency already inside `definePlugin()`. Error contract for every compile diagnostic: stable code (`E_PLUGIN_CYCLE`), one-line summary, the **full cycle path** (`password@1.2.0 → session@2.0.1 → password@1.2.0`), the installation site ("introduced by `organization()` at auth.ts:14"), a resolution hint ("extract the shared requirement into a capability and depend on `requiresCapabilities`"), and a docs URL per code (ESLint pattern). Keep `Auth.make`'s parameter type shallow — `ReadonlyArray<AuthPluginAny>` — so the *type system* never re-derives plugin-to-plugin structure; all graph reasoning lives in the compiler (this is the load-bearing lesson from tRPC/TS2589). Provide `auth plugin list --graph` rendering the resolved DAG (find-my-way/avvio pretty-print lesson). Also detect *capability* cycles (A requires `cap.x`, B provides `cap.x` but requires `cap.y`, …) the same way.

**Confidence:** high.

### Q23 — Capability namespace conventions, registry, exclusivity enforcement

**Evidence.** Namespacing discipline: VS Code reserves the `vscode.` prefix for core and asks extensions to namespace contributions; Chrome permissions are a curated, documented set of known strings ([declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)). Angular's `multi: true` providers aggregate append-only — safe for collections — but a plain duplicate provider *silently overrides* (last-wins) ([Angular DI in action](https://v17.angular.io/guide/dependency-injection-in-action)); NestJS global modules can similarly collide without ceremony ([Nest dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules)). Medusa 2.0 proves the strict alternative: modules cannot reach each other's services at all; cross-module interaction only through explicitly declared links ([Medusa v2 release](https://medusajs.com/blog/v2-release/), [module links](https://docs.medusajs.com/learn/fundamentals/module-links)). PRD §34–36 sketch `capabilities` / `requiresCapabilities` plus conflict detection.

**Recommendation.** Grammar: `capability := namespace "." path` where `path` is dot-separated lowercase kebab segments. Reserved namespaces: `auth.*` (core primitives: `auth.user`, `auth.session`, `auth.hasher`, …) and `effect-auth.*` (official plugins), enforced by the compiler — a third-party plugin declaring `provides: ["auth.hasher"]` fails compilation with a "reserved namespace" error; third parties derive their namespace from their npm scope (`@acme/passwordless` → `acme.passwordless.*`). Ship a `@effect-auth/registry` module: typed constants + a machine-readable JSON catalog (name, description, exclusivity, stability, docs URL) consumed by the compiler, CLI, and docs site — Chrome's curated-strings model. Exclusivity is declared per capability: `exclusive` (one provider; second provider → `CapabilityConflict` naming both plugins; this is how `auth.hasher` works) vs `multi` (aggregates: observers, strategies, middlewares — Angular `multi: true`). Every `provides`/`requires` pair validated at compile: missing provider → `MissingCapability` naming the requiring plugin and suggesting registry entries; `conflicts: [...]` pairs validated even when independent. No silent last-wins anywhere (Angular/NestJS lesson).

**Confidence:** high.

### Q24 — Route conflict policy

**Evidence.** find-my-way (Fastify's router) is the strongest precedent: registering `/foo/:bar` and then `/foo/:baz` **throws** — same position, different param name is a conflict — and duplicate static routes throw per method ([params-collisions test](https://github.com/delvedor/find-my-way/blob/main/test/params-collisions.test.js)); it also normalizes matching decisions (static > param > wildcard, longer static suffix wins) documented in its README ([find-my-way](https://github.com/delvedor/find-my-way)). Fastify scopes routes per encapsulation context and offers `prefix` per registered plugin ([Fastify plugins](https://fastify.dev/docs/latest/Reference/Plugins/)). better-auth's equivalent is a *convention* documented in its plugin guide: "Make sure your paths are unique… add the plugin name as a prefix to the path (`/my-plugin/hello-world` instead of `/hello-world`)" — i.e., unenforced ([better-auth plugins](https://better-auth.com/docs/concepts/plugins)). Hono permits stacking multiple handlers on one pattern (all run) — fine for middleware, wrong for endpoint ownership ([Hono middleware](https://hono.dev/docs/guides/middleware)). Astro integrations can `injectRoute` and collisions surface only at build ([Astro integrations](https://docs.astro.build/en/reference/integrations-reference/)).

**Recommendation.** All conflict checking happens on a normalized route key `METHOD " " path` with trailing slashes collapsed and case fixed (decide once: case-sensitive, no trailing-slash duplicates — find-my-way's options exist because frameworks that didn't decide accumulated flags). (1) Exact static collision → `RouteConflict` compile error naming both plugins and both definitions. (2) Param-name mismatch at the same tree position → also `RouteConflict` (`:id` vs `:orgId`), find-my-way precedent. (3) **Structural guarantee over convention**: every plugin's api group mounts under `/<pluginId>/` by default (compiler-injected), mirroring Fastify `prefix`; third-party contributions to core paths (`/sign-in`, `/sign-out`, …) or the bare root are rejected unless `override: true` is set. (4) When override/extension is genuinely needed (e.g., 2FA wrapping `sign-in`), make it a first-class contribution: `extendEndpoint({ target: "core:sign-in", plugin: "two-factor", middleware: [...] })` — additive, attributed, never a silent replacement; replacement itself requires `override: true` and emits an `auth doctor` warning. Multi-strategy stacking on one endpoint (Hono-style) is rejected for endpoint *ownership* but handled by named phases in middleware (Q28).

**Confidence:** high.

### Q25 — Schema conflict policy

**Evidence.** Two poles exist in production. better-auth: plugins own tables via `schema`, and may add fields to shared `user`/`session` tables — the added fields then flow into every user-returning endpoint's inferred types; the docs explicitly warn "Don't store sensitive information in the `user` or `session` table. Create a new table if you need to store sensitive information" ([better-auth plugins](https://better-auth.com/docs/concepts/plugins)). Medusa 2.0: strict isolation — "all business domains … rewritten from scratch to eliminate interdependencies between them"; modules cannot join each other's tables, and cross-module associations live in dedicated link tables created by `defineLink` ([Medusa v2 release](https://medusajs.com/blog/v2-release/), [module links](https://docs.medusajs.com/learn/fundamentals/module-links)). Strapi namespaces plugin models (`plugin::<plugin>.<model>`) and gives plugins `register()`/`bootstrap()` lifecycle slots to declare content-types ([Strapi plugin server API](https://docs.strapi.io/cms/plugins-development/server-api)). PRD §20 already defines plugin `tables` + `extensions` and the neutral IR.

**Recommendation.** Validation rules in the compiler (phase 7): (1) Plugin-owned table names MUST be `<pluginId>_<table>` (compiler auto-prefixes; a bare name is an error). Core table names (`user`, `account`, `session`, `verification`) are reserved. (2) `extensions` on shared tables are allowed for scalar attributes only, with rules: no reserved column names (`id`, `created_at`, `updated_at`, `email`…); no `NOT NULL` without a default (backfill trap); type must map cleanly through the IR (H section Q73/Q77 owns dialect mapping); two plugins declaring the same column → `SchemaConflict` naming both. (3) The better-auth sensitive-data warning becomes a compiler rule: columns on `user`/`session` are implicitly profile-exposed, so fields classified sensitive (tokens, secrets, PII beyond basics) are rejected on shared tables — must go to a side table. (4) Anything relational or larger than an attribute (passkey credentials, recovery codes, org memberships) belongs in plugin-owned tables with explicit FKs to `user.id`; the compiler validates FK targets exist **after** topo ordering (ties into Q26). Medusa's link-table pattern is the model for inter-plugin data relationships — effect-auth should not allow a plugin to ALTER another plugin's table at all (only core tables are extensible).

**Confidence:** high.

### Q26 — Migration aggregation

**Evidence.** The industry converged on diff-generated, review-before-apply migrations with drift detection (Prisma `migrate diff`/drift detection; Atlas SQL review linting destructive changes [INFERENCE on exact Atlas lint feature names]) and on ordered handwritten migrations (Rails/Alembic). better-auth generates schema/migrations from its plugin schema via CLI ([better-auth database docs](https://better-auth.com/docs/concepts/database)). Ordering by plugin dependency is not practiced by better-auth (tables are independent) but is required once plugins FK into each other and into core. Astro-style lifecycle hooks show where generation hooks naturally sit (`astro:build:done`) ([Astro integrations](https://docs.astro.build/en/reference/integrations-reference/)). PRD §21 already specifies: CLI inspects installed plugins → schema compiler → desired schema → planner → reviewable migrations; destructive requires confirmation.

**Recommendation.** (1) Aggregate the merged IR (post-conflict-validation), then diff against the migration ledger; one pending migration set per compile, deterministic: same installed plugin set → byte-identical SQL (hash-stamp it; the contract test harness in Q31 asserts determinism). (2) Statement ordering = plugin topo order (from `requiresPlugins`), tie-broken by plugin id; core tables first; FK constraints only after their targets — this is why Q21's id-level dependencies matter for migrations even when capabilities handle services. Each statement carries `-- plugin: <id>` annotations so review maps SQL to owners (reviewability, PRD §21). (3) Generated-first, handwritten-append-only: plugins may ship handwritten steps that always run after the generated section of their own migration unit; never interleaved. (4) Guardrails: destructive ops (DROP TABLE/COLUMN, type narrowing, index drops) are emitted but flagged; `auth migration apply` refuses them without `--allow-destructive`, and prints affected tables/columns + the owning plugin; cross-check before dropping anything referenced by another installed plugin's IR (compiler-level, cheap). (5) `auth migration status` reports applied/pending/drift (ledger vs live schema sniff) [drift mechanics detail belongs to H-section Q75].

**Confidence:** high on aggregation/ordering/guardrails design; medium on specific tooling vocabulary borrowed from Prisma/Atlas (not re-verified in this session).

### Q27 — Hook semantics

**Evidence.** Tapable encodes failure/value semantics in the hook *type* itself — `SyncHook`, `SyncBailHook` (first non-undefined result stops), `SyncWaterfallHook` (value threading), `AsyncSeriesHook` — and tap order is simply registration order, with `intercept` available for debugging ([webpack/tapable](https://github.com/webpack/tapable)). That gives typed semantics but fragile ordering. better-auth hooks are `before`/`after` arrays of `{ matcher, handler }` built with `createAuthMiddleware`; a before-hook returns a modified context, and hooks run for HTTP calls and direct server invocations ([better-auth hooks](https://better-auth.com/docs/concepts/hooks)). Babel's ordering rules (plugins run before presets; plugin order first-to-last; preset order **reversed**) are famously counter-intuitive — implicit ordering conventions are a long-term tax ([Babel plugins](https://babeljs.io/docs/plugins), [ordering issue](https://github.com/babel/babel/issues/4882)). Rollup solves ordering declaratively per hook with `order: 'pre'|'post'|null` + user order ([Rollup plugin dev](https://rollupjs.org/plugin-development/)). PRD §17–18: hooks control lifecycle, events observe; events must not make auth success depend on non-critical observers.

**Recommendation.** (1) **Typed contexts per hook point**: `BeforeSignIn` receives a Schema-validated input/context type, not `any`; hook registries are keyed by hook name with distinct types (no giant mutable `AuthHooks` interface — add hooks by extending the compiler's hook-point registry, versioned by Plugin API major). (2) **Failure semantics by hook class**: `before*` hooks are veto points — they may abort with a typed `HookAbortError` (user-safe message + stable code, mapped to HTTP status per §29) and may return a transformed context (bail/waterfall semantics made explicit, Tapable lesson). `after*` hooks and event observers are compile-wrapped into fail-isolated execution: an error is logged (span + error event) but cannot fail the operation (PRD §18 extended to after-hooks). (3) **Ordering**: plugin topo order, then explicit `order` number (default 0; sugar `pre`/`post` = ±100, Rollup-style), stable tie-break by plugin id then declaration index; resolved order is emitted by `auth plugin list --hooks` for debuggability. Never registration order (NestJS `APP_GUARD` anti-pattern; [Nest guards](https://docs.nestjs.com/guards)). (4) Observers must never receive mutable request state they don't declare (ties to Q28's declared-reads rule).

**Confidence:** high.

### Q28 — Middleware contributions

**Evidence.** Fastify's request lifecycle is the best-matured model: named phases (`onRequest`, `preParsing`, `preValidation`, `preHandler`, …) with encapsulated scoping, so a plugin's hooks apply only inside its subtree unless deliberately hoisted ([Fastify encapsulation](https://fastify.dev/docs/latest/Reference/Encapsulation/)). Hono middleware attach by path pattern (`app.use(path, mw)`) and the chained builder accumulates `Variables` types across middleware — with a documented failure mode when chains are broken or grow large ([Hono middleware](https://hono.dev/docs/guides/middleware); [hono#3587](https://github.com/honojs/hono/issues/3587)). NestJS binds guards globally via `APP_GUARD` multi-providers whose execution order follows module registration ([Nest guards](https://docs.nestjs.com/guards)). Express: order = registration, error handlers detected by arity — purely implicit. better-auth plugins contribute `middleware` with route matchers plus global `onRequest`/`onResponse` ([better-auth plugins](https://better-auth.com/docs/concepts/plugins)).

**Recommendation.** (1) Adopt Fastify's **named phases**: `preAuth` (rate limiting, captcha/bot defense), `auth` (core-reserved: strategy chain, `CurrentPrincipal`), `postAuth` (authorization, org scoping, feature flags). Plugins declare `phase`; core auth middleware is never interleaved or shadowed. (2) Scopes: per-endpoint (HttpApi middleware on the endpoint), per-group (api group), global (plugin middleware + optional route matcher, better-auth style). (3) Ordering within a phase = plugin topo order → explicit `order` → plugin id (same rules as hooks, one mechanism to learn). (4) **Avoid Hono's trap of type-accumulating chains**: middleware communicates by providing Effect services into context (`CurrentPrincipal`, `TenantContext`) or `FiberRef`, not by widening generics down the chain — Effect's service model is the escape hatch from the inference cliff that bit Hono ([#3587](https://github.com/honojs/hono/issues/3587)). (5) POLA rule: global middleware declares what it reads/modifies (`reads: ["headers", "body"]`); undeclared access is a compile error — middleware are capability-scoped like everything else.

**Confidence:** high.

### Q29 — Client contributions derived from HttpApi

**Evidence.** better-auth requires a *separate* client plugin per server plugin when endpoints are called from the frontend ("Most plugins require both server and client plugins to work correctly"), and the client plugin exists to provide frontend methods under a namespace (e.g., `authClient.organization.*`) ([better-auth plugins](https://better-auth.com/docs/concepts/plugins), [organization plugin](https://better-auth.com/docs/plugins/organization)) — the duplication PRD §22 calls out. tRPC proves the alternative end-to-end: the client is derived entirely from the router type, "no code generation" ([Create T3 App on tRPC](https://create.t3.gg/en/usage/trpc)), at the cost of the type-inference cliff documented above ([trpc#2448](https://github.com/trpc/trpc/discussions/2448)). Hono RPC does the same via `hc<AppType>` ([Hono RPC](https://hono.dev/docs/guides/rpc)). Effect `HttpApiClient` derives a typed client from an `HttpApi` definition natively — the framework capability better-auth had to build by hand (see D-section Q32/Q39 for current HttpApi capability verification, owned by the HTTP peer).

**Recommendation.** **One contract, zero client plugins for transport.** A plugin contributes `api` (HttpApi groups) once; `@effect-auth/client`'s `createAuthClient` consumes the *same compiled artifact* (PRD §12.2 `CompiledPlugins.api`) and exposes methods namespaced by group/plugin id (`client.password.signIn`, `client.organization.invite`). This deletes better-auth's server/client duality *because* Effect's HttpApi/HttpApiClient already carry the types — the structure better-auth approximates with `$Infer` types and paired packages. What remains as an optional `client` export on a plugin package: framework sugar only (React hooks, atoms, tanstack-query helpers), additive and keyed by plugin id — never a second definition of endpoints. The typed error union and security semantics (CSRF mode, bearer vs cookie) flow from the same compiled artifact; frontend ergonomics are the Client peer's (Q82–Q87) territory — the plugin-architecture guarantee is only that *no second source of truth exists*.

**Confidence:** high.

### Q30 — Runtime seam: static install vs runtime configuration

**Evidence.** Chrome MV3 is the canonical model: `permissions` are granted at install; `optional_permissions` are granted at runtime via `chrome.permissions.request` but **only within the statically declared set**; the manifest is the authority boundary ([declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), [chrome.permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions/)). VS Code separates declared contributions (static) from lazy activation (`activationEvents`) — the *surface* is static, the *execution* is runtime ([activation events](https://code.visualstudio.com/api/references/activation-events)). Nuxt splits modules (build-time install, code) from `runtimeConfig` (data) — the install/config split is explicit in its architecture. NestJS `forRoot()` options feel "runtime" but actually parameterize the module graph at import time ([Nest dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules)). PRD §33 + ADR-005/006 already fix the vocabulary (static install vs runtime config; `LayerMap` for keyed tenant resources — `LayerMap` caches scoped, layer-built resources per key on the effect-smol v4 line, [LayerMap.ts](https://github.com/Effect-TS/effect-smol/blob/main/packages/effect/src/LayerMap.ts)).

**Recommendation.** Hard rule: **installation is code, configuration is data.** `Auth.make({ plugins })` freezes the capability graph (endpoints, schema, migrations, hook points). Everything else is configuration validated *against* the graph at startup: enabling Google for tenant A is data consumed by the installed `oauth` plugin; enabling SMS-OTP when the `sms-otp` plugin is absent is a typed startup error (`CapabilityNotInstalled`, naming the config path and the install fix) — fail closed at boot, never lazily at first request. Runtime toggles may only select among *installed* capabilities (Chrome `optional_permissions` bounded by the manifest). Tenant-specific resources: `LayerMap` keyed by tenant id with caching and scoped lifecycle (PRD §33; [LayerMap](https://github.com/Effect-TS/effect-smol/blob/main/packages/effect/src/LayerMap.ts)) — a tenant cannot introduce new capabilities, only instantiate configured variants of installed ones. Litmus test for the seam: if a toggle would add/remove an endpoint, table, migration, or hook point, it is an install decision and belongs in `plugins: [...]`, not config. Enforce by contract test (Q31): "config alone cannot change the route table or schema IR."

**Confidence:** high.

### Q31 — Plugin contract test suite (`@effect-auth/test`)

**Evidence.** ESLint's `RuleTester` is the gold standard for *plugin contract harnesses*: authors declare `valid` and `invalid` cases with expected messages/autofix output, and the harness enforces the rule contract inside the normal test runner ([RuleTester tutorial](https://eslint.org/docs/latest/extend/custom-rule-tutorial/); typescript-eslint maintains an enhanced fork [rule-tester](https://typescript-eslint.io/packages/rule-tester/)). Fastify's `fastify.inject` lets plugin authors test full HTTP lifecycles without a listening socket, and its plugin guide pushes encapsulation-aware tests ([Fastify plugins guide](https://fastify.dev/docs/v5.0.x/Guides/Plugins-Guide/)). Nuxt ships `@nuxt/test-utils` for testing modules in real fixture setups [INFERENCE on exact module-test API names]. PRD §38 lists "plugin contract tests" and §39 test utilities as MVP-adjacent requirements.

**Recommendation.** Ship `@effect-auth/test` with two layers. (1) `runPluginContractTests({ plugin })` — the RuleTester analog, asserting the *compiler-facing* contract: metadata legality (id namespace, `apiVersion`, reserved-capability violations, Q23); route uniqueness + normalized-key conflicts including param-name mismatches (Q24); schema IR validity — table prefixes, reserved columns, NOT NULL defaults, sensitive-field classification on shared tables (Q25); migration determinism (two compiles → identical hash; destructive ops correctly flagged, Q26); hook classification (veto-capable hooks only in `before*`; after-hooks fail-isolated — a deliberately failing observer must not fail a sign-in flow, Q27); middleware declared-reads enforcement (Q28); config validation and the "config cannot change graph" property (Q30); redaction defaults (secrets never appear in spans/events the plugin emits). (2) `TestAuth` integration kit — Fastify `inject` analog: compile the plugin against in-memory repositories + `TestClock` + the HttpApi test client (no network, no DB) and run real flows (sign-up → sign-in → session expiry) with deterministic time. Also export fixture suites for dependency scenarios ("host with dependency plugin present/absent") asserting the exact documented compile errors (Q21–Q23) — so error-message UX is itself tested. Every official plugin runs the contract suite in CI; the registry (Q20) accepts only plugins whose published contract run passes [registry enforcement is policy, mark as product decision].

**Confidence:** high.

## Recommended defaults for effect-auth

1. **Contract**: `definePlugin()` → frozen declarative record; required = namespaced `id` + `apiVersion: 1`; every contribution optional; no imperative registration APIs, no mutation after freeze.
2. **Compatibility**: integer `apiVersion` (exact match at v1; semver ranges when API v2 exists); Nuxt-style `compatibility` checks at compile; registry + machine-readable compatibility matrix; codemods per Plugin API major; support current + previous generation only.
3. **Dependencies**: `requiresPlugins` (ids; structure, ordering, migrations) + `requiresCapabilities` (namespaced authority strings; substitution, conflicts). Tags are service-level only; layers additionally declare `layerRequires` tag data for compiler cross-checks.
4. **Validation & UX**: compile-time Kahn topo sort; every diagnostic = stable code + summary + full path/offending plugins + site + hint + docs URL; `auth plugin list --graph|--hooks` prints resolved DAGs and hook orders.
   4a. **Diagnostic code taxonomy** (one stable code per failure class; each gets a docs page, ESLint-style):
   - `E_PLUGIN_DUPLICATE_ID` — two plugins share an id (PRD §36).
   - `E_PLUGIN_MISSING_DEP` / `E_PLUGIN_CYCLE` — unresolved or cyclic `requiresPlugins` (Q22).
   - `E_API_VERSION_UNSUPPORTED` — plugin `apiVersion` outside the host's supported generations (Q20).
   - `E_NAMESPACE_RESERVED` — third-party contribution to `auth.*` / `effect-auth.*` (Q23).
   - `E_CAPABILITY_MISSING` / `E_CAPABILITY_CONFLICT` — unsatisfied or exclusively-clashed capability (Q21/Q23).
   - `E_ROUTE_CONFLICT` — exact or param-name collision (Q24).
   - `E_SCHEMA_CONFLICT` — table/column/prefix violation, duplicate shared-table column (Q25).
   - `E_MIGRATION_DESTRUCTIVE` — destructive op without `--allow-destructive` (Q26).
   - `E_HOOK_VETO_INVALID` — abort returned from a non-abortable (`after*`) hook (Q27).
   - `E_MIDDLEWARE_READS_UNDECLARED` — middleware touches undeclared request state (Q28).
   - `E_CAPABILITY_NOT_INSTALLED` — runtime config references an uninstalled capability; fail closed at startup (Q30).
5. **Namespaces**: `auth.*` and `effect-auth.*` reserved; third-party namespace from npm scope; `@effect-auth/registry` catalog with exclusivity metadata; exclusive capabilities conflict loudly, `multi` capabilities aggregate; never last-wins.
6. **Routes**: normalized `METHOD + path` keys; exact and param-name conflicts are compile errors; compiler-injected `/<pluginId>/` prefix for third parties; explicit attributed `extendEndpoint` for extension; `override: true` required for replacement.
7. **Schema**: plugin tables auto-prefixed; core tables extensible only via declared scalar extensions (no reserved names, no NOT NULL-without-default, sensitive fields rejected); cross-plugin ALTER prohibited; relations via explicit FKs or link-style tables.
8. **Migrations**: IR-diff generated, deterministic + hash-stamped, `-- plugin:` annotations; ordering = plugin topo, core first; handwritten steps append-only; destructive ops need `--allow-destructive` and cross-plugin reference checks.
9. **Hooks & middleware**: `before*` may abort with typed `HookAbortError` and transform context; `after*`/observers fail-isolated by construction; named middleware phases (`preAuth`/`auth`/`postAuth`), ordering = topo → explicit order → id; middleware declares what it reads; context propagation via services/FiberRef, never chain generics.
10. **Client**: single HttpApi contract → `HttpApiClient`-derived client namespaced by plugin group; plugin `client` exports are additive sugar only; no paired client-plugin definitions.
11. **Runtime seam**: "installation is code, configuration is data"; config validated against the frozen graph at startup with typed `CapabilityNotInstalled` failures; per-tenant resources via `LayerMap`; contract test asserts config alone cannot change routes/schema.
12. **Type strategy**: keep `Auth.make` input non-generic over plugins; per-plugin contribution interfaces merged by top-level intersection (O(#plugins), shallow instantiation); use builder/type-builder patterns, `const` generics, variance annotations, `satisfies`; never let the type system do graph reasoning.
13. **Test harness**: `@effect-auth/test` ships `runPluginContractTests` (RuleTester model) + `TestAuth` in-memory kit; all official plugins run it in CI; compile-error UX is itself asserted by fixtures.

## Open questions for the user

1. **Registry policy (Q20/Q31)**: how strict should the plugin registry be?
   - (a) Curated registry, contract-test pass required for listing (nuxt/modules model)
   - (b) Open listing, compatibility metadata optional
   - (c) No registry at v1; docs page of known plugins only
2. **Dual-generation support (Q20)**: when Plugin API v2 lands, how long do we run both?
   - (a) Current + previous (recommended)
   - (b) Current only, hard cut with codemod
   - (c) Indefinite shims (rejected by this research — Gatsby lesson)
3. **Third-party extensions of core routes (Q24)**: should `override: true` be allowed for third parties at all, or reserved to official plugins?
   - (a) Reserved to official plugins (safest)
   - (b) Allowed with loud `auth doctor` warning
   - (c) Allowed silently (rejected — conflicts with conflict-detection thesis)
4. **Shared-table extensions (Q25)**: how strict on `user.*` columns?
   - (a) Scalar attributes only, compiler-validated (recommended; better-auth-compatible)
   - (b) Disallow entirely; side tables only (Medusa-style; breaks better-auth parity)
   - (c) Free-form with warnings only
5. **Multi-capability strategies (Q23)**: may two plugins both provide an *exclusive* capability with an explicit user-picked winner (`Auth.make({ pick: { "auth.hasher": argon2() } })`)?
   - (a) Yes, explicit pick required (flexible)
   - (b) No; exclusive means compile error, swap via config-provided layer (simpler)
6. **Scope of v1 middleware phases (Q28)**: ship the three-phase model, or also Fastify-style fine-grained phases (`preValidation`-like) at v1?
   - (a) Three phases at v1, extensible enum later (recommended)
   - (b) Full phase taxonomy at v1
