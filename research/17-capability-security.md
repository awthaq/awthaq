# Capability security — Scientific Literature

Domain: the security science of extensible systems — capability models, isolation mechanisms, and plugin/marketplace supply chain. Maps the literature to effect-auth's plugin-compiler questions (Q20–Q31 of `research/00-questions.md`, Q7 governance, Q88–Q94 security engineering). This is the *scientific* layer under the practitioner baseline in `research/09-plugin-architecture.md` (which already cites Miller's ocap trio at bibliography level — this file is where they are actually read and applied).

**Relationship to the rest of the corpus:** the practitioner plugin-system prior art lives in `09-plugin-architecture.md`; operational session/token design in `04-sessions-tokens.md`; the better-auth feature benchmark in `02-better-auth.md`. This file supplies the *scientific security layer* — read 09 for what to build, this file for why it is defensible and where the v2 sandbox seam sits.

Corrections to the assignment brief, verified 2026-09: Jangda et al. "Not So Fast" is **USENIX ATC 2019**, not PLDI 2019; Lehmann et al. 2020 is titled "**Binary Security** of WebAssembly", not "Binary Safety"; Sejfia & Schäfer is **ICSE 2022**, not FSE; Duan et al. is **NDSS 2021**, not IMC; the CFI paper cited as 2009 is the **TISSEC 2009** extended version of the CCS 2005 paper.

## TL;DR

- Capabilities were born as an OS addressing primitive (Dennis & Van Horn 1966) and matured into a *composability* argument: authority should be conveyed as unforgeable references, never by who-calls-whom (Miller 2006). effect-auth's `requiresCapabilities` strings are a compile-time approximation of this discipline (Q21/Q23).
- The ocap literature's warning is precise: a capability *string* granted by ambient lookup is weaker than a capability *reference* handed from provider to consumer. The compiler must be the only place strings become references (Q23).
- "Installation is code, configuration is data" (Q30) is Chrome's MV3 model: static manifest permissions at install, runtime grants bounded by the static set. It is a security decision, not just an architecture decision.
- Sandboxing science is a solved *idea* with an unsolved *deployment story*: SFI (1993) → CFI/XFI (2005–2009) → WebAssembly (2017) → Spectre broke it → Swivel (2021) → provably-safe sandboxes (2022). A v2 Wasm story has precedent but real costs (45–56% perf gap on SPEC CPU).
- Every marketplace study (Chrome, Firefox, VS Code, npm) converges: **review, provenance, and least-privilege manifests do most of the work before any sandbox does**. VS Code extensions are effectively unsandboxed and the harm studies show exactly which non-sandbox controls fail.
- Chrome's own architecture review (Carlini et al. 2012) found the sandbox+permission model prevented privilege escalation but that the *injection channel* (HTTP scripts) was where severity lived — i.e., the marginal security comes from boring transport rules, not exotic isolation.
- MV3's load-bearing supply-chain control is the **remote-hosted-code ban** — the same decision PRD v1 makes with its "no dynamic install" non-goal. Document it as such.
- Macaroons (NDSS 2014) give the academic blueprint for purpose-scoped tokens: bearer capability + attenuating caveats, backwards-compatible. Directly applicable to effect-auth verification tokens (Q46) and API keys (Q59).
- Only ~40–48% of Chrome Web Store items comply with the *spirit* of least privilege (Picazo-Sanchez et al. 2022) — declaring permissions is easy to do badly, which is an argument for compiler-enforced capability grants over manifest self-declaration.
- Secrets (API keys, tokens) leak at scale through exactly the channel effect-auth must protect (Meli et al. 2019, NDSS): hash at rest, prefix-visible formats, scan-ready formats (Q59/Q92).

## Annotated bibliography

### Capability model origins & theory

**Jack B. Dennis, Earl C. Van Horn (1966). Programming Semantics for Multiprogrammed Computations.** *Communications of the ACM 9(3):143–155.* <https://dl.acm.org/doi/10.1145/365230.365252> — Introduced the capability as a machine primitive: a protected token naming an object plus the operations allowed on it, with create/execute/read/delete meta-instructions. Everything else in this file is elaboration; the core insight is that *authority is data you hold*, not a property of the caller. Implication for effect-auth: capability strings in plugin metadata are the 1966 idea in npm clothing — they work only if the runtime resolves them through one mediated mechanism (the compiler), never through ambient imports.

**Jerome H. Saltzer, Michael D. Schroeder (1975). The Protection of Information in Computer Systems.** *IEEE Computer 8(7) (extended from CACM 1974).* <https://web.mit.edu/saltzer/www/publications/protection/> — Canonical statement of least privilege, complete mediation, fail-safe defaults, separation of privilege, least common mechanism, psychological acceptability. Least privilege is the *policy* behind POLA; capabilities are one *mechanism* for it. For effect-auth: `requiresCapabilities` should be minimal by default and the contract test harness (Q31) should flag plugins that declare authority they don't exercise — psychological acceptability means the permission dialog (the compile report) must be readable.

**Henry M. Levy (1984). Capability-Based Computer Systems.** *Digital Press, 220 pp.* <https://homes.cs.washington.edu/~levy/capabook/> — The definitive survey of the first generation (Plessey 250, CAP, Hydra, StarOS, IBM System/38), freely available online. Its organizing lesson: every failed or fragile capability system failed at *unforgeability of names* or at *revocation*, not at the access-control logic. effect-auth's analog: capability strings must be unforgeable (registry-enforced namespaces, Q23) and revocation must be a designed primitive (Layer/Scope disposal), not an afterthought.

**Mark S. Miller, Ka-Ping Yee, Jonathan S. Shapiro (2003). Capability Myths Demolished.** *Johns Hopkins SRL Technical Report SRL2003-02.* <https://papers.agoric.com/assets/pdf/papers/capability-myths-demolished.pdf> — Systematically debunks the misconceptions that produce half-built capability systems: that capabilities are merely inverted ACLs, that holding a capability is mere "designation" without authority, and that capabilities inherently leak confidentiality or chain of custody. Proves proper capability systems support confinement, confidentiality, integrity — and that ACL-vs-capability comparisons are invalid without fixing the delegation story. For effect-auth: a `provides`/`requires` matrix *is* a delegation story; comparisons with better-auth-style ambient DI are invalid unless delegation is explicit (Q21).

**Mark S. Miller (2006). Robust Composition: Towards a Unified Approach to Access Control and Concurrency Control.** *PhD dissertation, Johns Hopkins University.* <https://papers.agoric.com/assets/pdf/papers/robust-composition.pdf> — The foundational object-capability text: systems composed of mutually suspicious components remain robust when (a) authority only flows through object references (ocap) and (b) concurrency follows non-blocking event-loop semantics (vats, promises). The same discipline that prevents confused-deputy authority leaks prevents deadlock/livelock — that's the "robust composition" thesis. For effect-auth: `Context.Tag`/`Layer` are already the reference-conveyance mechanism; the plugin compiler should guarantee plugins receive *capability handles* (services) and never ambient global access, and hook/event design should be non-blocking-first (ties into Q13, Q27).

**Gerwin Klein, Kevin Elphinstone, Gernot Heiser, et al. (2009). seL4: Formal Verification of an OS Kernel.** *SOSP '09, ACM.* <https://dl.acm.org/doi/10.1145/1629575.1629596> — Machine-checked proof that a capability-based microkernel implements its access-control spec exactly: no ambient authority, no leaks, complete mediation — proven, not asserted. The capstone evidence that capability enforcement can be made airtight when the mechanism is small. For effect-auth: the lesson is proportionality — effect-auth cannot prove its compiler, but it can keep the authority-bearing mechanism (namespace registry + capability resolution) small enough to test exhaustively (Q23, Q31, Q94).

**Robert N. M. Watson, Jonathan Woodruff, Peter G. Neumann, et al. (2015). CHERI: A Hybrid Capability-System Architecture for Scalable Software Compartmentalization.** *2015 IEEE Symposium on Security and Privacy.* <https://ieeexplore.ieee.org/document/7163016> — Hardware capabilities (unforgeable 129-bit tags, sealed per-domain) enabling fine-grained compartments with low crossing cost, addressing Levy's historical weakness that pure-software capability systems paid too much. The modern revival of everything in Levy 1984. For effect-auth: the long-horizon ceiling — if plugin sandboxing ever wants hardware-grade compartments, the capability *vocabulary* effect-auth establishes in v1 (`auth.*` strings) is the interface such compartments would consume.

**Lianghao Shen, Yusong Tan, Pan Dong, Jun Ma, Xiaoling Li (2022). A Simple and Efficient Object-Capability Revocation Method.** *ITCC '22 (4th International Symposium on Information Technology and Computer Communications), ACM, pp. 132–138.* <https://dl.acm.org/doi/10.1145/3548636.3548656> — Builds an efficient revocation mechanism for object-capability systems — the historically weakest link Levy 1984 documented (delegation without an un-delegation story). For effect-auth: revocation should ride Effect's scoped lifecycle — disposing a plugin's Layer removes its capability provider for new acquirers, and the contract test harness (Q31) should assert a revoked capability *fails acquisition*, not that it silently keeps working (Q20, Q30).


### Isolation science: SFI → CFI → XFI → WebAssembly

**Robert Wahbe, Steven Lucco, Thomas E. Anderson, Susan L. Graham (1993). Efficient Software-Based Fault Isolation.** *SOSP '93, ACM.* <https://dl.acm.org/doi/10.1145/168619.168635> — Proved untrusted binary code can be confined inside one address space by code rewriting (mask + guard sequences) at modest cost, without hardware process boundaries. The founding result of software sandboxing. For effect-auth: the existence proof that "same-process, verified-at-load" isolation is possible — the *load-time verification* pattern is what effect-auth's compiler already does for metadata, and what a future binary-sandbox story would extend to code (PRD non-goal today; seam documented below). `13-modularity-foundations.md` uses SFI for the cost-economics framing of the compile-time-only world; this file follows the isolation lineage *forward* to the WebAssembly line.

**Martín Abadi, Mihai Budiu, Úlfar Erlingsson, Jay Ligatti (2009). Control-Flow Integrity: Principles, Implementations, and Applications (extended version).** *ACM Transactions on Information and System Security 13(1) (original: CCS 2005).* <https://dl.acm.org/doi/10.1145/1609956.1609960> — Formalizes CFI: execution may follow only the edges of a pre-computed control-flow graph, enforced by ID checks before indirect transfers. The deeper idea is that *a static policy about all future behavior can be checked cheaply at each transfer*. For effect-auth: this is the same shape as the plugin compiler — compute the legal graph (capabilities, hooks, routes) once at build, then enforce at every crossing (hook invocation, route registration). Q27's "veto-capable hooks only in `before*`" is a CFI-style invariant.

**Úlfar Erlingsson, Martín Abadi, Michael Vrable, Mihai Budiu, George C. Necula (2006). XFI: Software Guards for System Address Spaces.** *OSDI '06, USENIX.* <https://www.usenix.org/legacy/event/osdi06/tech/full_papers/erlingsson/erlingsson.pdf> — Combines SFI and CFI to run mutually distrustful in-kernel extension modules in one address space, with access-control guards on memory regions ("flexible access control and dynamic memory management"). The canonical demonstration that *extension modules* — not just whole programs — can be confined. For effect-auth: XFI is the direct academic ancestor of "plugin sandbox"; its guard-everything-you-touch model is what a v2 Wasm design would recreate with Wasm's type system instead of binary rewriting.

**Andreas Haas, Andreas Rossberg, Derek L. Schuff, Ben L. Titzer, Dan Gohman, Luke Wagner, Alon Zakai, JF Bastien, Michael Holman (2017). Bringing the Web up to Speed with WebAssembly.** *PLDI 2017, ACM.* <https://dl.acm.org/doi/10.1145/3062341.3062363> — The WebAssembly MVP paper: a safe, portable virtual ISA with structured control flow, a linear memory, and a formally specified semantics; sandboxing is by construction (no untyped pointers, memory-bounds-checked by the engine). For effect-auth: this is the candidate substrate for a v2 plugin sandbox — plugins compiled to Wasm could receive capability services through explicit imports, making `requiresCapabilities` mechanically enforced rather than declarationally enforced. Today it is a documented seam, not a plan (PRD non-goal).

**Abhinav Jangda, Bobby Powers, Emery D. Berger, Arjun Guha (2019). Not So Fast: Analyzing the Performance of WebAssembly vs. Native Code.** *USENIX ATC '19.* <https://www.usenix.org/conference/atc19/presentation/jangda> — Measures Wasm at 45–56% slower than native on SPEC CPU (Firefox best, Safari worst) and diagnoses why (garbage collection, checked bounds, call-cost asymmetries). The corrective to "Wasm is near-native" marketing. For effect-auth: if a sandbox seam is ever built, the honest expectation is password-hashing and token-HMAC hot paths would stay native (outside the sandbox) while plugins' *glue* code is isolated — an XFI-style split of trusted core from untrusted composition.

**Daniel Lehmann, Johannes Kinder, Michael Pradel (2020). Everything Old is New Again: Binary Security of WebAssembly.** *29th USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity20/presentation/lehmann> — Shows the Wasm sandbox does not make compiled programs safe: memory bugs in C/C++ compiled to Wasm remain exploitable *inside* the module (data corruption, intra-module control-flow hijack), and this matters as Wasm becomes a packaging target outside the browser. For effect-auth: Wasm isolation would protect effect-auth *from* plugins, not plugins *from their own dependencies* — the npm supply chain survives the sandbox (Q92, Q94).

**Aaron Hilbig, Daniel Lehmann, Michael Pradel (2021). An Empirical Study of Real-World WebAssembly Binaries: Security, Languages, Use Cases.** *WWW '21, ACM.* <https://dl.acm.org/doi/10.1145/3442381.3450138> — Analyzes 8,461 unique Wasm binaries: nearly all come from C/C++ with minimal use of Wasm-specific hardening features — i.e., in practice Wasm is a *transport format for legacy unsafe code*, not a safety upgrade. For effect-auth: a future "sandboxed plugin" story must specify what plugins compile *from*; accepting arbitrary C-derived Wasm brings Lehmann-2020's vulnerability profile along with the sandbox.

**Shravan Narayan, Craig Disselkoen, Daniel Moghimi, Sunjay Cauligi, Evan Johnson, Zhao Gang, Anjo Vahldiek-Oberwagner, Ravi Sahita, Hovav Shacham, Dean Tullsen, Stefan Savage (2021). Swivel: Hardening WebAssembly against Spectre.** *30th USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity21/presentation/narayan> — Demonstrates that speculative execution lets malicious Wasm code break the sandbox or coerce victim code into leaking secrets (shared speculation windows), and builds a compiler that prevents it — the basis for Fastly's production edge sandbox. For effect-auth: the "sandbox guarantee" conversation has a hardware-tax line item; any v2 sandbox story must either adopt Swivel-grade techniques or scope its threat model to exclude speculatively-hostile plugins explicitly (Q88 threat model).

**Jay Bosamiya, Wen Shih Lim, Bryan Parno (2022). Provably-Safe Multilingual Software Sandboxing using WebAssembly.** *31st USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity22/presentation/bosamiya> — Produces *machine-checked proofs* that translated sandboxed modules cannot exceed their interface — combining Wasm isolation with verified translation, award-winning for showing provable sandbox safety is practical. For effect-auth: the end-state of the seam documented here — a plugin contract (`apiVersion`, capability imports) that a verifier, not just a reviewer, can check. The registry + contract-test harness (Q23, Q31) is the embryonic version of this: machine-checkable plugin properties.

### Browser and IDE plugin marketplace security

**Lei Liu, Xinwen Zhang, Guanhua Yan, Songqing Chen (2012). Chrome Extensions: Threat Analysis and Countermeasures.** *NDSS 2012.* <https://www.ndss-symposium.org/ndss2012/ndss-2012-programme/chrome-extensions-threat-analysis-and-countermeasures/> — Attacks Chrome's extension model *from inside the policy*: malicious extensions abusing legitimately-granted permissions (info harvesting, injection), plus countermeasures. Establishes the recurring finding that a correct permission architecture still fails when *any* party in the manifest is malicious. For effect-auth: compile-time capability validation protects against *accidents* and *overreach*, not against a plugin that truthfully declares and maliciously uses `auth.user` — governance (Q7) must cover behavior, not just declarations.

**Nicholas Carlini, Adrienne Porter Felt, David Wagner (2012). An Evaluation of the Google Chrome Extension Security Architecture.** *21st USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/carlini> — Manual review of 100 extensions found 70 vulnerabilities in 40; Chrome's privilege separation blocked privilege escalation, and two *boring* rules (ban HTTP-injected scripts and inline scripts) would prevent 47 of the 50 most severe holes. The empirical model of "sandbox + manifest + transport hygiene". For effect-auth: the equivalent hygiene rules are compiler-enforced — no plugin code fetched at runtime (MV3-style), no secrets in hook transforms (Q93 redaction), strict Schema parsing at every boundary (Q41). The sandbox was not the biggest win; the lint rules were.

**Ignacio Sánchez-Rola, Xabier Ugarte-Pedrero, Igor Santos, Davide Balzarotti (2017). Security Analysis of Browsers Extension Resources Control Policies.** *26th USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/sanchez-rola> — Shows side channels through extension resource-control policies allow enumerating installed extensions across all major browser families — installed-but-supposedly-invisible software leaks its existence. For effect-auth: "silent" installed plugins (disabled, feature-flagged off) must not be observable through error messages, timing, or route sets — consistent 404s and startup-time capability checks (Q30) are the defense (ties to enumeration resistance, Q90).

**Pablo Picazo-Sanchez, Lara Ortiz-Martin, Gerardo Schneider, Andrei Sabelfeld (2022). Are chrome extensions compliant with the spirit of least privilege?** *International Journal of Information Security 21(6):1283–1297.* <https://link.springer.com/article/10.1007/s10207-022-00610-w> — Only ~40–48% of analyzed Web Store items comply with the *spirit* (not letter) of least privilege; ships developer check tools and vendor-acceptance scripts that analyze requested-vs-used permissions. The quantified gap between declaring authority and needing it. For effect-auth: self-declared `requiresCapabilities` will drift; the contract test harness (Q31) should compute *used* capabilities from plugin code/IR and diff against *declared* — the vendor-acceptance-script pattern verbatim.

**Benjamin Eriksson, Pablo Picazo-Sanchez, Andrei Sabelfeld (2022). Hardening the Security Analysis of Browser Extensions.** *SAC '22 (ACM Symposium on Applied Computing), pp. 1694–1703.* <https://dl.acm.org/doi/10.1145/3477314.3507098> — Systematic study of extension attack entry points: 1,349 extensions vulnerable to inter-extension attacks leading to XSS, and a cluster of 4,410 "New tab" extensions performing traffic stealing; countermeasures via permission-model refinement and manifest declarations. For effect-auth: plugins compose with *each other*, not just the host — inter-plugin authority leakage (via shared `Context` tags, Q9, and shared-table columns, Q25) is the same inter-extension channel; the compiler's conflict rules are the defense.


**Valerio Bucci, Wei Li (2023). From Manifest V2 to V3: A Study on the Discoverability of Chrome Extensions.** *RAID 2023, Springer LNCS.* <https://dl.acm.org/doi/10.1007/978-3-031-49187-0_10> — Crawls 108,416 extensions and measures how MV3's Web-Access-Request tightening changed what security tooling can see (4–10% relative reduction in WAR detectability). One of the first MV2→MV3 academic assessments: the platform shift moved both attacker and defender visibility. For effect-auth: any tightening of the plugin contract (v1→v2) changes what `auth doctor` and registry scanners can detect — version the contract with migration support (Q20, Q100), or detection tooling silently degrades.

**Karlo Lukic, et al. (2025). Privacy vs. Profit: The Impact of Google's Manifest Version 3 (MV3) Update on Ad Blocker Effectiveness.** *arXiv:2503.01000 (preprint; PoPETs-track listing).* <https://arxiv.org/abs/2503.01000> — [PARTIAL — venue; authors beyond the first unverified] Measures MV2 vs MV3 ad blockers: no statistically significant reduction in blocking or anti-tracking effectiveness for MV3 counterparts, against the widespread assumption that MV3's capability restrictions would gut functionality. For effect-auth: the one measured counterpoint to "least privilege breaks plugins" — when capabilities are declared and matched to real need, tightening authority can be nearly free. Pairs with Bucci & Li for the MV2→MV3 decision record.


**Elizabeth Lin, Igibek Koishybayev, Trevor Dunlap, William Enck, Alexandros Kapravelos (2024). UntrustIDE: Exploiting Weaknesses in VS Code Extensions.** *NDSS 2024.* <https://www.ndss-symposium.org/ndss-paper/untrustide-exploiting-weaknesses-in-vs-code-extensions/> — Systematically maps four vulnerability sources in the VS Code marketplace (e.g., marketplace workspace trust gaps, extension activation) and verifies code-execution exploits affecting >6M installs; VS Code extensions run unsandboxed with the user's full privileges. The cautionary tale for effect-auth as a *developer-machine* product too: CLI and `@effect-auth/test` execute plugin code. For effect-auth: contract tests must run plugins in a thrown-away process with a test-double capability set (Q31), never the developer's real credentials — the UntrustIDE failure mode is "trusted tool runs untrusted extension at full authority".

**Shehan Edirimannage, Charitha Elvitigala, Asitha Indrajith, Wahanawatta Don, Praboda Wijesekara, Ibrahim Khalil (2024). Developers Are Victims Too: A Comprehensive Analysis of The VS Code Extension Ecosystem.** *arXiv:2411.07479 (preprint).* <https://arxiv.org/abs/2411.07479> — Large-scale ecosystem analysis finding the extension host lacks practical security controls and lets untrusted third-party code run, with developers themselves as the under-protected victims. [PARTIAL — preprint, venue unverified.] For effect-auth: plugin *authors* and plugin *users* are both victims of ecosystem attacks (typosquatted deps, hijacked publishes); the governance model (Q7) must protect the supply chain's producers (npm provenance, Q92) as well as its consumers.

**Nirvan Jagpal, Elaine Raybuck, Peter Snyder, et al. (2015). Trends and Lessons from Three Years Fighting Malicious Extensions.** *Google Security Blog / research report.* <https://research.google.com/pubs/archive/43824.pdf> — [non-academic] Google's operational account of fighting malicious Chrome extensions at scale: monetization-driven abuse, the arms race between review and evasion, and the move to automated + human-hybrid curation. For effect-auth: the realistic preview of operating a plugin registry (Q7, Q98) — abuse follows monetization (crypto-mining, credential proxying via `Mailer`/`RateLimiter` capabilities), and curation automation is a permanent cost, not a launch feature.

### Package-ecosystem supply chain

**Marc Ohm, Henrik Plate, Michael Meier, Arnold Sykosch (2020). Backstabber's Knife Collection: A Review of Open Source Software Supply Chain Attacks.** *DIMVA 2020, Springer.* <https://arxiv.org/abs/2005.09535> — Dataset and analysis of 174 malicious packages from real attacks across npm, PyPI, RubyGems; shows most attacks execute at *installation* (install scripts), and introduces a reference taxonomy of attack vectors. For effect-auth: npm is the plugin supply chain; `postinstall` is the attack surface the PRD cannot lint away — governance should mandate provenance (Q92) and the registry should prefer plugins whose packages declare no install scripts.

**Markus Zimmermann, Cristian-Alexandru Staicu, Cam Tenny, Michael Pradel (2019). Small World with High Risks: A Study of Security Threats in the npm Ecosystem.** *28th USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity19/presentation/zimmerman> — Demonstrates a real targeted attack chain via npm's small-world structure (reverse-engineering a popular ad blocker and publishing a lookalike), and shows install scripts and maintainer-account compromise are systemic, not exotic. For effect-auth: `requiresPlugins` graph edges (Q21) must be *versioned and pinned* in lockfiles; a plugin's dependencies are effectively transitive plugins with zero declared capabilities — the compiler's `auth doctor` should surface unexplained transitive authority.

**Ruian Duan, Omar Alrawi, Ranjita Pai Kasturi, Ryan Elder, Brendan Saltaformaggio, Wenke Lee (2021). Towards Measuring Supply Chain Attacks on Package Managers for Interpreted Languages.** *NDSS 2021.* <https://arxiv.org/abs/2002.01139> — Systematic measurement framework (MALOSS) comparing malicious-package detection across npm/PyPI/RubyGems; packages fail through remarkably few behavioral patterns (exfiltration, eval, download-and-execute). For effect-auth: the same small behavior vocabulary applies to plugins — a capability-annotated plugin can be *behaviorally* checked against its declarations (static call-graph vs `requiresCapabilities`), which is exactly the vendor-acceptance-script pattern (Q31, Q94).

**Piergiorgio Ladisa, Henrik Plate, Matias Martinez, Olivier Barais (2023). SoK: Taxonomy of Attacks on Open-Source Software Supply Chains.** *2023 IEEE Symposium on Security and Privacy.* <https://arxiv.org/abs/2204.04008> — The reference SoK: a threat tree of over 100 unique OSS supply-chain attack vectors, mapped to concrete defenses and controls, validated with security researchers. For effect-auth: use this as the checklist for Q92 (provenance, attestations, signed releases) and Q7 (registry trust model) — "plugin ecosystem security" is not one control but a chosen subset of a known taxonomy, and the SoK names which subset matches which attacker.

**Taoufik Sejfia, Max Schäfer (2022). Practical Automated Detection of Malicious npm Packages.** *ICSE 2022, ACM.* <https://dl.acm.org/doi/10.1145/3510003.3510104> — Combines three layers (classifiers trained on npm's malicious-package corpus, behavioral heuristics, semantic comparison against benign lookalikes) to catch malicious packages, including typosquatting patterns, in the Amalfi system; public artifact. For effect-auth: the registry's listing gate (Q98) can and should be mechanical — classifiers plus a required contract-test pass — rather than human review alone, because human review is exactly what the typosquatting attacks defeat.

**Nusrat Zahan, Laurie Williams, Thomas Zimmermann, Patrice Godefroid, Brendan Murphy, Chandra Sekhar Maddila (2022). What are Weak Links in the npm Supply Chain?** *ICSE-SEIP 2022, ACM/IEEE.* <https://arxiv.org/abs/2112.10165> — Interviews npm's own security engineers plus ecosystem data to rank the weak links (typosquatting, maintainer-account compromise, malicious packages, dependency confusion) and how they are actually caught in practice. For effect-auth: the registry's threat list should be built the same way — from operators' incident experience, not from academic novelty — and "maintainer takeover" is a governance problem (Q7: 2FA, org ownership, transfer audits), not a code problem.

**Shradha Neupane, Grant Holmes, Elizabeth Wyss, Drew Davidson, Lorenzo De Carli (2023). Beyond Typosquatting: An In-depth Look at Package Confusion.** *32nd USENIX Security Symposium.* <https://www.usenix.org/conference/usenixsecurity23/presentation/neupane> — Measures the full space of package-confusion attacks (exact typosquatting, combosquatting, imitation) and proposes detection beyond string distance; shows confusion attacks are broader and more nuanced than the classic typosquat. For effect-auth: plugin-id squatting (`effect-auth-passward` vs `effect-auth-password`) needs the same treatment — registry listing should check confusion against official plugin names, not just exact matches (Q98).

### Capability tokens: macaroons, bearer URLs, secrets

**Arnar Birgisson, Joe Gibbs Politz, Úlfar Erlingsson, Ankur Taly, Michael Vrable, Mark Lentczner (2014). Macaroons: Cookies with Contextual Caveats for Decentralized Authorization in the Cloud.** *NDSS 2014.* <https://www.ndss-symposium.org/ndss2014/ndss-2014-programme/macaroons-cookies-contextual-caveats-decentralized-authorization-cloud/> (PDF: <https://www.ndss-symposium.org/wp-content/uploads/2017/09/04_3_1.pdf>) — Bearer credentials carrying an HMAC-chained list of *caveats* that only ever *attenuate* authority (context, expiry, third-party discharge), backwards-compatible with existing bearer infrastructure. The academic standard for "least-privilege tokens people actually deploy". For effect-auth: purpose-scoped verification tokens (Q46) and API-key scopes (Q59) should be designed caveat-first: issue broad-at-issuance-time, attenuate per-use (TTL, single-use, principal-bound), never widen. Plugin capability tokens should follow the same attenuation-only rule (Q30: config may narrow, never amplify).

**Kevin Fu, Emil Sit, Kendra Smith, Nick Feamster (2001). Dos and Don'ts of Client Authentication on the Web.** *10th USENIX Security Symposium.* <https://www.usenix.org/conference/10th-usenix-security-symposium/dos-and-donts-client-authentication-web> — The classic field study of 27 sites' web-auth flaws, deriving design hints for capability-URL-style bearer tokens: sufficient entropy, never in URLs of third-party requests, careful with referrer/logs, revocation semantics. For effect-auth: magic links and email-verification tokens (Q46/Q57) *are* capability URLs; this paper plus the W3C TAG guidance below is the checklist for their generation, transmission, and logging discipline (Q93).

**W3C Technical Architecture Group (2014). Good Practices for Capability URLs.** *W3C TAG finding.* <https://www.w3.org/2001/tag/doc/capability-urls/> — [non-academic] Practitioner canon for unguessable capability URLs: high entropy, limited lifetime, scoped audience, exclusion from logs and analytics. For effect-auth: the exact standard `@effect-auth/core` should encode for magic-link and invitation tokens (Q46), and its contract tests should assert (entropy source, TTL enforcement via `TestClock`, Q18).

**Michael Meli, Matthew R. McNiece, Bradley Reavey (2019). How Bad Can It Git? Characterizing Secret Leakage in Public GitHub Repositories.** *NDSS 2019.* <https://www.ndss-symposium.org/ndss-paper/how-bad-can-it-git-characterizing-secret-leakage-in-public-github-repositories/> — Scans billions of GitHub files, collecting 200,000+ leaked credentials; secret leakage affects 100,000+ repositories with thousands of new unique secrets daily, most credentials remaining valid when discovered. For effect-auth: plugin *authors* hold high-value secrets (OAuth client secrets for their provider plugins); the framework's stance must assume leakage — hash API keys and session tokens at rest (Q45/Q59), design keys as prefix-visible + hashed-body (Q59), and publish secret-scanning patterns so leaked plugin credentials are detectable (Q92).

**Torsten Lodderstedt, Mark McGloin, Phil Hunt (2013). OAuth 2.0 Threat Model and Security Considerations.** *IETF RFC 6819 (Informational); updated by RFC 9700.* <https://www.rfc-editor.org/rfc/rfc6819> — [non-academic] The protocol-community canon for token threats and countermeasures: limit token scope, bound lifetime, one-time usage, audience-bind tokens, rotate refresh tokens, never embed credentials in shipped code (§5.3.1 is the Meli et al. finding stated as a requirement). For effect-auth: the official-plugin OAuth providers (Q54) and API-key plugin (Q59) inherit this checklist; effect-auth should enforce — not just document — the token countermeasures (structural TTL, single-use, audience) so plugin authors cannot opt out.

## Cross-cutting themes for effect-auth

**Security model conclusion — what to do before sandboxing.** Across five decades and three ecosystems (OS kernels, browsers, package registries), the literature yields one ordered playbook for running third-party code safely *without* a sandbox: (1) make the plugin surface statically declarative, inspectable without execution; (2) enforce least-privilege capability contracts *mechanically* — computed from use, never self-declared (Picazo-Sanchez et al.; Eriksson et al.); (3) hard-code transport and lifecycle hygiene (no remotely-fetched code, validated boundaries) because that is where severity actually lived (Carlini et al.; MV3's remote-code ban); (4) require provenance and attestations for everything published (Ladisa et al.; Ohm et al.); (5) gate registry listing with automated detection plus mandatory contract tests, not human review alone (Sejfia & Schäfer; Jagpal et al.); (6) assume secrets leak and design accordingly (Meli et al.). A v2 sandbox then has a known menu to build on: explicit capability imports (Haas et al., XFI shape), in-module vs cross-module boundary discipline (XFI), an honest performance budget (Jangda et al.), a stated speculative-execution position (Swivel), and a machine-checkable plugin contract (Bosamiya et al.). effect-auth v1 should implement (1)–(6) and *design the seam* — capability strings as future sandbox imports — without shipping the sandbox.

1. **Capability strings are authority, and the compiler is the unforgeability mechanism (Q21, Q23).** The ocap canon (Dennis & Van Horn, Miller, Myths Demolished) says authority must be unforgeable and conveyed, never ambient. Strings are forgeable by nature; the registry + reserved-namespace grammar (Q23) makes *forgery a compile error*, which is the only enforcement effect-auth has. Design consequence: the compiler — not TypeScript, not convention — resolves `requiresCapabilities` to concrete Layer-provided services, and third parties cannot mint `auth.*` names. This is the 1966 mediated-meta-instruction pattern.
  - Unforgeability ⇒ only `definePlugin()`/the compiler can mint capability names; a plugin reaching a service Tag it never required is a lint error (`E_CAPABILITY_UNDECLARED`) — the CFI "checked at every crossing" pattern applied to DI.
  - Conveyance ⇒ plugins receive typed capability handles via their layer, never module-level singletons — the object-capability "references only" rule in TypeScript clothing.

2. **POLA has a measurable failure rate when self-declared (Q23, Q31).** Picazo-Sanchez et al.: ~60% of Web Store items over-declare. Countermeasure with precedent: compute *used* capabilities from the plugin IR and diff against *declared* at contract-test time (the vendor-acceptance-script pattern). This upgrades `requiresCapabilities` from an honor system to a checked invariant, and feeds `auth doctor`.
  - The diff report is user-facing documentation: a compile-time "permission dialog" in Saltzer–Schroeder's psychological-acceptability sense — `auth doctor --capabilities` prints granted vs used per plugin.
  - Over-declaration found by the diff is a *warning* at compile and a *registry listing blocker* — two audiences, one check.

3. **"Installation is code, configuration is data" is a security boundary, not just a DX nicety (Q30).** Chrome's `permissions` vs bounded `optional_permissions` is the proven seam; macaroon caveats prove the runtime direction must be attenuation-only. effect-auth rule with literature backing: runtime config may narrow installed capabilities per tenant (caveats), never introduce or amplify them (`CapabilityNotInstalled` at boot). Sánchez-Rola additionally warns: don't leak installed-but-disabled plugins through behavior.
  - Concretely: the tenant config schema is *derived* from the installed plugin set, and config validation runs at boot against it — the generated schema is the enforcement point, not a hand-written mirror (Q15).
  - Disabled ≠ invisible: route sets, error codes, and timing must not reveal uninstalled/disabled plugins (Sánchez-Rola's enumeration lesson, aligned with Q90).

4. **Most of the sandbox's value is available before the sandbox: transport hygiene and manifest discipline (Q92, Q94, Q7).** Carlini et al.: 47/50 severe extension holes closed by two lint-level rules; MV3's remote-code ban is the load-bearing supply-chain control and PRD's "no dynamic install" non-goal is the same decision. effect-auth's equivalent hygiene: compiler-rejected remote/dynamic code contributions, Schema-validated boundaries, redaction defaults (Q93), no install scripts in plugin packages (registry preference per Ohm et al.).
  - Write the hygiene rules as compiler errors with stable codes (the diagnostic taxonomy already planned for conflicts) — Carlini's finding says two or three such rules outrank exotic isolation in prevented severity.
  - Prefer plugins whose npm packages declare no install scripts; make it a registry listing signal (Ohm et al.: installation is the attack moment).

5. **Governance is a permanent cost center, not a launch artifact (Q7, Q98).** Jagpal (Google's 3 years) and the VS Code studies show marketplace abuse is continuous, monetization-driven, and defeats naive review; Ladisa's SoK supplies the control taxonomy; Sejfia & Schäfer show the listing gate can be mechanical. A curated registry (contract-test pass + provenance + classifier) is the evidence-backed middle path between "open marketplace" and "impossible to police".
  - Minimum viable gate: contract-test pass + npm provenance + secret scan + malicious-package classifier verdict, recomputed per release (Jagpal's lesson: curation is continuous, not a launch event).
  - Set the "official plugin" trademark boundary in the same stroke (Q7) — Chrome's history shows brand signaling is itself a security control users lean on.

6. **Tokens and API keys should be designed as attenuable capabilities (Q46, Q59, Q92).** Macaroons supply the shape (attenuate-only caveats), Fu et al. and the W3C finding supply the URL-token hygiene, Meli et al. supplies the leakage assumption. Concrete: verification tokens carry purpose+TTL+single-use as structural caveats; API keys are prefix + hashed body; magic links follow capability-URL practice; all are testable invariants in `@effect-auth/test`.
  - Caveat-first API shape: tokens mint with purpose + TTL + audience and can only be *narrowed* downstream (macaroon discipline); verification-token storage carries the caveat set (Q46).
  - API keys: prefix-visible, body stored only as an HMAC — makes Meli-style leakage scannable and revocation cheap (Q59).

7. **The sandbox seam is real, sequenced, and priced (Q88, non-goal today).** SFI → CFI/XFI → Wasm → Swivel → Bosamiya is a 30-year arc with a clear moral: software isolation works when (a) the mechanism is small, (b) policy is checked at every crossing, and (c) the threat model names speculative execution honestly (Swivel) and accepts a performance tax (Jangda: 45–56%). v2 options in order of literature support: Wasm-with-explicit-capability-imports (Haas/XFI shape), process-per-plugin contract-test execution (UntrustIDE countermeasure), or documented abstention with the seam preserved (capability imports designed now so the boundary exists).
  - The seam to preserve now: capability strings map 1:1 onto sandbox import names, so a v2 sandbox swaps *enforcement*, not the contract.
  - The performance budget decides placement: `PasswordHasher`/HMAC stay native outside any sandbox (Jangda; Q53), plugin glue is isolatable.
  - The threat model (Q88) must state a position on speculative execution before any sandbox claim is made (Swivel).

8. **Defend the supply chain's producers too (Q7, Q92).** Meli et al. and Edirimannage et al. establish that plugin *authors* are victims (leaked provider secrets, hijacked publishes). npm provenance, attestations, and secret-scanning patterns for `@effect-auth/plugin-*` templates belong in the security story, not just consumer-side registry curation.
  - Ship `@effect-auth/create-plugin` templates that publish with provenance and document secret handling, so author-side leakage has a paved road (Q92).
  - Publish secret-scanning patterns for official plugins' credential formats so Meli-style scanners recognize effect-auth keys in the wild.

9. **The threat model (Q88) is the artifact that makes the rest testable.** The literature consistently shows that "secure against attackers" only becomes checkable when the model names its assets, its boundary, and its exclusions: seL4 proves enforcement *relative to a stated spec*; SFI/CFI/XFI isolate *across a named boundary*; Swivel exists because a threat model that omitted speculative execution was simply wrong; Ladisa's SoK turns "supply chain attacks" into a named, countable vector list. effect-auth's PRD-level threat model should follow that shape.
  - Name the trust boundary explicitly: host core vs plugin vs plugin-vs-plugin vs npm transitive dependencies — four boundaries with different enforcement today (compiler, compiler, conflict rules, nothing).
  - State exclusions honestly: v1 does not sandbox (so hostile-plugin *code* is out of scope and governance covers it), and the speculative-execution position only becomes mandatory if/when a sandbox is claimed.
  - Map every abuse case to a named control from the taxonomy (Ladisa) and a test in the abuse-case suite (Q94) — the Carlini method of ranking controls by prevented severity, not by novelty.

## Open questions

1. **Are string-named capabilities ambient authority? (Q21/Q23)** In strict ocap terms, `requiresCapabilities: ["auth.hasher"]` grants by *name* in a shared namespace — closer to ambient authority than to reference conveyance. The compiler-mediated resolution (registry-checked, reserved-prefix-enforced) narrows the gap but the design question stands: should capability acquisition always be *granted by another plugin or core* (an explicit provider edge in the graph) rather than *claimed by name*? The former is truer to Miller 2006; the latter is simpler and matches Chrome's curated-strings model.
2. **How much attenuation should runtime config be allowed? (Q30)** Macaroon caveats support attenuation-only runtime narrowing (per-tenant TTLs, scopes). Should tenant config also be able to narrow *declared* plugin capabilities per tenant (macaroon-style) or only select among installed providers (Chrome-style)? Both have literature backing; they produce different config schemas.
3. **Registry trust model vs Q7 governance:** curated listing with mechanical gates (Sejfia & Schäfer model) vs open listing with signed provenance only (npm model). The VS Code evidence (UntrustIDE, Edirimannage) argues against pure-open; the evidence does not fix *where* the line is.
4. **What does `auth doctor` owe the supply chain? (Q92/Q94)** Should the CLI run Ladisa-taxonomy-derived checks on the *application's* dependency tree (transitive npm authority), or is that out of scope for a framework and proper to delegate to `npm audit`/OSV tooling? The Zimmermann small-world result suggests plugin-level visibility into transitive deps has value generic tooling lacks.
5. **Is contract-test execution a sandbox boundary yet? (Q31)** UntrustIDE implies yes — plugin code must not run with developer credentials. Process-isolated test execution with test-double capabilities is cheap and evidence-backed; full Wasm isolation is not. Where's the v1 line: subprocess isolation now, or document it as v2 seam alongside the runtime sandbox?
6. **If v2 sandboxes arrive, what happens to `requiresCapabilities`?** Wasm imports make capabilities *mechanical* (Haas/XFI pattern) but conflict with TypeScript plugins running in-process. Decide early whether capability strings remain the contract while their *enforcement* upgrades from declared to imported — i.e., keep the vocabulary stable so the sandbox swaps enforcement only.
7. **Do plugin-issued tokens answer to the host's caveat chain? (Q46/Q59/Q20)** Plugins like the JWT plugin issue tokens *for the host*; macaroons suggest the host should issue a capability to the plugin that can only be attenuated — so every token a plugin mints carries host-auditable caveats (purpose, audience, TTL). That is a real constraint on plugin power (an OAuth plugin could no longer mint arbitrary tokens) and a genuine design decision: framework-enforced caveat minting vs plugin freedom with audit logging.
