Effect Idiom Dossier

The headline: this codebase does not run effects — it assembles them. Every runtime Effect.* reference in packages/core/src is a type annotation (Effect.Effect<Shape, E, R> in signatures). Actual execution idioms — Effect.gen, yield*, Effect.fn, pipe — live entirely in test code (AuthPlugin.test.ts, features/), where they are current and correct. Source-level Effect usage is deliberately declarative Layer composition: Layer.effect + a Layer.provideMerge fold, two real service declarations, and a type-level layer algebra (FoldLayer, ProvideMerged) that mirrors the runtime fold.

The 22.2 category score on the dashboard is an artifact of a v3-calibrated KPI contract: it counted Context.Tag (removed in Effect v4), mistook Array.prototype.flatMap for Effect.flatMap, and scored a gen/flatMap preference on a codebase with zero sequencing to prefer. This dossier corrects the record and audits what the score could not see.

Pattern Atlas

what the idiom actually is

The source stratum implements a plugin-as-Layer algebra. This is not missing idiom — it is a different, deliberate idiom: build-time composition where type-level functions (Validate<P>, FoldLayer<P>) statically refuse invalid assemblies, and the runtime does a topological fold.

F-01 provideMerge fold over static layers strength

The composition fold seeds with the first plugin's layer and folds Layer.provideMerge in topological order, so each plugin's requirement on its dependencies is satisfied, not adjacent — the code explicitly documents why Layer.merge and a Layer.empty seed both fail to type-check Auth.ts:337-345. This is advanced v4 Layer reasoning, applied correctly.

F-02 api/layer consistency enforced, not assumed strength

A plugin's HttpApi contract and its layer are two outputs of one AuthPlugin.layer call — handlers' HttpApiGroup.ToService requirement joins the layer's ROut, making BEH-EA-013 ("api and layer provably consistent") structural rather than conventional AuthPlugin.ts:163-196. Overloads per handler-branch handle the contravariant ROut honestly AuthPlugin.ts:198-234.

F-03 compile-time refusals double-locked at runtime strength

Validate<P> refuses duplicate ids and missing deps as type errors, and the same invariants are re-checked by Kahn's algorithm at runtime with a real cycle path in the message Auth.ts:212-249, 251-270. The test proves the runtime path through the public AuthPlugin.layer API only — no private-state backdoor AuthPlugin.test.ts:113-137.

F-04 init errors are thrown, not typed gap

throw new Error(...) ×4 at module-initialization boundaries: circular dependency Auth.ts:243, internal invariant Auth.ts:257, empty-plugin-tuple refusals Auth.ts:314,342. Defensible — these fire before any Effect exists, so a typed channel has nothing to flow through — but Data.TaggedError subclasses (e.g. CircularPluginDependency, EmptyPluginTuple) would make the failures catchable and testable by class, and the cycle-path message machine-readable. Cheap to fix before consumers exist.

F-05 Migration channels are maximally wide risk

Migration.up: Effect.Effect<void, unknown, unknown> Migrations.ts:14 — both the error channel and the requirement channel are unknown. Every migration loses all type-safety at exactly the boundary (persistence) where failures are most likely, and the placeholder is load-bearing: renumberMigrations already re-keys and propagates these values Auth.ts:273-286. When the Persistence stratum (BEH-EA-033+) lands, this must narrow to SqlClient-shaped R and tagged E — the module header says so itself. Highest-leverage idiom debt in the repo.

F-06 test-side idioms are current-generation strength (test stratum)

Tests exercise the modern v4 surface: it.effect + Effect.gen + yield* service access + Effect.provide via pipe AuthPlugin.test.ts:87-97, Effect.fn for handler shapes, and @ts-expect-error as a compile-refusal regression harness AuthPlugin.test.ts:76-82 — an unused @ts-expect-error is itself a tsc error, so the type-level tests cannot rot silently. When src grows workflows, the idiom baseline to imitate already exists here.

F-07 dependency idiom: exact-pinned RC discipline note

effect: 4.0.0-rc.115 pinned exact via pnpm catalog pnpm-workspace.yaml:13, with documented rationale (rc builds are not ABI-compatible across versions; conflicts must be loud) and a revisit trigger at 4.0.0 stable pnpm-workspace.yaml:5-11. This is the correct posture for a library that re-exports Effect types through its public API.

F-08 service identity is namespaced string keys design note

Plugin service keys embed the plugin id (effect-auth/plugin/${Id}, AuthPlugin.ts:39,129-130) and dependency declarations are recorded in a WeakMap with a live getter so subclasses inherit dependsOn with correct this-binding AuthPlugin.ts:109-159. Unusual, carefully reasoned — worth a second pair of eyes once a second real plugin (M1 Core) exercises subclassing.
